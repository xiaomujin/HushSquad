# HushSquad（静队）项目上下文与技术设计文档

> **文档用途**：将本文档完整提供给本地 AI 开发助手，作为最高上下文依据。
> **版本**：v0.2（修订稿）　**日期**：2026-11-16　**上一版**：v0.1
> **代号**：HushSquad / 静队
> **一句话定位**：类 TeamSpeak 的语音开黑软件，Rust + Tauri 2，桌面与 Android 优先，追求低延迟与强降噪。

## 0. 本版变更摘要（相对 v0.1）

v0.1 的架构骨架保留，以下 9 处做了修正。凡涉及原 v0.1 判断被推翻的，都写明原因，便于回看。

| # | 变更 | 原因（关键依据） | 影响章节 |
|---:|---|---|---|
| 1 | 延迟目标由单一「60–80 ms」改为**三档验收线 + 测量定义** | v0.1 的 30 ms DFN3 + 60–80 ms 端到端在算术上不成立：漏了 Opus 固定前瞻 6.5 ms 与两端设备缓冲各 5–10 ms | §2.2、§11.1、附录 A |
| 2 | 语音加密：OCB2-AES128 → **ChaCha20-Poly1305** | OCB2 已于 2018 年被证明可选择性伪造；Mumble 使用它是历史包袱，不是设计优点 | §7.3 |
| 3 | NAT 打洞 / 盲中继**移出主线** | TS 式拓扑下人人出站连服务器，**SFU 本身就是中继**，打洞无收益；且候选 crate 为 v0.1.0、13 次下载 | §7.1、§7.6 |
| 4 | MCU 混音**移出 v1**，只保留协议占位 | MCU 预混音与「按人调音量 / 单独收听」互斥；按听众混音是 O(n²) 且额外 30–50 ms | §8.1 |
| 5 | Opus 参数钉死为 10 ms 帧 + VOIP 模式 + in-band FEC，**不用 RestrictedLowDelay** | RLD 不减少 6.5 ms 前瞻，只为 2.5–10 ms 帧牺牲质量；2.5 ms 帧与 10 ms 的 DFN3 链路粒度矛盾 | §6.3 |
| 6 | 新增四个章节：**丢包与冗余 / 时钟漂移与重采样 / 安全与身份模型 / 延迟测量方法学** | v0.1 完全缺失，且都是低延迟语音的体验主导项 | §6.5、§6.6、§7.4、§11.5 |
| 7 | AEC 由「必经环节」降级为「可选、后置迭代」 | 开黑用户基本用耳机；软件 AEC3 需要可靠播放参考信号与两端时钟对齐，是整个项目最难的实时工程，且 TS3 从无 AEC | §6.2 |
| 8 | 项目结构：`apps/desktop` + `apps/android` → **单个 `apps/app`** | Tauri 2 里 Android 是同一工程的构建目标（`tauri android init` 生成 `gen/android`），拆两个 app 会重复前端与 IPC 接线 | §9 |
| 9 | 依赖清单**逐项核实**，4 个不存在的包移出，3 个近零使用的包降级为「不承重」 | 见附录 C（核实日期 2026-11-16） | §14、附录 C |

另外，Android 音频 I/O 由「AudioRecord + JNI 桥接」改为**复用 cpal**（cpal 0.18 已有 `cfg(target_os = android)` 后端，依赖 jni/ndk）——平台差异比 v0.1 预估的更小。

## 1. 给本地 AI 的工作说明

你是本项目的本地 AI 开发助手。以下决策已定，不得擅自更改；如认为需要更改，先给反例与数据，再等人确认：

1. **语言与核心栈**：语音处理、传输、服务器核心逻辑一律 Rust。
2. **客户端壳**：桌面与 Android 共用**同一个** Tauri 2 工程与同一套 Web 前端。
3. **Web 端暂缓**：不为浏览器兼容性做任何妥协。
4. **传输层**：自建加密 UDP，参考 Mumble 的**频道/用户/包模型**，不参考其加密与 NAT 方案；不引入 ICE/STUN/TURN/SDP。
5. **拓扑**：v1 只做 SFU 反射器，**无 P2P、无打洞、无 MCU**；服务器即中继。
6. **音频链路不可省略**：发送 采集 →（可选 AEC）→ 降噪 → AGC → Opus；接收 抖动缓冲 → 解码 → 混音 → 播放。
7. **降噪双档**：DeepFilterNet3 为质量档，RNNoise 为低延迟档，运行时切换；SilentMic-RT 不作为生产依赖。
8. **加密**：ChaCha20-Poly1305 + 每包序号/nonce，控制面 TLS 1.3 或 QUIC；**不实现 OCB2**。
9. **开发时间不是硬约束**：优先技术上限、可维护性、可验证性。
10. **许可证敏感**：AGPL/强传染依赖需显式标注并征询确认；`mumcord-codec` 已确认 AGPL-3.0-only，仅作参考。

输出代码或设计时请遵守：

- 明确所属 crate / 模块 / 平台；
- 标注假设、风险、未验证点，未验证结论必须写「待 M0 实测」；
- 不把「候选依赖」当作「已确定依赖」；附录 C 里标 ⚠️ 的包不得承重；
- 实时音频线程内禁止锁、堆分配、系统调用、日志格式化；
- 涉及协议先给消息/字段草案，再给实现建议；
- 跨平台代码区分桌面与 Android 的 I/O、权限、后台策略；
- 任何新增延迟都要给出毫秒数，并说明它落在附录 A 的哪一行预算里。

## 2. 项目背景与目标

### 2.1 产品目标

- 频道/房间树（参考 TeamSpeak / Mumble 的频道结构）；
- 小队语音：加入频道后与同频道成员实时语音；
- 按键说话（PTT）与即时静音；
- 选择性收听：按人调音量、静音、单独收听；
- 强降噪：压制机械键盘、风扇、椅子刮擦、背景人声；
- 低延迟：分档目标见 §2.2；
- 桌面与 Android APK 优先，Web 端暂缓。

### 2.2 延迟目标（v0.2 修订）

v0.1 的「端到端 60–80 ms」在 DFN3 档不可达。改为三档，每档都有明确适用条件与统计口径：

| 档位 | 条件 | 端到端嘴到耳 | 用途 |
|---|---|---|---|
| **L0 极限档** | 无降噪、5 ms 缓冲、同城 VPS、有线网 | p50 ≤ 45 ms（见附录 A 预算） | 只用于验证骨架与测量方法，不作为产品承诺 |
| **L1 低延迟档** | RNNoise 档、常规宽带 | **p50 ≤ 75 ms，p95 ≤ 100 ms** | 默认承诺档 |
| **L2 质量档** | DeepFilterNet3 档（含工作线程队列）、常规宽带 | **p50 ≤ 125 ms，p95 ≤ 150 ms** | 强降噪优先场景 |

口径定义：**嘴到耳 = 麦克风采集进 I/O 回调 → 对端播放回调送出**，含两端设备缓冲、编解码、网络单程、抖动缓冲；统计 p50/p95，不用均值；测量方法见 §11.5。

> 决策风险：L2 的额外延迟是否可被接受，必须在 M0 做 A/B 盲听验证（见 §10 M0-G3）。若不可接受，DFN3 降级为「安静环境可选档」，默认改为 RNNoise。
>
> **2026-11-17 修订（P3-7）**：DFN3 每帧约 185 次堆分配（C-20），不能进音频回调，实测改跑工作线程（C-25）。队列带来**常数 20 ms**额外延迟（C-26），所以 L2 的真实代价是 **30 + 20 = 50 ms**，比 L1 多约 50 ms，而不是原来记的 30 ms。验收线已按此上调 20 ms。队列深度可降到 1 帧（10 ms），届时验收线可再降 10 ms——这一步等 P2B 有真机再定，桌面端先用 2 帧换 OS 调度抖动余量。

> 口径拆分（**ADR-0010**）：本节 p50/p95 **只含软件预算**，即附录 A 第 2–10 行。设备段（第 1 行采集缓冲、第 11 行播放缓冲）按实测单列、不进承诺值——2026-11-17 在本机量到采集设备段 **139 ms**（USB 电容麦内部缓冲），远高于附录 A 原设的 5–10 ms 常数。客户端必须自带回环自检（数字回环 vs 声学回环，差值即设备段）并呈现本机实测值，不对外给单一端到端数字。

### 2.3 非目标

浏览器 Web 端；视频；直播/大型会议；完整 WebRTC 协商栈；MCU 服务端混音（v1）；P2P / NAT 打洞（v1）；SilentMic-RT；GPUI / 纯 Dioxus 主 UI；从零发明全新语音协议。

### 2.4 关键约束

- 延迟与降噪质量优先于开发速度；
- 桌面与 Android 共享尽可能多的 Rust 代码，平台差异收敛在 I/O 适配层；
- 传输层可控、可观测、可调优；音频前处理与传输层解耦，未来可平移到 LiveKit 或 QUIC；
- 所有强许可证依赖需显式评估。

## 4. 总体架构

### 4.1 分层图（v0.2：删去 P2P 与 OCB2）

```text
┌──────────────────────────────────────────────────────┐
│              UI 层：单个 Tauri 2 工程                  │
│   桌面 WebView  │  Android WebView （同一套前端代码）    │
│   通过 Tauri IPC 调用 Rust 命令 / 订阅事件             │
└───────────────────┬──────────────────────────────────┘
                    │ IPC（控制与状态，不传 PCM）
┌───────────────────▼──────────────────────────────────┐
│              客户端 Rust 核心（共享 crate）             │
│  ┌─────────────────┐   ┌───────────────────────────┐  │
│  │ audio-io 抽象    │   │ audio-core（实时线程）      │  │
│  │ 桌面+Android:cpal│   │ AEC? → DFN3/RNN → AGC2     │  │
│  │ （+平台 AEC 可选）│   │ → Opus 10ms → 冗余/FEC     │  │
│  │ rtrb 无锁缓冲    │   │ ← NetEQ ← 解码 ← 混音      │  │
│  └─────────────────┘   └───────────────────────────┘  │
│  ┌─────────────────┐   ┌───────────────────────────┐  │
│  │ client-core      │   │ transport                  │  │
│  │ 频道/用户/PTT/   │   │ UDP + ChaCha20-Poly1305    │  │
│  │ 选择性收听状态机  │   │ 会话重绑定/keepalive/限速  │  │
│  └─────────────────┘   └───────────────────────────┘  │
└───────────────────┬──────────────────────────────────┘
                    │ 加密 UDP（语音面）／TLS 1.3（控制面）
┌───────────────────▼──────────────────────────────────┐
│                 hushsquad-server（Rust）              │
│  控制面：频道树 / 用户 / ACL / 信令                    │
│  语音面：SFU 反射器（校验成员与频道 epoch 后 fan-out）  │
│  可选：MCU 混音（协议占位，v1 不实现）                  │
└──────────────────────────────────────────────────────┘
```

### 4.2 设计原则

1. UI 只做展示与输入；实时音频、编解码、网络全在 Rust 侧，前端不接触 PCM 与网络包。
2. 音频前处理与传输层解耦：`audio-core` 不依赖 `transport`，可平移。
3. 实时线程无锁、无分配、无阻塞：I/O 回调与处理链之间用 `rtrb` SPSC 环。
4. 桌面与 Android 共享核心 crate，平台差异只在 `audio-io` 与权限/后台服务适配层。
5. 传输做减法：服务器即中继，语音面只有一条加密 UDP 通道 + 一条控制通道。
6. 协议参考 Mumble 的**数据模型**，不复制其加密、不追求客户端互通（见 §13 Q8）。

## 5. 客户端设计

### 5.1 Tauri 2 工程形态

- **一个 Tauri 工程，两个构建目标**：`cargo tauri dev/build`（桌面）与 `cargo tauri android dev/build`（APK）。Android 目标由 `tauri android init` 生成 `gen/android`，不是独立的 app crate。
- 前端只做 UI 与状态渲染，通过 IPC 命令下发「加入频道 / PTT 按下 / 设某人音量」等意图；通过事件接收「成员列表变化 / 语音活动指示 / 网络统计」。
- 语音活动指示、延迟数字等高频 UI 数据**合并到 10–20 Hz 的一次事件**里推送，不要每帧一次 IPC。

### 5.2 平台音频 I/O

| 平台 | 采集 | 播放 | 说明 |
|---|---|---|---|
| 桌面 Win/macOS/Linux | `cpal` | `cpal` | 默认 WASAPI / CoreAudio / ALSA/PipeWire |
| Android | `cpal`（android 后端，jni + ndk） | `cpal` | 待 M0 实测是否走 AAudio 低延迟路径；若为 OpenSL ES 且延迟不达标，再评估 `oboe` 直连 |
| Android 专用能力 | 平台 AEC / NS 开关、音频路由（听筒/扬声器/蓝牙 SCO） | 同左 | 走 JNI 薄封装，不进入音频热路径 |

要点：

- 采集设备可能给 44.1 kHz，**不要假设 48 kHz 直通**，进链路前后各一次重采样（`rubato`），见 §6.6；
- cpal 回调内只做 `rtrb` 写入/读取，不做任何处理；
- Android 需要 `RECORD_AUDIO`、`MODIFY_AUDIO_SETTINGS`、`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MICROPHONE`，前台服务 `foregroundServiceType=microphone`；Android 14+ 的 while-in-use 限制必须实测；
- 蓝牙耳麦：A2DP 只能单向高质量，回传麦克风会切到 SCO/HFP，延迟与音质都劣化。**v1 明确：推荐有线/USB 耳机；蓝牙只保证可用不保证低延迟**，并在 UI 提示。

### 5.3 线程模型

```text
[采集回调线程 cpal] --f32 PCM--> [rtrb A] --> [音频线程：AEC?→NS→AGC→Opus]
                                                        |
                                              [rtrb B / 定长帧队列]
                                                        v
                                                  [网络线程：UDP 加密发送]

[网络线程：收包解密/校验] --> [每说话人 NetEQ 抖动缓冲]
        --> [混音/解码线程] --f32 混音--> [rtrb C] --> [播放回调线程 cpal]
```

要求：

- 采集/播放回调中禁止：加锁、分配、日志、`println!`、格式化字符串、`Vec::push` 扩容、阻塞 IO；
- 音频线程用 `audio_thread_priority` 提升（cpal 已有 `realtime` feature 可直接用）；
- 音频线程与网络线程之间只通过无锁 SPSC 或预分配定长队列通信，队列满/空必须有确定的降级策略（丢最旧 / 补静音），不能等待；
- Android JNI 引用只在初始化与设备切换时创建，热路径不经过 JNI；
- 时钟：统一用单调时钟（`Instant`），禁止用墙钟计算抖动与延迟。

### 5.4 客户端状态机（初稿）

```text
Disconnected → Authenticating（TLS 控制面） → Connected（有频道树）
Connected → Joining(channel_id) → InChannel
InChannel → Reconnecting（掉线，指数退避，保持 UI 状态）
任意态 → Error(reason)
```

语音面会话与频道状态分离：频道切换只改「服务器 fan-out 的目标集合」，不重建 UDP 会话与密钥。

## 6. 音频处理链路

### 6.1 统一音频参数

| 项 | 值 | 备注 |
|---|---|---|
| 采样率 | 48 kHz（内部统一） | 设备为 44.1 kHz 时由重采样器转换 |
| 声道 | 单声道 | 语音场景固定单声道 |
| 样本格式 | f32 | 输出到设备前如需 i16 再转换 |
| 处理帧长 | 10 ms（480 样本） | DFN3 的 hop 为 10 ms，链路粒度必须与之一致 |
| Opus 帧长 | **10 ms**（大房间可配 20 ms） | 见 §6.3，不用 2.5/5 ms |

### 6.2 发送链路（含 AEC 的现实定位）

```text
麦克风采集
  → [可选] 回声消除：Android 平台 AEC（VOICE_COMMUNICATION 音源）或桌面 webrtc-audio-processing
  → 高通（80 Hz，去隆隆声与桌面震动；**必须在 AGC2 之前**，否则低频能量会污染电平估计，
     让 AGC 低估语音、抬高增益）
  → 降噪：DeepFilterNet3（质量档，算法延迟 30 ms）/ RNNoise（低延迟档，约 10 ms）
  → AGC2（sonora-agc2：自适应数字增益 + 限幅；需与平台 AGC 二选一，避免双重处理）
  → 可选的轻度扩展器（静音时压底噪）
  → Opus 10 ms 编码（in-band FEC 开）
  → 冗余封装 + ChaCha20-Poly1305
  → UDP 发送
```

**AEC 决策（v0.2）**：v1 **不作为必经环节**。理由：目标用户绝大多数使用耳机；软件 AEC3 需要「对端混音后的播放信号」作为参考，且采集与播放两个时钟必须对齐，这是整个项目最难、最容易长期调不好的实时工程；TS3 至今没有 AEC 也不影响其定位。

- 第一阶段（M1）不接 AEC，链路上只留 `EchoStage` 接口与一个 `Passthrough` 实现；
- 若实测发现外放用户不可用，再按平台顺序接：Android 平台 AEC → 桌面 `webrtc-audio-processing`（tonarino 2.1.0，工程上最成熟）；
- 纯 Rust `sonora` 的 AEC3 作为备选，接入前需验证：双讲性能、非线性残留、收敛时间、ARM 上的 CPU。

### 6.3 Opus 参数（本版钉死）

| 参数 | 取值 | 理由 |
|---|---|---|
| application | `OPUS_APPLICATION_VOIP` | 语音优化；`RESTRICTED_LOWDELAY` 不减少 6.5 ms 前瞻，只为 2.5–10 ms 帧牺牲质量 |
| 帧长 | 10 ms（可选 20 ms） | 与 10 ms 处理链一致；20 ms 可把包率与头部开销减半 |
| 比特率 | 默认 32 kbps VBR；范围 24–40 kbps | 语音 + FEC 后的合理上限 |
| complexity | 10 | 桌面可 10，低端 Android 视实测降为 8 |
| 声道 | `OPUS_SET_FORCE_CHANNELS(1)` | 单声道 |
| in-band FEC | 开 | 抖动缓冲等不起重传，只能靠前向纠错 |
| DTX | 与 VAD 联动；PTT 模式下关 | PTT 场景静音期本就不发包，DTX 收益低且引入包率不规律 |
| `OPUS_SET_PACKET_LOSS_PERC` | 5–10 | 让编码器为 FEC 留出冗余 |
| lookahead | 固定 6.5 ms（48 kHz 下 312 样本） | 任何实现都要付，预算必须计入 |

绑定选型：默认 `opus`（libopus 安全绑定，BSD）——Android 交叉编译需 cmake，但可复现；`opus-pure`（纯 Rust，BSD-3，0.2.3）作为对照实验，需先验证其延迟模式与语音质量，通过前不做默认。

### 6.4 降噪选型

| 方案 | 算法延迟 | 效果 | 成熟度 | 结论 |
|---|---:|---|---|---|
| DeepFilterNet3（`deep-filter-rt` 0.2.0，MIT/Apache） | 30 ms | 非平稳噪声（键盘、风扇、椅擦、背景人声）强 | 上游推理部分可用，但 crate 年轻、下载量低、参考项目为 Linux 首发 0.1.0 | **质量档**，自带降级路径 |
| RNNoise（`nnnoiseless` 0.5.2，116 万下载，纯 Rust） | 约 10 ms | 稳态噪声好，非平稳一般 | 成熟 | **低延迟档 / 默认档** |
| SilentMic-RT | 声称 sub-3 ms | 未验证 | 仓库不可访问 | 不作为依赖 |
| dtln-rs | 需实测 | 一般 | crates.io 上不存在，仅 GitHub 参考 | 跟踪，不引入 |
| gtcrn（`svod` 纯 Rust 推理栈） | 需实测，超轻量 | 待测 | crates.io 上不存在对应包 | Android 能效备选，需重新寻找 |
| 商用 SDK（如 Krisp） | 约 20 ms | 商用级 | 商业授权 | 金钱换确定性备选 |

**切换策略**：自己定义 `trait DenoiseStage { fn process(&mut self, frame: &mut [f32; 480]) -> VADProb; }`，两个实现各自薄封装。**不要**把运行时切换押在某个第三方「统一 Stage」crate 上（v0.1 提到的 `sew-noise` 在 crates.io 上仅 12 次下载）。

自动档位（M3 再做）：以 CPU 帧耗时（p95 处理时长 / 10 ms）与丢包率为主输入，手动档位始终可覆盖。

### 6.5 接收链路 + 丢包与冗余（新增）

```text
UDP 收包 → 解密/校验 → 按 sender 分流
  → 每说话人一个 NetEQ 抖动缓冲（自适应，含时钟漂移补偿）
  → Opus 解码（丢包时按 seq 间隙声明丢包，走 in-band FEC / PLC）
  → 每人独立增益 / 静音 / 独听过滤（混音前）
  → 混音（含软限幅，防多人同时说话削波）
  → 播放
```

**丢包策略（v0.1 完全缺失，本版补齐）**：抖动缓冲仅 10–20 ms，**没有重传的时间窗**，所以只靠三件事：

1. **包级冗余**：每个语音包携带当前帧 + 上一帧的副本（头部带长度与 CRC）。多约 25–35% 带宽，**零额外延迟**，对 1–2 个连续丢包极其有效。默认开启，可在服务器/房间级别关闭；
2. **Opus in-band FEC**：编码器侧已开，解码器在检测到 seq 间隙时以 FEC 模式解码下一包；
3. **PLC + 静音填充**：连续丢包 ≥ 3 时由 PLC 渐隐到静音，避免机器人音与音量突跳。

**不做**：ARQ / NACK 重传（10–20 ms 缓冲下重传到达时已过播放时刻）；FEC 矩阵（Opus 帧短，包级冗余性价比更高）。

### 6.6 时钟漂移与重采样（新增）

三个不同时钟必须处理：本地采集时钟、网络参考时钟、本地播放时钟。

- 内部统一 48 kHz；设备非 48 kHz 时用 `rubato` 转换，转换器放在 I/O 边界而非处理链中段；
- 本地采集与播放速率差通常 10–100 ppm：5 分钟通话可积累数十毫秒，表现为「越说越不同步、缓冲慢慢涨/枯」。抖动缓冲必须做漂移补偿。
  **2026-11-17 已验证（P4-4，C-30/C-31）**：`neteq` 0.9.1 **确实实现了**漂移补偿（时间压缩/拉伸），
  但**工作点在我们的预算之外**——压缩阈值是 `max(target, low_limit + 20 ms)`，那个 +20 ms 是常数，
  20 ms 的 target 意味着它要等缓冲涨到 35 ms 才动手；而预拉伸额外要求「当前缓冲 ≥ 30 ms」，在 20 ms
  预算里永不成立。实测 +100 ppm 4 小时稳在 36.76 ms（33–44 ms 锯齿），−100 ppm 一次预拉伸都没有、
  靠 194 次 PLC 补了 1.44 s。**所以「抖动缓冲自带漂移补偿」不能当成设计前提**；
- 每说话人缓冲深度、欠载（underrun）与溢出次数必须作为指标暴露到 UI 的网络面板；
- 因此在 `neteq` 之上**必须**包一层「按缓冲深度微调」的补偿器（执行方案 P4-6 / 对策 D）：位置在网络线程、
  `pull()` 之后、写入 PCM 环之前；这是必须实现的，不是优化项。它的验收线就是重跑 P4-4 的四条判据。
  **2026-11-17 已实现并验收（P4-6，C-34/C-36）**：`audio-core::drift` 的 `DriftControl`——执行器只有
  「丢/补样本」与「拉包次数」两个，一个控制环（PCM 环水位）就够；±100 ppm 各 4 小时四条判据全绿
  （正向稳态 12.19 ms、反向 17.81 ms，两向 0 下溢 0 爆音），0 ppm 下几乎逐样本透明。**已默认开启**。
  已知局限（C-37）：传感器是「排队包数」，抖动与漂移分不开，弱网下会做约 26 倍的无效时间伸缩；
  正解是把传感器换成 `Δ序号 / Δtick − 1`（对抖动与丢包都免疫），需要网络层把序号喂进来，归 P5；

### 6.7 延迟预算（详见附录 A）

摘要（良好网络）：L1 低延迟档 p50 ≈ 75 ms，L2 质量档 p50 ≈ 105 ms。任何设计变更若增加 >2 ms 延迟，必须在附录 A 中记账。

## 7. 传输层设计

### 7.1 拓扑与原则（v0.2 修订）

- **v1 无 P2P、无打洞、无盲中继**：TS 式产品形态是「每社区一台公网服务器」，所有客户端出站连接，服务器天然是中继；打洞在这个拓扑下没有收益，却带来 NAT 类型分类、信令、失败回退三套工程量；
- 语音面：一条长寿命加密 UDP 通道，客户端→服务器→同频道其他成员；
- 控制面：TLS 1.3（或 QUIC）长连接，承载频道树、用户、ACL、信令；
- 服务器语音端点由控制面下发（地址 + 会话密钥材料），客户端不需要 STUN/TURN；
- 未来若要 1:1 直连或 LAN 模式，再引入打洞——接口上只需保证「语音对端地址」是一个可替换的量。

### 7.2 语音包格式（草案，二进制）

```text
struct VoicePacket {            // 头部固定 20 字节，全部大端
  magic: u8,            // 0x48，极早期丢弃垃圾包
  version: u8,          // 1
  flags: u8,            // bit0 有冗余, bit1 冗余为 PLC 占位, bit2 打点, bit3 绑定, bit4 静音帧
  red_len: u8,          // 冗余帧字节数，无则 0
  channel_epoch: u16,   // 频道成员快照，防跨频道/过期转发
  sender_id: u32,       // 服务器分配，会话内永不复用（参与 nonce 构造）
  seq: u32,             // 每 sender 每 key_epoch 单调递增
  timestamp: u32,       // 48 kHz 采样计数（按 2^32 回绕处理）
  opus_len: u16,        // 0 表示无音频（打点/绑定包）
  opus_data: [u8; opus_len],
  red_data: [u8; red_len],
  tag: [u8; 16],        // ChaCha20-Poly1305 标签；AAD = 前 20 字节头
}
```

定稿头部 **20 字节** + 16 字节标签，加 IP/UDP 28 字节 = **64 字节/包**（详见 `协议草案-v0.1.md` §4）。10 ms 帧时头部开销与 32 kbps 的有效载荷同级——**这是选 20 ms 帧能给大房间省一半开销的原因**（附录 B）。

### 7.3 加密与会话密钥（v0.2 修订）

| 项 | 决策 |
|---|---|
| 语音面 AEAD | **ChaCha20-Poly1305**（`chacha20poly1305` crate）；不实现 OCB2/AES-OCB |
| nonce 构造 | 12 B = `0u32 ‖ sender_id(u32, BE) ‖ seq(u32, BE)`；每个 sender_id 会话内永不复用，因此 (key, nonce) 不会重复。密钥轮换用新 key_epoch 派生新 key |
| 密钥来源 | 控制面 TLS 1.3 会话完成后，双方用 ECDH 临时密钥 + 服务器签名的握手导出 per-session 语音密钥；重连必须换密钥 |
| 服务器角色 | **per-hop AEAD**：服务器解密校验后再按目标加密下发。这样服务器可做成员校验、可观测、可将来加 MCU。群组密钥 E2EE（服务器转发密文）作为未来可选，v1 不做 |
| 重放防护 | 每 sender 维护滑动窗口（64 包），窗口外或重复 seq 直接丢弃；同时在窗口内去重以保证冗余帧不重复计费。**顺序必须是 AEAD → 窗口**：`seq` 在明文头里，先更新窗口等于给伪造源地址的人一个「推走窗口」的把手（协议草案 §12.3） |
| 反放大 | UDP 首包必须携带控制面下发的会话 token，服务器在认证前不发送任何数据 |
| 速率限制 | 每会话每秒语音包数上限（如 150 pps）与字节上限，超限丢弃并计数 |

> 说明：OCB2 在 2018 年被证明可选择性伪造，Mumble 使用它是历史遗留。我们只继承 Mumble 的**数据模型**（频道/用户/语音包语义），不继承其密码学。

### 7.4 会话、漫游与保活（新增）

- 会话以 **session_id** 索引，不以 UDP 五元组索引；手机 Wi-Fi ↔ 4G 切换时，同一 session_id 从新地址到达经 AEAD 验证通过即**原地重绑定**，不重认证、不重进频道（这是 Android 端的必须能力）；
- keepalive：空闲期每 10–15 s 一个探测包（flags.bit2），超时 3 个周期判离线；同时维持 NAT 映射；
- 路径 MTU：语音包小（< 200 B），不做 PMTU 发现，但发送侧限制单包 ≤ 1200 B；
- 拥塞/发送节奏：语音是低码率定速流，v1 只做**简单 pacing**（按 10 ms 节拍均匀发送，不突发）+ 丢包/延迟统计上报，不做完整 CC；若未来承载视频或屏幕共享再引入；
- 弱网观测：每 5 s 上报 RTT、丢包率、抖动、抖动缓冲深度、欠载次数，UI 可展示。

### 7.5 控制面协议来源

- 消息集合参考 `mumble-client-protocol`（0.1.0，仅作规范参考，不视为稳定黑盒）：频道树、用户状态、加入/离开、ACL、whisper/shout、频道监听；
- 我们自己定义 protobuf/JSON 消息（M2 先给带字段号的 .proto 草案），换取可演进的版本协商；
- `mumcord-codec` 已确认 AGPL-3.0-only：**不得链接**，只能阅读参考或经确认后使用。

### 7.6 与 LiveKit 的关系（结论不变）

| 维度 | LiveKit | 自建 UDP |
|---|---|---|
| 传输工程确定性 | 高，NAT/弱网/拥塞成熟 | 需自行填补（但我们的拓扑使然，规模有限） |
| 延迟可控性 | WebRTC 抖动缓冲与协商带来额外固定延迟 | 自控，可压到 10–20 ms |
| 降噪控制 | Rust SDK 不内置强降噪，需在其 Source 前处理 | 完全可控 |
| 运维负担 | Cloud 近零；自托管仍有部署/Redis/多节点 | 单二进制 + 证书即可，规模小 |
| 判断 | 快速原型 / 备选路径 | **默认** |

> 保留条件：`audio-core` 不得依赖 `transport` 的任何类型，以便整套前处理能平移到 LiveKit 或 QUIC。这是硬约束。

## 8. 服务器设计

### 8.1 语音面：只做 SFU（v0.2 修订）

v1 服务器在语音面只做四件事：

1. 校验发送者是否属于该频道/房间成员集合；
2. 校验 `channel_epoch` 与当前成员快照一致，防跨频道/跨房间转发与旧 epoch 注入；
3. 把 Opus 帧 fan-out 给同频道其他成员（各自加密）；
4. 计数与丢弃异常（超速、非成员、epoch 不符、解密失败）。

**MCU 混音移出 v1**：根本冲突是与「按人调音量 / 静音 / 单独收听」互斥——一旦服务器预混，客户端就拿不到可独立控制的分轨；若为每个听众单独混音，CPU 为 O(n²) 且额外增加服务端抖动缓冲 + 重编码 30–50 ms。协议里保留 `codec_mode` 字段占位，未来若做「大厅广播只读混音」再启用。

### 8.2 模块划分

```text
hushsquad-server
├── control-plane   # 频道树、用户、ACL、信令、认证
├── voice-plane     # SFU 反射器（校验 + fan-out），MCU 占位
├── session         # 会话表、密钥派生、重绑定、速率限制
├── transport       # UDP 收发、pacing、keepalive
└── observability   # 指标、日志、追踪
```

### 8.3 并发与实现约束

- 语音面用**一个专用线程 + 单 UDP socket**（`recvmmsg`/`sendmmsg` 或 tokio 的 `UdpSocket` 但绑定到独立 runtime），避免多线程争抢同一 socket；控制面用 tokio；
- 转发路径零拷贝/零分配：预分配 per-session 发送缓冲，fan-out 时只改目标地址与加密（或对同一密文复用）；
- 服务器指标（P2）：在线会话数、每会话 pps/bps、fan-out 次数、丢包与超速丢弃、RTT 分布。

其余 M0 内容：桌面 cpal 延迟基线、`webrtc-audio-processing` 与 `sonora` AEC3 对比（仅评估不集成）、`neteq` 源码审查（漂移补偿是否存在）、延迟测量工具落地（附录 D）。

### M1 单机音频链路（先做无降噪骨架）

1. **骨架基线**：采集 → Opus 编码 → 解码 → 播放本地环回，测 L0 延迟与 CPU（这是后续一切延迟比较的基准）；
2. 逐级插入：高通 → AGC2 → RNNoise → DFN3，每级单独记账延迟与 CPU；
3. **丢包与冗余**：RED + in-band FEC + PLC，配 `testkit` 模拟丢 1%/3%/5%；
4. 降噪档位运行时切换（含无爆音切换）；
5. 离线 WAV 回归：固定输入集出固定指标，防止后续改动悄悄劣化。

### M4 质量与运维

## 11. 验收标准（v0.2：可测量化）

### 11.1 延迟

- L1：p50 ≤ 75 ms、p95 ≤ 100 ms（常规宽带、跨城）；L2：p50 ≤ 105 ms、p95 ≤ 130 ms；
- 每环节延迟可分解，且能在 UI 网络面板看到：采集缓冲、前处理、编码、网络单程、抖动缓冲、播放缓冲；
- Android 允许更高，但必须记录并给出「差距来自哪一环」。

### 11.2 降噪

- 机械键盘、风扇、椅擦、背景人声有明显压制（给定测试音频集的主观 ABX + 客观分段 SNR/语音保真指标）；
- DFN3 档与 RNNoise 档可无爆音热切换；
- 不出现吞字、金属音、明显音乐噪声（降噪典型伪影）。

### 11.3 稳定性

- 音频热路径无锁、无分配、无阻塞（可用分配器计数与 `#[no_alloc]` 风格断言在测试中验证）；
- 连续 4 小时通话无累积漂移（缓冲深度不单调漂移）、无爆音；
- Android 后台录音 1 小时稳定，不被系统回收；
- 网络切换（Wi-Fi ↔ 4G）后 2 s 内恢复，不掉频道。

### 11.4 传输与安全

- 跨频道/旧 epoch 语音包 100% 被拒（有测试用例）；
- 重放包被滑动窗口拒绝；超速包被限速丢弃并有计数；
- 无人能凭裸 UDP 包获得服务器响应（反放大）；
- 丢包 3% 下可听质量主观不低于「偶有轻微断续」。

### 11.5 延迟测量方法学（新增，必须先落地）

统一口径，三种手段配合：

1. **服务器回环打点**：客户端发送带单调时间戳的探测包，服务器立即回送；测得 RTT 与单程估计，用于网络段预算。**注意**时钟域不同，只做差值不做绝对同步；
2. **进程内打点**：每个 stage 进出各记一次 `Instant`，环形缓冲保存 p50/p95（不在热路径格式化字符串）；
3. **物理环回**：外放一段已知的 chirp/脉冲序列，用另一台设备或同一设备的麦克风录回，测「嘴到耳」真值，用于校准前两项之和。

报告中必须写：网络条件、缓冲配置、档位、n 次、p50/p95/max。禁止只报均值。

v0.1 的表漏了 Opus 固定前瞻与两端设备缓冲，导致「DFN3 + 60–80 ms」不成立。下表逐项列全，单位 ms。

| # | 环节 | L0 无降噪 | L1 RNNoise | L2 DFN3 | 备注 |
|---:|---|---|---|---|---|
| 1 | 采集缓冲（设备/驱动） | 3–5 | 5–10 | 5–10 | Android 通常高于桌面 |
| 2 | 帧成组（10 ms 帧，取均值） | 0–5 | 0–10 | 0–10 | 与 DFN3 hop 绑定，不可去 |
| 3 | 降噪 | 0 | 10 | **30** | DFN3 的算法延迟，含自身 lookahead |
| 3b | 降噪工作线程队列 | 0 | 0 | **20** | 只有 DFN3 需要（每帧 185 次分配）；2 帧 = 20 ms，同时是线程容错时间（C-26） |

| 5 | Opus 编码前瞻 | 6.5 | 6.5 | 6.5 | 48 kHz 下 312 样本，固定 |
| 6 | 发送排队（pacing） | 0–1 | 0–2 | 0–2 | 按 10 ms 节拍均匀发，不突发 |
| 7 | 网络单程（客户端→服务器） | 3–8 | 8–20 | 8–20 | 同城/跨城差异大 |
| 8 | 服务器 fan-out | 0.5–1 | 0.5–2 | 0.5–2 | 纯转发，不解码 |
| 9 | 抖动缓冲（稳态） | 3–5 | 10–15 | 15–20 | 自适应；弱网会增长，由 UI 呈现。**注意**：这 15–20 ms 只有在我们自己的漂移补偿器（P4-6）把缓冲钉住时才成立——`neteq` 自带的补偿在 20 ms target 下的平衡点是 35–45 ms（C-30）。P4-6 实测：±100 ppm 下 12.19 / 17.81 ms，两向摆动 10 ms（= 一个包，物理下限），0 下溢（C-34/C-36） |
| 10 | 解码 + 混音 | 0.3 | 0.3 | 0.3 | CPU 开销，几乎无附加延迟 |
| 11 | 播放缓冲（设备/驱动） | 3–5 | 5–10 | 5–10 | — |
| | **合计区间** | **16–32** | **46–83** | **97–127** | 理论下界 |
| | **实测预期 p50 / p95** | 30 / 40 | 65 / 85 | **110 / 130** | 区间取中值 + 抖动 |
| | **验收线（§2.2）** | p50 ≤ 45 | p50 ≤ 75、p95 ≤ 100 | p50 ≤ 125、p95 ≤ 150 | 留出机型/网络余量 |

- 「帧成组」在 I/O 以 480 样本块投递时与采集缓冲部分重叠，实现上不要重复相加，测量时以物理环回为准；
- **禁止**为省 7.5 ms 改用 2.5 ms Opus 帧：链路是 10 ms 粒度，省不到，且质量与包率双输；
- 第 1 行（采集缓冲）与第 11 行（播放缓冲）是**设备段**：实测填入，不预设常数。2026-11-17 实测采集设备段 **139 ms**（见 ADR-0010），因此本表的合计区间只是**软件部分**下界，不是端到端预期；
- 任何新增环节必须在本表占一行，并标明属于发送侧或接收侧。

## 附录 B：带宽与包率（决定帧长选择）

单个语音流的线上码率（自有头 20 B + AEAD 标签 16 B + IP/UDP 28 B = 64 B/包）：

| 20 ms 帧 / 32 kbps | 80 B | 50 pps | ≈ 58 kbps | ≈ 90 kbps |
| 10 ms 帧 / 24 kbps | 30 B | 100 pps | ≈ 75 kbps | ≈ 99 kbps |
| 20 ms 帧 / 24 kbps | 60 B | 50 pps | ≈ 50 kbps | ≈ 74 kbps |

25 人房间（每人收 24 路）下行与服务器出口：

| 配置 | 单客户端下行 | 服务器出口 | 服务器包率（出） |
|---|---:|---:|---:|
| 10 ms + 冗余 | ≈ 2.8 Mbps | ≈ 69 Mbps | 60 000 pps |

## 附录 E：术语与口径

| 术语 | 口径 |
|---|---|
| 嘴到耳 | 麦克风 I/O 回调入口 → 对端播放回调出口，含两端设备缓冲 |
| 算法延迟 | 某 DSP 阶段固有的前瞻/成组延迟，与 CPU 耗时无关 |
| 处理延迟 | 该阶段 CPU 耗时，必须远小于帧长（10 ms 帧下建议 < 30%） |
| SFU | 服务器只转发不混音；本项目的唯一语音面形态（v1） |
| 冗余（RED） | 每包携带上一帧副本，用带宽换丢包鲁棒性，零额外延迟 |
| epoch | 频道/房间成员快照编号，用于拒绝跨房间或过期语音包 |
| 重绑定 | 同 session_id 从新源地址到达并通过 AEAD 后更新地址，不重认证 |
