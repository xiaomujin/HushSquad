# 权限与频道管理设计 v0.1（评审稿）

> 一句话：**频道树由管理员在客户端里右键维护；权限是服务器级的 4 个角色，展开成位图存库；
> 服务器的校验是事实，界面的裁剪只是可发现性。**
>
> 这份文档只定方案，不写代码。第 10 节有 6 个待拍板的点。

## 0. 现状：地基比想象的多，缺的是「谁能改」

先把已有的东西摆清楚，免得重复造：

| 已经有了 | 在哪 |
|---|---|
| 权限位图 `perms: u64` 随账号存库（`users.perms`，默认 1 = 可进频道） | `crates/store/src/users.rs` |
| 认证成功后 `perms` 写进 `Session`，并经 `AuthResult.perms` 下发给客户端 | `server-core` / `control.rs` |
| `Perm` 位定义（JOIN / MOVE_ANYONE / KICK / BAN / CREATE_CHANNEL / MANAGE_CHANNEL / ADMIN） | `docs/proto/hushsquad-control-v1.proto` |
| `ChannelState` 带 `parent_id` / `position` / `max_users` / `flags`（bit3 = 分组容器） | 同上 |
| 客户端 `Roster` **已经能处理** `ChannelAdded` / `ChannelUpdated` / `ChannelRemoved` / `UserUpdated` | `client-core/src/roster.rs` |
| 服务器**已经在发** `ChannelUpdated`（进频道后人数变化）与 `UserUpdated` | `server-core/src/control.rs` |
| 服务器静音的**执行路径**（丢包 + `server_muted` 计数） | `server-core/src/voice.rs` |
| 分组容器不可加入的校验 | `server-core/src/control.rs` |

| 还没有 | 后果 |
|---|---|
| **没有任何一处校验 `perms`** | 权限位是装饰：任何客户端都能踢人（等做完才知道） |
| 频道树**不落盘**，只在启动时按 `--channel` 建 | 重启就回到一个「大厅」，管理员改的结构全丢 |
| 没有频道 CRUD 的**请求**消息（只有广播） | 客户端没法建/改名/删 |
| 没有「设置别人状态」的消息 | 服务器静音执行路径在，但没人能按下它 |
| 没有「踢人」 | 断别人的会话只能靠重启服务器 |
| 没有「谁是管理员」这个概念 | 所有人权限都是 1 |

结论：**协议和客户端镜像早就按「可编辑的频道树」设计好了，缺的是服务器侧的写入口和 UI。**

## 1. 要解决的三件事

1. **频道树可编辑**：管理员在客户端里新建 / 改名 / 排序 / 删除 / 设为分组，且重启不丢。
2. **权限可分配**：管理员能给别人分配角色，分配立刻生效。
3. **越权不可能**：客户端裁剪菜单只是体验；服务器对每个操作重新校验，越权一律 `PERMISSION_DENIED`。

第 3 条是硬约束，写在这里是因为它决定了实现顺序：**权限必须比频道编辑先落地**，
否则「右键删除频道」这个按钮在协议上就等于「任何人删任何频道」。

## 2. 权限模型（决策 A）

### 2.1 三个候选

| 方案 | 表达力 | 代价 | 现实中的例子 |
|---|---|---|---|
| **A. 全局位图 / 角色** | 能表达「他是管理员」，不能表达「他只是这个频道的管理员」 | 最小：协议、存储、UI 都不用新增结构 | 现成的 `Perm` 枚举就是照这个画的 |
| **B. 按频道 ACL（沿树继承）** | 最完整 | 每个频道一份 ACL，要同步给客户端、要做 ACL 编辑器、要定义继承与覆盖语义 | Mumble |
| **C. 服务器组 + 频道组**（两套） | 表达力接近 B，心智模型更清楚 | 两套角色、两套 UI，仍然要同步频道组 | TeamSpeak |

### 2.2 推荐：A —— 服务器级 4 个角色，展开成位图

**为什么不是 B**：Mumble 的 ACL 是「功能齐全但没人用」的典型。它的继承 + 显式覆盖 + 组嵌套
让「谁能进这个频道」这个问题需要打开三层对话框才能回答。我们的场景是**一个小队 5–20 人、
频道 5–10 个、管理员 1–2 个**，这个规模下 B 的表达力换来的全是维护成本。

**为什么不是 C**：两套角色会让「给他权限」变成一道选择题，而答案取决于用户能不能分清
「服务器角色」和「频道角色」——他们分不清。

**关键收益**：权限是**全局**的，所以客户端拿到自己的 `perms` 之后就能在本地决定所有 UI
（要不要显示右键菜单、哪些项灰掉），不需要为每个频道向服务器问「我能在这个频道做什么」。
这条直接决定了客户端的复杂度。

### 2.3 将来要做 B 时，接口怎么留

不改协议就能扩：`perms` 是 `u64`，只用了低 9 位；将来加「频道级覆盖」时，新增一张
`channel_acl(channel_id, user_id, perms)` 表和一个 `ChannelAcl` 消息，生效规则是
「频道 ACL ∪ 沿树继承 ∪ 全局 perms」。**触发条件**：出现「一个频道只让某几个人进」的真实需求，
或者管理员数超过 3 个且开始互相干扰。在那之前不做。

### 2.4 角色 × 权限位

| 位 | 名字 | 含义 | 服主 | 管理员 | 协管 | 成员 |
|---:|---|---|:-:|:-:|:-:|:-:|
| 1 | `JOIN_CHANNEL` | 进频道 | ✓ | ✓ | ✓ | ✓ |
| 2 | `MOVE_ANYONE` | 把**别人**移到别的频道 | ✓ | ✓ | ✓ | |
| 4 | `KICK` | 踢出服务器（断开会话） | ✓ | ✓ | ✓ | |
| 8 | `BAN` | 封禁（**v1 不做**，位保留） | ✓ | ✓ | | |
| 16 | `CREATE_CHANNEL` | 新建频道 | ✓ | ✓ | | |
| 32 | `MANAGE_CHANNEL` | 改名 / 删除 / 排序 / 人数上限 / 设为分组 | ✓ | ✓ | | |
| 64 | `ADMIN` | 分配角色、查看账号列表 | ✓ | ✓ | | |
| 128 | `MUTE_OTHERS` | 服务器静音别人（新增位） | ✓ | ✓ | ✓ | |
| 256 | `OWNER` | 服主：唯一、可转移（新增位） | ✓ | | | |

- **协管**（moderator）是「能管人、不能动结构」：踢人、服务器静音、移动别人。
  一个团长不该有删除频道的权力。
- **`MUTE_OTHERS`** 是新增位。现有 `Perm` 里没有它，但服务器静音的执行路径已经在了。
- **`OWNER`** 是新增位而不是单独的列：这样「转移服主」就是一次位操作，不用改表结构。

## 3. 存储

### 3.1 账号与权限（已有列，不迁移）

`users.perms INTEGER NOT NULL DEFAULT 1` 已经存在。**存位图，不存角色名**：

- 角色只是位图的**命名组合**，界面上按位图反查角色名；
- 位图组合不匹配任何内置角色时，界面显示「自定义」（将来加位或手改库都自然兼容）；
- 不需要为了加一个角色做数据迁移。

### 3.2 频道树（新表，schema v1 → v2）

```sql
CREATE TABLE IF NOT EXISTS channels (
    channel_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    parent_id   INTEGER NOT NULL DEFAULT 0,   -- 0 = 根
    name        TEXT    NOT NULL,
    position    INTEGER NOT NULL DEFAULT 0,   -- 同级排序
    max_users   INTEGER NOT NULL DEFAULT 0,   -- 0 = 用服务器默认（32）
    flags       INTEGER NOT NULL DEFAULT 0,   -- bit3 = 分组容器
    created_at  INTEGER NOT NULL DEFAULT (unixepoch())
);
```

- **迁移**：`VERSION` 1 → 2；表为空时插入「大厅」（与现在的默认行为一致）。
- **id 稳定性**：`AUTOINCREMENT` 保证删除后不复用 id —— 迟到的客户端引用旧 id 只会得到
  `CHANNEL_NOT_FOUND`，不会误操作到新频道。
- **不存的东西**：成员（在内存里）、`channel_epoch`（每次成员变化重新发号）。
- **`--channel` 参数**：保留，但语义改成「首次建库时的初始频道」，库非空时忽略并打印一行说明。

### 3.3 并发写

服务器是**单线程状态机**（`Server::handle_*` 拿 `&mut self`），所以「两个管理员同时改」在
服务器侧天然串行。客户端侧不做乐观更新（见 6.5）。

## 4. 协议改动

### 4.1 新消息（都带 `request_id`）

```text
// 频道结构：需要 CREATE_CHANNEL / MANAGE_CHANNEL
CreateChannel   { uint32 parent_id, string name, uint64 flags }
                → 广播 ChannelAdded（含 origin_request_id，见 4.2）
UpdateChannel   { uint32 channel_id, optional name, optional max_users, optional flags }
                → 广播 ChannelUpdated
MoveChannel     { uint32 channel_id, uint32 parent_id, uint32 position }
                → 广播 ChannelUpdated（受影响的每个兄弟各一条；子树跟着走，成员不变，不 bump epoch）
DeleteChannel   { uint32 channel_id }
                → 广播 ChannelRemoved（+ 必要时 UserUpdated）

// 成员管理：需要 MOVE_ANYONE / MUTE_OTHERS / KICK
MoveUser        { uint32 user_id, uint32 channel_id }
                → 广播 UserUpdated
SetUserState    { uint32 user_id, optional bool server_mute, optional bool server_deaf }
                → 广播 UserUpdated
KickUser        { uint32 user_id, string reason }
                → 目标收到 Error{ code = KICKED, fatal = true }，随后断连

// 权限：需要 ADMIN
ListUsers       { }
                → 定向 UserList { repeated UserEntry { user_id, username, perms, anonymous, online } }
SetUserPerms    { uint32 user_id, uint64 perms }
                → 定向 PermsChanged { user_id, perms }（发给本人 + 所有带 ADMIN 的会话）
```

**为什么没有 `ReorderChannels`**：拖拽一次落点就是「移到父级 P 的第 i 位」，`MoveChannel` 已经
能表达。原来的「整表重排」方案是为了防并发丢频道，但拖拽语义下并发只会让 `position` 的含义
稍微偏移，服务器夹到合法范围即可，**不会丢任何频道**。少一条消息就少一套校验。

新增错误码：`INVALID_ARGUMENT = 10`（名字非法、层级超限、参数越界）、
`CONFLICT = 11`（同级重名、频道非空、最后一个管理员）、`KICKED = 12`。
具体原因放 `Error.message`，客户端原样显示——错误码只用于客户端要分支的场合。

### 4.2 `ChannelAdded` 加一个字段

```text
message ChannelAdded {
  ChannelState channel = 1;
  uint64 origin_request_id = 2;   // 0 = 别人发起的；非 0 = 你的请求，用来关对话框并选中新节点
}
```

广播是给所有人的，只有发起者需要知道「这是我刚建的那个」。加一个字段比加一条 ack 消息省事，
且旧客户端会忽略它（proto3 未知字段规则）。

### 4.3 谁看得见别人的权限

**v1 不广播别人的权限**。`UserState` 不加 `perms` 字段，`PermsChanged` 只发给本人和 admin。
理由：这是最小暴露面，而且 v1 的界面也不需要「成员列表显示皇冠」。

需要看到别人角色的唯一地方是**权限面板**，它走 `ListUsers`（仅 admin）。代价是面板的数据
要单独刷新（`PermsChanged` 会让它保持最新）。

### 4.4 兼容性

- 全部是**新增消息**，不动现有字段 → 协议主版本不变（v1）。
- 旧服务器收到未知 oneof 分支：按协议规则「忽略并记日志」，客户端会表现为「请求没有反应」，
  所以客户端的管理请求要带 3 s 超时（见 6.5）。

## 5. 服务器校验点

每个写操作三件事，顺序不能变：

1. **鉴权**：`perms & 需要的位 != 0`，否则 `PERMISSION_DENIED`；
2. **不能操作比自己权限高的人**：破坏性操作（踢 / 服务器静音 / 降权）要求
   `actor_perms ⊇ target_perms`。这一条挡住了「管理员踢服主」「管理员给同僚降级」；
3. **业务校验**（见下表），失败返回 `INVALID_ARGUMENT` / `CONFLICT`。

| 操作 | 需要的位 | 业务校验 |
|---|---|---|
| `CreateChannel` | `CREATE_CHANNEL` | 名字 1–32 字符、去首尾空白、禁 `/` 与控制字符；同级不重名；父级存在且深度 ≤ 3 |
| `UpdateChannel` | `MANAGE_CHANNEL` | 改名同上；`max_users` ∈ 0..=1024；设为分组前**必须没人**；取消分组总是允许 |
| `MoveChannel` | `MANAGE_CHANNEL` | 目标不是自己或自己的子孙（防成环）；移动后子树深度 ≤ 3；`position` 超出范围就夹到末尾；移完把新旧两个父级的 `position` 重排成 0..n-1（**同一个事务里**） |
| `DeleteChannel` | `MANAGE_CHANNEL` | 频道里有人 → 拒绝（提示「先把 N 个人移走」）；子树会连带删除，确认框里列出数量；不能删掉最后一个可加入的频道 |
| `MoveUser` | `MOVE_ANYONE` | 目标频道可加入、未满员；被移动的人在线 |
| `SetUserState` | `MUTE_OTHERS` | 只能改 `server_mute` / `server_deaf`；`actor ⊇ target` |
| `KickUser` | `KICK` | `actor ⊇ target`；不能踢自己（要退就断开） |
| `SetUserPerms` | `ADMIN` | 授予的位必须是自己的**子集**（防提权）；带 `OWNER` 时做**原子转移**（清旧 owner + 设新 owner）；不能撤掉最后一个 `ADMIN`/`OWNER` |

「管理员能给自己加权限吗」——不能，因为 `授予 ⊆ 自己` 这条规则里，给自己加位就是违反它。

## 6. 客户端 UI

### 6.1 频道右键菜单（左栏树节点）

```text
加入频道                 可加入、未满员、不是分组
──────────────────────
新建子频道…              CREATE_CHANNEL
重命名…                  MANAGE_CHANNEL
设为分组 / 取消分组        MANAGE_CHANNEL
人数上限…                MANAGE_CHANNEL
上移 / 下移              MANAGE_CHANNEL
──────────────────────
删除频道…                MANAGE_CHANNEL（二次确认，写明会连带删几个子频道）
```

「新建频道」（根级）放在「频道」区头的 `+` 按钮上，同时也在区头右键菜单里。

**排序用拖拽**（2026-11-19 决定，改掉原来的「上移 / 下移」）：

| 拖到哪 | 结果 |
|---|---|
| 分组 / 频道的**主体** | 成为它的子节点，追加到末尾 |
| 节点之间的**间隙**（显示一条横线） | 成为它的兄弟，插在那条线处 |
| 空白区 / 区头 | 成为根级，追加到末尾 |

拖拽必须显式拒绝并给出视觉反馈（光标变禁止、落点不高亮）的三种情况：

1. 拖到自己身上；
2. 拖到自己的**子孙**上（成环）；
3. 拖到深度不够的位置（目标深度 + 被拖子树的深度 > 3）。

落点判定在 UI 里算，最后只发一条 `MoveChannel { channel_id, parent_id, position }` ——
**「插在第几位」由前端算成整数下标**，服务器不需要理解鼠标。

键盘可达性：拖拽为主，`Alt+↑ / ↓` 作为 P7-3 的补充（同一父级内移动一位），走同一条消息。

### 6.2 成员右键菜单

```text
本机音量 ▸ 0–200          总是（只影响自己听）
静音他 / 取消静音           总是（本机）
独听他 / 取消独听           总是（本机）
──────────────────────
移到频道 ▸               MOVE_ANYONE
服务器静音 / 解除          MUTE_OTHERS
──────────────────────
踢出服务器…               KICK（二次确认，可填原因）
权限…                    ADMIN（打开权限面板并定位到这个人）
```

### 6.3 权限面板

设置页新增一页「服务器」（只有带 `ADMIN` 的人看得见入口）：

```text
用户名        在线   角色      操作
小木           ●     服主      （只读，右侧「转移服主…」）
老K            ●     管理员    [角色 ▾]
阿岚           ○     成员      [角色 ▾]
游客-3F2A      ●     成员      [角色 ▾]   匿名
```

- 角色下拉：服主 / 管理员 / 协管 / 成员 / 自定义（只读项）。
- 离线账号也在列表里——权限是账号级的，不需要在线才能改。
- 底部一行说明：「角色只决定能做什么。服务器对每次操作都会重新校验，改权限不需要重启。」

### 6.4 无权限的菜单项：灰掉 + 说明，不隐藏

隐藏会让用户既不知道有这个功能，也不知道该找谁开权限。所以：**项在，灰的，`title` 写
「需要管理员权限」**。代价是菜单更长——对一个 5 项的菜单可以接受。

### 6.5 拖拽要乐观，其余等广播

本机设置（音量 / 静音 / 独听）照旧**乐观更新**——那是本地状态。

频道结构分两种：

- **拖拽排序：必须乐观**。拖完等 3 秒才动会让人以为没拖上。做法是**覆盖层**：拖拽后 UI 先按
  新结构渲染一份 `pendingTree`，收到服务器的广播就丢掉覆盖层、以服务器为准。
  失败（`Error` 带回同一个 `request_id`）就**直接丢掉覆盖层**——不需要写回滚逻辑，
  因为镜像（`Roster`）从头到尾只被服务器消息改过，丢掉覆盖层就自动回到服务器的状态。
- **新建 / 改名 / 删除 / 人数上限：等广播**。这些是模态操作，用户在对话框里等一会儿是正常的，
  而且等广播能立刻暴露「名字重复」这类冲突。发出后按钮置 pending，3 s 超时报「服务器没有响应」。

代价说清楚：乐观更新意味着**服务器拒绝时用户会看到树弹回去**。这是拖拽的固有代价，
用「失败时给一条明确的提示」来补偿，而不是假装不会发生。

## 7. 引导与防呆

### 7.1 第一个服主从哪来

**第一个通过 `hushsquad-server adduser` 建的账号自动成为服主**，控制台打印一行：
`alice 是这个服务器的服主（可以给其他人分配权限）`。

理由：现在的部署流程第一步本来就是 `adduser`，不需要引入新概念（口令、配置文件、网页向导）。
后路：`hushsquad-server promote <用户名>` 手动设服主，用于「服主账号丢了重建」这种灾难恢复。

### 7.2 老库升级

启动时检测：**有账号但没有 `OWNER`** → 把 `user_id` 最小的非匿名账号提为服主，打印警告
（说明这是自动决定，可以用 `promote` 改）。

### 7.3 几条硬规则

| 规则 | 为什么 |
|---|---|
| 服主唯一，只能转移不能并存 | 否则「谁说了算」没有答案 |
| 不能撤掉最后一个 `ADMIN`/`OWNER` | 否则服务器变成没人能管的状态，只能改库 |
| 删除服主账号 → 拒绝（先转移） | 同上 |
| 授予的位必须是自己的子集 | 挡住提权：管理员造不出服主 |
| 不能对权限比自己高的人做破坏性操作 | 挡住「管理员踢服主」 |

### 7.4 删频道时里面的人怎么办

**拒绝，并提示「先把这 N 个人移到别的频道」**，而不是静默把人挪走。静默移动用户是权限系统里
最容易挨骂的行为（「我的房间怎么把我踢出来了」）。管理员有 `MOVE_ANYONE`，一个人右键一次就能挪完。

## 8. 分阶段

| 阶段 | 内容 | 为什么在这个顺序 |
|---|---|---|
| **P7-1 权限地基** | 新增 3 条权限消息 + 校验点 + 引导服主 + 权限面板 + 成员右键（踢 / 服务器静音 / 移动） | 它是频道 CRUD 的校验前提；而且做完立刻有用（能管人了） |
| **P7-2 频道树** | 频道表 + 迁移 + 5 条结构消息 + 服务器校验 + 频道右键菜单 + 新建/改名/删除对话框 | 工作量的大头，但地基已经在 P7-1 铺好 |
| **P7-3 打磨** | 上移下移的键盘可达、空状态、错误文案、`--channel` 的兼容说明 | — |

P7-1 不碰数据库迁移，所以可以独立上线、独立验证。

## 9. 不做什么（v1 边界）

| 不做 | 理由 / 后路 |
|---|---|
| 按频道 ACL | 见 2.3，留了 `u64` 高位和「并集」规则 |
| 自定义角色 | 4 个内置够用；位图已经存了，将来加角色只改映射 |
| 封禁（BAN） | 需要 IP / 账号黑名单 + 解封入口，是独立一件事；位保留 |
| 频道密码的 UI | 协议位已在（`flags` bit2、`JoinChannel.password`），v1 不做编辑界面 |
| 临时频道（`flags` bit1） | 需要「最后一个人离开后自动回收」，与频道树持久化相互影响 |
| 键盘移动频道（`Alt+↑/↓`） | P7-3 补；拖拽已覆盖功能，键盘只影响可达性 |
| 审计日志（谁踢了谁） | v1 只写服务器 stdout；要可查询得先有日志表 |
| 权限的实时撤销（改权限后把人踢出当前频道） | 改权限后**下一次操作**才生效；已在频道里的人不被动 |

## 10. 已拍板（2026-11-19）

| # | 问题 | 结论 |
|---:|---|---|
| 1 | 权限粒度 | **服务器级 4 角色**，不做按频道 ACL（留 `u64` 高位与「并集」规则作后路） |
| 2 | 角色切分 | **服主 / 管理员 / 协管 / 成员**；协管能踢人、服务器静音、移动别人，不能改频道结构 |
| 3 | 第一个服主 | 第一个 `adduser` 的账号自动成为服主；`promote` 作灾难恢复 |
| 4 | 删频道 | 有人就拒绝（先移人）；有子频道连带删，确认框写明数量 |
| 5 | 无权限的菜单项 | **灰掉 + 说明**，不隐藏 |
| 6 | 排序 | **拖拽**（不是上移 / 下移）；`position` 存进 SQLite，服务器在一个事务里重排 |

两条附带结论：

- **`ReorderChannels` 不再需要**：拖拽的落点就是 `MoveChannel{parent, position}`（见 §4.1）。
- **拖拽必须乐观更新**：用覆盖层 + 失败即丢弃（见 §6.5），其余结构操作仍等广播。

### 踩到的坑（值得记住）

**`#[serde(tag = "kind")]` 的内部标记无法序列化「新类型变体里装一个序列」。**
`Event::Accounts(Vec<AccountView>)` 在 `channel.send()` 时返回 `Err`，而调用方写的是
`let _ = channel.send(..)` —— 于是消息**静默消失**，界面上表现为「面板永远是空的」，
服务器日志里没有任何异常（请求确实到了、也确实处理了）。改成结构体变体
`Accounts { accounts: Vec<..> }` 就好了。教训：内部标记枚举的变体只能是结构体或单元，
带「裸序列/裸标量」的新类型变体在**发送时**才失败，编译器不管。

**另一个小坑**：右键菜单的遮罩用了 `<button>`（为了键盘可达），但没清浏览器默认样式，
于是它带着白色底色盖住了整个窗口——截图里只剩菜单，界面全白。CSS 里补
`background: transparent; border: 0; padding: 0` 才对。
