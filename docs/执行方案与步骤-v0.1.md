# HushSquad 执行方案与执行步骤

> 版本 v0.1.1（前置条件确认后修订）　日期 2026-11-16
> 上游依据：`HushSquad-技术设计-v0.2.md`（架构与验收）、`crates-选型验证报告-v0.1.md`（依赖事实）、`协议草案-v0.1.md`（线格式）。
> 本文档回答一个问题：**从空仓库到「能出声、延迟可测」的最小闭环，具体按什么顺序做、每步留什么产出、什么数字算通过。**
>
> **v0.1.1 修订依据**：2026-11-16 确认的 6 项前置条件（见 §12）。据此调整了：工具链锁定 1.100.0、测试素材改为「合成优先」、P2 收缩为纯桌面、Android 拆为独立分支 §15、许可证状态改为「待定」。

## 0. 执行原则（先读这 6 条，它决定了下面所有步骤为什么这么排）

1. **垂直切片，不做横向铺开**：先打通「采集→编码→解码→播放」这一条最细的线，再加降噪、再加网络、最后才做 UI。任何时刻仓库里都必须有一个**能跑出数字**的可执行程序。
2. **先测量，后优化**：每个阶段结束时必须新增或更新 `docs/measurements.md` 里的数字。没有数字的「做完了」不算完成。
3. **音频核心永不依赖 I/O 与网络**：`audio-core` 只吃 `[f32; 480]`，吐 `[f32; 480]`，可以在 CI 里离线跑。这是能持续做回归的唯一前提。
4. **降噪按档位插入，每档单独记账**：加一级就记一次延迟与 CPU，超出附录 A 预算的行必须当场决策，不允许「先加上后面再优化」。
5. **网络与协议放在音频之后**：音频链没达到 L0/L1 之前不碰 UDP，否则会同时调试两个不可见系统。
6. **服务器最后做，但协议先定**：协议文档已在仓库里，服务器实现只是为了验证协议，不是产品起点。

## 1. 阶段总览

## 3. P1 骨架 L0（3 人日）—— 第一个能出数字的东西

这一阶段完全不碰实时 I/O，也不碰网络，只做「离线把音频跑过链并报告每级耗时」。做完之后，后面所有优化都有比较基准。

### P1-1 定义核心接缝（先定接口，再写实现）

`crates/audio-core/src/lib.rs` 的**唯一公开契约**（草案，允许在 P1 内调整一次）：

```rust
pub const SAMPLE_RATE: u32 = 48_000;
pub const FRAME_SAMPLES: usize = 480;      // 10 ms
pub type Frame = [f32; FRAME_SAMPLES];

/// 所有音频阶段的统一接口。实时线程里调用 process()。
pub trait Stage {
    fn name(&self) -> &str;
    /// 该阶段引入的算法延迟（样本数）。这是预算表的唯一事实来源。
    fn latency_samples(&self) -> usize;
    /// 原地处理一帧，返回 VAD 概率（0.0–1.0，未知则 1.0）。
    fn process(&mut self, frame: &mut Frame) -> f32;
}
```

三条纪律（写进 `audio-core/CONTRIBUTING` 或文档注释）：

- `process()` 内**禁止**任何堆分配、锁、日志格式化、`Vec` 扩容；
- 所有可变缓冲在 `new()` 里预分配；
- 新增阶段必须同时更新 `latency_samples()`，否则预算表失真。

### P1-2 直通链 + 链路描述器

- `Chain`：`Vec<Box<dyn Stage>>` 仅在构造期使用，`process` 里遍历（v1 允许，先测出来再谈去虚化）；
- `ChainDesc`：可以序列化成 JSON 的链路描述（`[None]`、`[Rnn]`、`[Rnn, Agc2]`、`[Dfn3, Agc2]`…），保证「同一个实验可复现」；
- `total_latency_ms()` = 各 stage `latency_samples` 之和 / 48。

**验收**：`cargo test -p audio-core` 里断言 `ChainDesc::parse("none").total_latency_ms() == 0.0`、`parse("rnn").total_latency_ms() == 10.0`。

### P1-3 Opus 封装（先把编解码做成可替换的接缝）

```rust
pub trait AudioCodec {
    fn encode(&mut self, frame: &Frame, out: &mut [u8]) -> usize;
    /// lost = true 表示上一包丢失，解码器应走 PLC/FEC 路径
    fn decode(&mut self, payload: &[u8], lost: bool, out: &mut Frame) -> bool;
    fn lookahead_samples(&self) -> usize;   // 48 kHz 下应为 312
}
```

实现要点（来自报告 §2.5）：`Application::Voip`、10 ms 帧、`set_inband_fec(true)`、`set_packet_loss_perc(5..10)`、`set_complexity(10)`、`set_bitrate(32_000)`、单声道。**不要**用 `Application::LowDelay`。

**验收**：单元测试断言 `lookahead_samples() == 312`；编码 480 样本再解码，输出长度 480，SNR > 20 dB。

### P1-4 `testkit` 离线回放（本阶段最重要的产出）

CLI 设计（先定死用法，后面一直用）：

```bash
cargo run -p testkit -- \
  --in  testdata/clean_48k_mono.wav \
  --out out/proc.wav \
  --chain rnn,agc2 \
  --codec opus:10ms:32k \
  --report out/report.json
```

报告 JSON 字段（固定 schema，`docs/measurements.md` 直接粘）：

```json
{
  "chain": ["rnn", "agc2"],
  "codec": "opus:10ms:32k",
  "latency": { "algorithm_ms": 16.5, "per_stage_ms": { "rnn": 10.0, "agc2": 0.0, "opus": 6.5 } },
  "cpu_ms_per_frame": { "rnn": { "p50": 0.31, "p95": 0.55 }, "opus_enc": { "p50": 0.12, "p95": 0.2 } },
  "vad_mean": 0.42,
  "allocations_in_hot_path": 0,
  "wav_out": "out/proc.wav"
}
```

`allocations_in_hot_path`：用一个自定义 `GlobalAlloc` 计数器在 `process` 前后取差值，**非 0 直接让测试失败**。这条比任何代码评审都有效。

### P1-5 测试素材（**合成优先**，真实素材后补）

> 决策（§12 第 3 条）：真实开黑场景最终必须测，但当前先用合成素材把流程与基线跑通。

合成素材由 `testkit` 自己生成：`cargo run -p testkit -- gen --out testdata/ --seed 42`。随机种子固定 → 素材可复现、可进仓库、体积可控。

| 素材 | 合成方法 | 能验证什么 | **不能**验证什么 |
|---|---|---|---|
| `clean_48k_mono.wav` | 扫频正弦 + 合成元音（3 条共振峰）+ 音节包络 | 链路不炸、增益正确、SNR 底线 | 真实语音失真、吞字 |
| `keyboard_48k_mono.wav` | 随机脉冲群（5–20 ms 衰减振荡，2–8 kHz 重心，10–40 次/秒） | 非平稳瞬态压制趋势 | 真实键帽噪声谱 |
| `fan_48k_mono.wav` | 粉噪 + 1 kHz 以下低频加重 | 稳态噪声压制 | 真实风扇调制 |
| `chair_48k_mono.wav` | 带通 100–800 Hz 的随机包络摩擦噪声 | 低频瞬态 | 真实椅擦 |
| `babble_48k_mono.wav` | 4–6 路合成元音以不同节奏叠加 | 背景人声压制趋势 | 真实多人交谈 |
| `noise_only_48k_mono.wav` | 白噪 / 粉噪 | 音乐噪声与泄漏检测 | — |

**硬性限制（必须写进 `docs/measurements.md` 的头注）**：合成素材只能看趋势与做回归，**不能**作为以下事项的依据：

- D6 盲听裁决（P3-6）——推迟到真实素材到位；
- 设计文档 §11.2「降噪有明显压制」的终判；
- 「降噪不引入明显失真」这类主观判断。

真实素材到位后的动作顺序：替换 `testdata/` → 重跑 P3-5 基线 → 才允许做 P3-6；否则 P3-6 保持「阻塞」。

格式约定：48 kHz / 单声道 / f32 wav / 峰值约 −6 dBFS / 20–30 s。
### P1-6 延迟模型自检

写一个 `cargo run -p testkit -- latency-model --chain dfn3,agc2 --codec opus:10ms` 子命令，把设计文档附录 A 的表**用代码复算一遍**，输出预测 p50/p95。

**为什么值得做**：后面每次改链路，这个数字自动更新，人就不会凭感觉争论延迟。

**P1 完成定义**：上面三条 CLI 都能跑；`out/report.json` 里 `allocations_in_hot_path == 0`；`docs/measurements.md` 有了第一张表（P1 行）。

## 4. P2 桌面实时 I/O（3 人日）

> **本阶段只做桌面。** Android 环境未就绪（§12 第 5 条），安卓全部工作移到附录 §15 的 P2B 分支，独立排期。

### P2-1 `audio-io` 抽象

```rust
pub struct CaptureHandle;  // 内部：cpal stream + 向 rtrb 生产者写入
pub struct PlayoutHandle;  // 内部：cpal stream + 从 rtrb 消费者读取
pub fn list_devices() -> Result<Devices>;
pub fn start_capture(dev: Option<&str>, sink: rtrb::Producer<f32>) -> Result<CaptureHandle>;
pub fn start_playout(dev: Option<&str>, src: rtrb::Consumer<f32>) -> Result<PlayoutHandle>;
```

纪律：回调里**只做 `push`/`pop`**；缓冲不足时播放侧写静音、采集侧丢最旧，并各自计数 `xruns`。

### P2-2 `apps/loopback`（临时二进制，P6 前一直在用）

功能：采集 → `rtrb` → 直接回播（可选串 Opus 编解码），同时：

- 记录 `xruns`（采集丢帧 / 播放欠载）；
- 支持 `--impulse` 模式：播放已知脉冲序列，麦克风录回后自动算环回延迟；
- 输出与 testkit 同一套 JSON 报告。

**为什么必须有 `--impulse`**：这是唯一不靠假设就能拿到 D1 真值的手段（设计文档 §11.5 方法 3）。没有它，就只能相信「cpal 说 480 帧就是 10 ms」。

### P2-3 桌面三平台跑 D1

每平台至少 3 次 × 60 s，记录 p50/p95/max 与 xruns。目标 **≤ 15 ms p95**。至少覆盖：默认共享模式、buffer 调小一档、独占/低延迟模式（Windows 上 WASAPI 独占、Linux 上 PipeWire 直连）三种配置。

### P2-4 设备热插拔与错误恢复（容易被漏，但产品必须有）

- 拔掉 USB 耳机 / 切换默认设备时：捕获 `cpal` 的错误回调，重启流，UI 层收到事件；
- 不允许出现「设备消失后进程 panic」或「音频线程静默死掉但 UI 仍显示在线」；
- 验收：插拔 10 次不崩、恢复后仍能出声，且 measurements 里记录恢复耗时。

### P2-5 记录 D1

写进 `docs/measurements.md`，并把设计文档附录 D 的 D1 行标为「已测」。

**P2 完成定义**：桌面 D1 达标（≤ 15 ms p95）；插拔 10 次不崩；`measurements.md` 有 D1 的多配置行。

## 5. P3 处理链（5 人日）

**顺序不能乱**：先无降噪基线 → 高通 → AGC2 → RNNoise → DFN3。每加一级，跑一次 `testkit`，把数字填进 `docs/measurements.md`。

### P3-1 高通 + AGC2

- 高通 80 Hz（自己写 2 阶 biquad，20 行，`latency_samples() == 0`）；
- AGC2 封装 `sonora-agc2`：它按 10 ms 帧工作，需显式给采样率 48 000；
- **决策点**：若目标平台已有系统级 AGC（Android `VOICE_COMMUNICATION`），必须二选一，并把选择写进 `ChainDesc` 注释。

### P3-2 RNNoise 档（默认档）

- 封装 `nnnoiseless`：`FRAME_SIZE = 480`（已核实），`process_frame(out, in) -> f32`；
- 返回的 VAD 概率一路传到上层，供「谁在说话」的 UI 与 DTX 使用；
- `latency_samples()` 返回 480（10 ms）。

### P3-3 DFN3 档（feature `denoise-dfn3`，非默认）

- 封装 `deep-filter-rt`：480 样本帧、`delay()` 应为 1440 样本（30 ms）——**在单元测试里断言这个常数**，否则升级后预算表会静默失真；
- 模型 8.4 MB，确认 release 构建后的二进制增量（D11），写进 measurements；
- 若 `tract` 在目标机跑不动，触发 §11 的对策 B。

### P3-4 热切换

- 实现：新链先跑 20 ms 影子输出，再用 20 ms 线性交叉淡入替换，避免爆音；
- 切换必须在音频线程内完成，**不允许**在线程里 `Box::new`（预分配两套 stage 实例）。

### P3-5 离线回归基线

- 用 `testdata/` 五条素材 × 四档链跑出指标（不提交 wav）：每档的 RMS、SNR、削波计数、`vad_mean`；
- `tests/golden.rs` 比对指标容差（±5%），超差即失败；
- 这是后续所有依赖升级的护栏（deep-filter-rt 两周三次发版，没有护栏迟早出事）。

### P3-6 D6 盲听裁决（决定 DFN3 是否默认）——**当前阻塞：缺真实语音素材**

### P2 执行记录与偏差（2026-11-17，P2-1/P2-2 已落地，P2-3 待真机）

> 1. **cpal 0.18 与 0.15 的 API 有三处硬差异**（按旧记忆写必编译失败）：`SampleRate` 已变成 `u32` 的类型别名（不再有 `.0`）；设备的 `name()` 方法没了，名字只能走 `Display`（`device.to_string()`），身份是 `id()`；`build_input_stream`/`build_output_stream` 的 config **按值传**，第 4 个参数是 `Option<Duration>` 的 timeout。
> 2. **采样格式要覆盖 U8**：本机「网易虚拟音频设备」只提供 U8（部分虚拟声卡也是），原本只处理 F32/I16/U16 会直接开不了流。现已覆盖 U8 / I16 / U16 / I32 / F32 / F64。
> 3. **Windows 的 `sleep(1ms)` 实际睡 ~15 ms**：第一版「每 tick 推 1 ms 的量」导致 3 秒里播放欠载 16 704 样本。改成按**墙钟时间**算出应推到哪个位置（`target = elapsed × rate`）之后降到 1 117 样本，环缓冲占用也保持很低。
> 4. **录音环形缓冲不能和播放一样小**：抽干是「每轮循环一次」，两轮之间可能 15 ms，10 ms 的环必然溢出（实测丢 480 样本）。`--impulse` 模式把录音环放大到 20 倍（200 ms）；`--ring-ms` 默认值也从 10 改成 **50 ms**——10 ms 的环在两个独立设备之间必然溢出（实测直通模式丢 23 042 样本）。
> 4b. **`ErrorKind::Xrun` 是良性事件，不能当设备掉线**：第一版把任何错误都当「要重建流」，虚拟设备每抖一次就重建一次，2 秒里重启 2 次、丢 23 042 样本。改成「只有 `DeviceNotAvailable` / `HostUnavailable` / `StreamInvalidated` / `UnsupportedConfig` / `PermissionDenied` 才重建，`Xrun` / `DeviceChanged` / `DeviceBusy` / `RealtimeDenied` 只计数」之后：丢弃 0、欠载 96 样本、重启 0 次。
> 5. **虚拟设备冒烟只证明了管线通，证明不了延迟**：流能开、统计能收、报告能写；但虚拟声卡没有 loopback 路径，录音峰值 0.0078 恰好是 8-bit 的量化步长（1/128），即「有底噪、无信号」。所以 `--impulse` 现在会明确报「没找到相关峰：录音峰值 x（−60 dBFS 以上才算有声）」而不是吐一个假数字。
> 6. **`--impulse` 的不确定度是写进报告的**：`uncertainty_ms = (播放环**实测最大占用** + 一个回调缓冲) / 采样率`（用实测占用而不是环容量，容量只是上限），虚拟设备上量到 ±21.9 ms。它包含流启动错位，因此只能当「量级正确」用。要压到 ±2 ms 以内，得用 cpal 回调时间戳（`InputCallbackInfo::timestamp().capture` 与 `OutputCallbackInfo::timestamp().playback`）跨流比较——列为 P2-3 的后续工作。
> 7. **D1 必须在真实设备上跑，而且会出声**：`loopback --impulse` 默认走系统默认输出/输入，外放时才有声学路径（耳机环回则测的是电学路径）。
> 8a. **采样格式必须按质量挑**：第一版取「第一个支持 48 kHz 的配置」，在 TOPPING DAC + USB 电容麦上抓到的是 **U8**——播放侧 8-bit 量化、录音侧噪声底就是 1/128（−42 dBFS），脉冲完全测不出来。改成按 F32 > F64 > I32 > I16 > U16 > U8 排序后正常。**这也解释了第一次「没有出声」的观感**：8-bit 端点播出的脉冲又轻又糊。
> 8b. **`--impulse` 的估计器还不算可信**：周期脉冲串做互相关有「延迟 mod 周期」歧义，实测在 4 / 23 / 443 ms 之间乱跳；改单次脉冲（`--single`）后仍有 ±8 ms 的重复性误差（三次 11.8 / 4.0 / 9.5 ms，相关度 0.72–0.79）。原因是房间把 1 ms 脉冲抹宽了，峰值不再是稳定特征。**结论：D1 暂不能判定**，需要换成匹配滤波（用实际发射波形做相关）或共享时钟方案。
> 8c. **cpal 的 `StreamInstant` 在 WASAPI 上两路原点不共享**：把输入/输出回调时间戳直接相减，得到的是 154–198 ms 的常数偏移（每次运行都稳定在同一量级），而不是真实延迟。已把该路径保留为实验字段 `delay_ms_stream_clock`，主值仍用相关法。要修正必须拿到共享时钟（WASAPI `IAudioClock`/QPC 直读），这是 P2-3 的独立子项。
> 8d. **播放环的「推入序号 ≠ 流序号」**：流启动先播静音、欠载又插静音，直接把推入序号当流序号会让时间戳法偏出 150–200 ms。已在 `CallbackStamp` 里记 `real_frames` 并据此建映射。

> 3. 产品侧决定：客户端是否默认尝试独占、失败如何回退（判据已可靠：填充 0 次 + `GetPosition` 恒 0）；
> 4. P2-3 的 macOS / Linux 数字；
> 5. P3 处理链（高通 + AGC2 → RNNoise + VAD）——纯离线可测，不依赖音频硬件，是唯一能连续推进的主线。
>
> 已知坑（别重复踩）：归一化相关对幅度不敏感，会被低频漂移骗（用能量加权）；脉冲要零均值；
> 相关法的绝对值含流启动错位（0.4–1.4 s），只有时间戳法的值能用；`--buffer` 在共享模式下不改变实测延迟；
> 采样格式必须按质量挑（U8 会让脉冲听不见也测不到）；`Initialize`/`Start` 成功不等于流在跑；
> Windows 默认定时器精度 15.6 ms 会让所有 1 ms 级的轮询/供料失准（必须 `timeBeginPeriod(1)`）；
> WASAPI 回环采集必须用端点混音格式，否则 `AUDCLNT_E_UNSUPPORTED_FORMAT`。

> 8. **`--buffer <帧>` 已实现，独占模式还没做**：P2-3 要求的三配置里，「默认共享」「buffer 调小一档」现在都能跑；「WASAPI 独占」需要 cpal 的 `wasapi` feature + `AudioClient` 扩展，属于额外工作量，列为 P2-3 的独立子项。注意 `--buffer` 只是**请求**值，设备可以拒绝并回退默认——报告里记的是请求值，判断是否真的生效要看 xrun 与延迟变化。
