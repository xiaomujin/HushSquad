# HushSquad 执行方案与执行步骤

> 版本 v0.1.1（前置条件确认后修订）　日期 2026-11-16
> 上游依据：`HushSquad-技术设计-v0.2.md`（架构与验收）、`crates-选型验证报告-v0.1.md`（依赖事实）、`协议草案-v0.1.md`（线格式）。
> 本文档回答一个问题：**从空仓库到「能出声、延迟可测」的最小闭环，具体按什么顺序做、每步留什么产出、什么数字算通过。**
>
> **v0.1.1 修订依据**：2026-11-16 确认的 6 项前置条件（见 §12）。据此调整了：工具链锁定 1.100.0、测试素材改为「合成优先」、P2 收缩为纯桌面、Android 拆为独立分支 §15、许可证状态改为「待定」。

## 0. 执行原则（先读这 6 条，它决定了下面所有步骤为什么这么排）

1. **垂直切片，不做横向铺开**：先打通「采集→编码→解码→播放」这一条最细的线，再加降噪、再加网络、最后才做 UI。任何时刻仓库里都必须有一个**能跑出数字**的可执行程序。
2. **先测量，后优化**：每个阶段结束时必须新增或更新 `docs/measurements.md` 里的数字。没有数字的「做完了」不算完成。
3. **音频核心永不依赖 I/O 与网络**：`audio-core` 只吃 `[f32; 480]`，吐 `[f32; 480]`，可以在 CI 里离线跑。这是能持续做回归的唯一前提。
4. **降噪按档位插入，每档单独记账**：加一级就记一次延迟与 CPU，超出附录 A 预算的行必须当场决策，不允许「先加上后面再优化」。
5. **网络与协议放在音频之后**：音频链没达到 L0/L1 之前不碰 UDP，否则会同时调试两个不可见系统。
6. **服务器最后做，但协议先定**：协议文档已在仓库里，服务器实现只是为了验证协议，不是产品起点。

## 1. 阶段总览

## 3. P1 骨架 L0（3 人日）—— 第一个能出数字的东西

这一阶段完全不碰实时 I/O，也不碰网络，只做「离线把音频跑过链并报告每级耗时」。做完之后，后面所有优化都有比较基准。

### P1-1 定义核心接缝（先定接口，再写实现）

`crates/audio-core/src/lib.rs` 的**唯一公开契约**（草案，允许在 P1 内调整一次）：

```rust
pub const SAMPLE_RATE: u32 = 48_000;
pub const FRAME_SAMPLES: usize = 480;      // 10 ms
pub type Frame = [f32; FRAME_SAMPLES];

/// 所有音频阶段的统一接口。实时线程里调用 process()。
pub trait Stage {
    fn name(&self) -> &str;
    /// 该阶段引入的算法延迟（样本数）。这是预算表的唯一事实来源。
    fn latency_samples(&self) -> usize;
    /// 原地处理一帧，返回 VAD 概率（0.0–1.0，未知则 1.0）。
    fn process(&mut self, frame: &mut Frame) -> f32;
}
```

三条纪律（写进 `audio-core/CONTRIBUTING` 或文档注释）：

- `process()` 内**禁止**任何堆分配、锁、日志格式化、`Vec` 扩容；
- 所有可变缓冲在 `new()` 里预分配；
- 新增阶段必须同时更新 `latency_samples()`，否则预算表失真。

### P1-2 直通链 + 链路描述器

- `Chain`：`Vec<Box<dyn Stage>>` 仅在构造期使用，`process` 里遍历（v1 允许，先测出来再谈去虚化）；
- `ChainDesc`：可以序列化成 JSON 的链路描述（`[None]`、`[Rnn]`、`[Rnn, Agc2]`、`[Dfn3, Agc2]`…），保证「同一个实验可复现」；
- `total_latency_ms()` = 各 stage `latency_samples` 之和 / 48。

**验收**：`cargo test -p audio-core` 里断言 `ChainDesc::parse("none").total_latency_ms() == 0.0`、`parse("rnn").total_latency_ms() == 10.0`。

### P1-3 Opus 封装（先把编解码做成可替换的接缝）

```rust
pub trait AudioCodec {
    fn encode(&mut self, frame: &Frame, out: &mut [u8]) -> usize;
    /// lost = true 表示上一包丢失，解码器应走 PLC/FEC 路径
    fn decode(&mut self, payload: &[u8], lost: bool, out: &mut Frame) -> bool;
    fn lookahead_samples(&self) -> usize;   // 48 kHz 下应为 312
}
```

实现要点（来自报告 §2.5）：`Application::Voip`、10 ms 帧、`set_inband_fec(true)`、`set_packet_loss_perc(5..10)`、`set_complexity(10)`、`set_bitrate(32_000)`、单声道。**不要**用 `Application::LowDelay`。

**验收**：单元测试断言 `lookahead_samples() == 312`；编码 480 样本再解码，输出长度 480，SNR > 20 dB。

### P1-4 `testkit` 离线回放（本阶段最重要的产出）

CLI 设计（先定死用法，后面一直用）：

```bash
cargo run -p testkit -- \
  --in  testdata/clean_48k_mono.wav \
  --out out/proc.wav \
  --chain rnn,agc2 \
  --codec opus:10ms:32k \
  --report out/report.json
```

报告 JSON 字段（固定 schema，`docs/measurements.md` 直接粘）：

```json
{
  "chain": ["rnn", "agc2"],
  "codec": "opus:10ms:32k",
  "latency": { "algorithm_ms": 16.5, "per_stage_ms": { "rnn": 10.0, "agc2": 0.0, "opus": 6.5 } },
  "cpu_ms_per_frame": { "rnn": { "p50": 0.31, "p95": 0.55 }, "opus_enc": { "p50": 0.12, "p95": 0.2 } },
  "vad_mean": 0.42,
  "allocations_in_hot_path": 0,
  "wav_out": "out/proc.wav"
}
```

`allocations_in_hot_path`：用一个自定义 `GlobalAlloc` 计数器在 `process` 前后取差值，**非 0 直接让测试失败**。这条比任何代码评审都有效。

### P1-5 测试素材（**合成优先**，真实素材后补）

> 决策（§12 第 3 条）：真实开黑场景最终必须测，但当前先用合成素材把流程与基线跑通。

合成素材由 `testkit` 自己生成：`cargo run -p testkit -- gen --out testdata/ --seed 42`。随机种子固定 → 素材可复现、可进仓库、体积可控。

| 素材 | 合成方法 | 能验证什么 | **不能**验证什么 |
|---|---|---|---|
| `clean_48k_mono.wav` | 扫频正弦 + 合成元音（3 条共振峰）+ 音节包络 | 链路不炸、增益正确、SNR 底线 | 真实语音失真、吞字 |
| `keyboard_48k_mono.wav` | 随机脉冲群（5–20 ms 衰减振荡，2–8 kHz 重心，10–40 次/秒） | 非平稳瞬态压制趋势 | 真实键帽噪声谱 |
| `fan_48k_mono.wav` | 粉噪 + 1 kHz 以下低频加重 | 稳态噪声压制 | 真实风扇调制 |
| `chair_48k_mono.wav` | 带通 100–800 Hz 的随机包络摩擦噪声 | 低频瞬态 | 真实椅擦 |
| `babble_48k_mono.wav` | 4–6 路合成元音以不同节奏叠加 | 背景人声压制趋势 | 真实多人交谈 |
| `noise_only_48k_mono.wav` | 白噪 / 粉噪 | 音乐噪声与泄漏检测 | — |

**硬性限制（必须写进 `docs/measurements.md` 的头注）**：合成素材只能看趋势与做回归，**不能**作为以下事项的依据：

- D6 盲听裁决（P3-6）——推迟到真实素材到位；
- 设计文档 §11.2「降噪有明显压制」的终判；
- 「降噪不引入明显失真」这类主观判断。

真实素材到位后的动作顺序：替换 `testdata/` → 重跑 P3-5 基线 → 才允许做 P3-6；否则 P3-6 保持「阻塞」。

格式约定：48 kHz / 单声道 / f32 wav / 峰值约 −6 dBFS / 20–30 s。
### P1-6 延迟模型自检

写一个 `cargo run -p testkit -- latency-model --chain dfn3,agc2 --codec opus:10ms` 子命令，把设计文档附录 A 的表**用代码复算一遍**，输出预测 p50/p95。

**为什么值得做**：后面每次改链路，这个数字自动更新，人就不会凭感觉争论延迟。

**P1 完成定义**：上面三条 CLI 都能跑；`out/report.json` 里 `allocations_in_hot_path == 0`；`docs/measurements.md` 有了第一张表（P1 行）。

## 4. P2 桌面实时 I/O（3 人日）

> **本阶段只做桌面。** Android 环境未就绪（§12 第 5 条），安卓全部工作移到附录 §15 的 P2B 分支，独立排期。

### P2-1 `audio-io` 抽象

```rust
pub struct CaptureHandle;  // 内部：cpal stream + 向 rtrb 生产者写入
pub struct PlayoutHandle;  // 内部：cpal stream + 从 rtrb 消费者读取
pub fn list_devices() -> Result<Devices>;
pub fn start_capture(dev: Option<&str>, sink: rtrb::Producer<f32>) -> Result<CaptureHandle>;
pub fn start_playout(dev: Option<&str>, src: rtrb::Consumer<f32>) -> Result<PlayoutHandle>;
```

纪律：回调里**只做 `push`/`pop`**；缓冲不足时播放侧写静音、采集侧丢最旧，并各自计数 `xruns`。

### P2-2 `apps/loopback`（临时二进制，P6 前一直在用）

功能：采集 → `rtrb` → 直接回播（可选串 Opus 编解码），同时：

- 记录 `xruns`（采集丢帧 / 播放欠载）；
- 支持 `--impulse` 模式：播放已知脉冲序列，麦克风录回后自动算环回延迟；
- 输出与 testkit 同一套 JSON 报告。

**为什么必须有 `--impulse`**：这是唯一不靠假设就能拿到 D1 真值的手段（设计文档 §11.5 方法 3）。没有它，就只能相信「cpal 说 480 帧就是 10 ms」。

### P2-3 桌面三平台跑 D1

每平台至少 3 次 × 60 s，记录 p50/p95/max 与 xruns。目标 **≤ 15 ms p95**。至少覆盖：默认共享模式、buffer 调小一档、独占/低延迟模式（Windows 上 WASAPI 独占、Linux 上 PipeWire 直连）三种配置。

### P2-4 设备热插拔与错误恢复（容易被漏，但产品必须有）

- 拔掉 USB 耳机 / 切换默认设备时：捕获 `cpal` 的错误回调，重启流，UI 层收到事件；
- 不允许出现「设备消失后进程 panic」或「音频线程静默死掉但 UI 仍显示在线」；
- 验收：插拔 10 次不崩、恢复后仍能出声，且 measurements 里记录恢复耗时。

### P2-5 记录 D1

写进 `docs/measurements.md`，并把设计文档附录 D 的 D1 行标为「已测」。

**P2 完成定义**：桌面 D1 达标（≤ 15 ms p95）；插拔 10 次不崩；`measurements.md` 有 D1 的多配置行。

## 5. P3 处理链（5 人日）

**顺序不能乱**：先无降噪基线 → 高通 → AGC2 → RNNoise → DFN3。每加一级，跑一次 `testkit`，把数字填进 `docs/measurements.md`。

### P3-1 高通 + AGC2

- 高通 80 Hz（自己写 2 阶 biquad，20 行，`latency_samples() == 0`）；
- AGC2 封装 `sonora-agc2`：它按 10 ms 帧工作，需显式给采样率 48 000；
- **决策点**：若目标平台已有系统级 AGC（Android `VOICE_COMMUNICATION`），必须二选一，并把选择写进 `ChainDesc` 注释。

### P3-2 RNNoise 档（默认档）

- 封装 `nnnoiseless`：`FRAME_SIZE = 480`（已核实），`process_frame(out, in) -> f32`；
- 返回的 VAD 概率一路传到上层，供「谁在说话」的 UI 与 DTX 使用；
- `latency_samples()` 返回 480（10 ms）。

### P3-3 DFN3 档（feature `denoise-dfn3`，非默认）

- 封装 `deep-filter-rt`：480 样本帧、`delay()` 应为 1440 样本（30 ms）——**在单元测试里断言这个常数**，否则升级后预算表会静默失真；
- 模型 8.4 MB，确认 release 构建后的二进制增量（D11），写进 measurements；
- 若 `tract` 在目标机跑不动，触发 §11 的对策 B。

### P3-4 热切换

- 实现：新链先跑 20 ms 影子输出，再用 20 ms 线性交叉淡入替换，避免爆音；
- 切换必须在音频线程内完成，**不允许**在线程里 `Box::new`（预分配两套 stage 实例）。

### P3-5 离线回归基线

- 用 `testdata/` 五条素材 × 四档链跑出指标（不提交 wav）：每档的 RMS、SNR、削波计数、`vad_mean`；
- `tests/golden.rs` 比对指标容差（±5%），超差即失败；
- 这是后续所有依赖升级的护栏（deep-filter-rt 两周三次发版，没有护栏迟早出事）。

### P3-6 D6 盲听裁决（决定 DFN3 是否默认）——**当前阻塞：缺真实语音素材**

## 6. P4 鲁棒性（4 人日）

### P4-1 网络模拟器（在 testkit 里，不是真网络）

```rust
pub struct NetSim { pub loss: f32, pub jitter_ms: u32, pub reorder: f32, pub seed: u64 }
impl NetSim { pub fn step(&mut self, pkt: Packet, now_ms: u64) -> Vec<(u64, Packet)>; }
```

固定种子 → 结果可复现。先做它，再做抖动缓冲，否则弱网结论不可信。

### P4-2 抖动缓冲接入

- 用 `neteq`（`default-features = false`，见报告 §2.6）；
- 先解决 D7-1 的未决问题：关掉默认 feature 后能否只用缓冲、自己解码？结论决定是否要自建适配层；
- 每个 sender_id 一个缓冲实例；缓冲自报的延迟进 measurements。

### P4-3 包级冗余 + FEC + PLC

- 发送侧：每包带上一帧副本（`flags.bit0`、`red_len`）；
- 接收侧：当前包丢失 → 用下一包里的 red 恢复；再丢 → 走 Opus FEC 解码；连续 ≥3 → PLC 渐隐到静音；
- 用 `NetSim` 扫 0/1/3/5/10% 丢包，出「丢包率 × 可听质量」矩阵（D8）。

### P4-4 漂移与长跑

- 注入 ±100 ppm 漂移，跑 4 小时（用 `--speedup` 虚拟时钟加速）；
- 验收：缓冲深度不单调漂移、无爆音、无累积延迟增长；
- 不通过 → 外层加「按缓冲深度微调重采样比」的补偿器（`rubato` ratio 微调）。

### P4-5 混音与按人控制

- 多人 PCM 混音（排除自己）+ 软限幅；
- 按人音量/静音/独听是混音**前**的独立增益（这正是 MCU 方案做不到、而 v1 选 SFU 的产品理由）；
- 验收：8 人同时说话不削波、独听某人时其他人完全静音。

### P4-6 漂移补偿（对策 D，由 P4-4 触发）

- **位置**：网络线程上、`JitterBuffer::pull()` 之后、写入 PCM 环之前。那里已经知道 `buffered_samples`，
  且不占音频线程——音频线程仍然只做「出队 + 混音」。
- **两个候选机制，用测量选，不先拍**：
  1. 按缓冲深度微调**重采样比**（`rubato` ratio 微调；±500 ppm 的音高变化约 0.05 %，听不出，但要
     算清它自己的插值延迟与每帧 CPU，且它在音频线程上会分配）；
  2. **分数样本累积 + 1 ms 等功率交叉淡化**丢/补几个样本（零分配、无附加延迟，代价是每几百毫秒
     一次极短拼接——`max_step` 检测器能直接看出它做得好不好）。
- **控制律**：PI，目标 = 缓冲深度中点（17.5 ms），输出限幅 ±500 ppm，禁止对单帧抖动做反应。
- **验收**：重跑 `testkit drift-run --hours 4 --ppm ±100`，四条判据全绿（稳态在 15–20 ms、不爬、
  摆动 ≤ 5 ms、0 下溢 0 硬跳变）；再补一次**「抖动 + 漂移」联合长跑**——漂移会先把缓冲推到谷底，
  抖动才是真正的杀手，单靠漂移测试看不出来。

**P4 完成定义**：丢包矩阵与长跑报告进 measurements；D7/D8 有明确结论；混音链路能离线跑 8 轨。

### P2 执行记录与偏差（2026-11-17，P2-1/P2-2 已落地，P2-3 待真机）

> 1. **cpal 0.18 与 0.15 的 API 有三处硬差异**（按旧记忆写必编译失败）：`SampleRate` 已变成 `u32` 的类型别名（不再有 `.0`）；设备的 `name()` 方法没了，名字只能走 `Display`（`device.to_string()`），身份是 `id()`；`build_input_stream`/`build_output_stream` 的 config **按值传**，第 4 个参数是 `Option<Duration>` 的 timeout。
> 2. **采样格式要覆盖 U8**：本机「网易虚拟音频设备」只提供 U8（部分虚拟声卡也是），原本只处理 F32/I16/U16 会直接开不了流。现已覆盖 U8 / I16 / U16 / I32 / F32 / F64。
> 3. **Windows 的 `sleep(1ms)` 实际睡 ~15 ms**：第一版「每 tick 推 1 ms 的量」导致 3 秒里播放欠载 16 704 样本。改成按**墙钟时间**算出应推到哪个位置（`target = elapsed × rate`）之后降到 1 117 样本，环缓冲占用也保持很低。
> 4. **录音环形缓冲不能和播放一样小**：抽干是「每轮循环一次」，两轮之间可能 15 ms，10 ms 的环必然溢出（实测丢 480 样本）。`--impulse` 模式把录音环放大到 20 倍（200 ms）；`--ring-ms` 默认值也从 10 改成 **50 ms**——10 ms 的环在两个独立设备之间必然溢出（实测直通模式丢 23 042 样本）。
> 4b. **`ErrorKind::Xrun` 是良性事件，不能当设备掉线**：第一版把任何错误都当「要重建流」，虚拟设备每抖一次就重建一次，2 秒里重启 2 次、丢 23 042 样本。改成「只有 `DeviceNotAvailable` / `HostUnavailable` / `StreamInvalidated` / `UnsupportedConfig` / `PermissionDenied` 才重建，`Xrun` / `DeviceChanged` / `DeviceBusy` / `RealtimeDenied` 只计数」之后：丢弃 0、欠载 96 样本、重启 0 次。
> 5. **虚拟设备冒烟只证明了管线通，证明不了延迟**：流能开、统计能收、报告能写；但虚拟声卡没有 loopback 路径，录音峰值 0.0078 恰好是 8-bit 的量化步长（1/128），即「有底噪、无信号」。所以 `--impulse` 现在会明确报「没找到相关峰：录音峰值 x（−60 dBFS 以上才算有声）」而不是吐一个假数字。
> 6. **`--impulse` 的不确定度是写进报告的**：`uncertainty_ms = (播放环**实测最大占用** + 一个回调缓冲) / 采样率`（用实测占用而不是环容量，容量只是上限），虚拟设备上量到 ±21.9 ms。它包含流启动错位，因此只能当「量级正确」用。要压到 ±2 ms 以内，得用 cpal 回调时间戳（`InputCallbackInfo::timestamp().capture` 与 `OutputCallbackInfo::timestamp().playback`）跨流比较——列为 P2-3 的后续工作。
> 7. **D1 必须在真实设备上跑，而且会出声**：`loopback --impulse` 默认走系统默认输出/输入，外放时才有声学路径（耳机环回则测的是电学路径）。
> 8a. **采样格式必须按质量挑**：第一版取「第一个支持 48 kHz 的配置」，在 TOPPING DAC + USB 电容麦上抓到的是 **U8**——播放侧 8-bit 量化、录音侧噪声底就是 1/128（−42 dBFS），脉冲完全测不出来。改成按 F32 > F64 > I32 > I16 > U16 > U8 排序后正常。**这也解释了第一次「没有出声」的观感**：8-bit 端点播出的脉冲又轻又糊。
> 8b. **`--impulse` 的估计器还不算可信**：周期脉冲串做互相关有「延迟 mod 周期」歧义，实测在 4 / 23 / 443 ms 之间乱跳；改单次脉冲（`--single`）后仍有 ±8 ms 的重复性误差（三次 11.8 / 4.0 / 9.5 ms，相关度 0.72–0.79）。原因是房间把 1 ms 脉冲抹宽了，峰值不再是稳定特征。**结论：D1 暂不能判定**，需要换成匹配滤波（用实际发射波形做相关）或共享时钟方案。
> 8c. **cpal 的 `StreamInstant` 在 WASAPI 上两路原点不共享**：把输入/输出回调时间戳直接相减，得到的是 154–198 ms 的常数偏移（每次运行都稳定在同一量级），而不是真实延迟。已把该路径保留为实验字段 `delay_ms_stream_clock`，主值仍用相关法。要修正必须拿到共享时钟（WASAPI `IAudioClock`/QPC 直读），这是 P2-3 的独立子项。
> 8d. **播放环的「推入序号 ≠ 流序号」**：流启动先播静音、欠载又插静音，直接把推入序号当流序号会让时间戳法偏出 150–200 ms。已在 `CallbackStamp` 里记 `real_frames` 并据此建映射。

> 9a. **±8 ms 抖动不是「房间把脉冲抹宽」，而是相关度指标本身失效**。旧实现取 3 ms 窗做归一化相关、再按「最早一个超过全局峰 75% 的局部极大」定位。问题在归一化：它把窗内能量除掉，于是**幅度完全不进入判据**。用 `--dump` 把真机录音存成 WAV 一看，静音区的 rms 相关度是 **0.72**、最大 0.98——录音被 300–400 Hz 的低频漂移主导（比脉冲只低 30 dB，且与脉冲同频段），任何平滑窗都能拿到 0.9 以上。工具于是把底噪判成「4 ms 的延迟」，而真正的脉冲在 900 ms 处。
> 9b. **脉冲波形必须零均值**。第一版是「半正弦 × 指数衰减」，单极性、含很大直流分量；直流让「一段常数」也能和模板对上。改成 **汉宁包络 × 整周期正弦**（对称、严格零均值）后，自相关主瓣窄到 0.5 ms，峰值位置对 1 样本平移也不再系统性偏移（旧波形上抛物线插值有 +0.7 样本的固定偏差）。
> 9c. **判据从「相关度」换成「检测信噪比」**：`detection_snr = 峰值 ÷ 整条曲线的 |score| 中位数`，低于 20× 直接拒绝给数。真机上这个数是 134–1751×，纯漂移只有 3–5×，余量足够。相关度仍保留为质量参考字段（`correlation`），但不再当判据。
> 9d. **真机重复性达标：5 次 × 3 配置，极差 0.14–0.39 ms**（旧实现 ±8 ms）。这是把「折叠 + 能量加权 + 抛物线插值」三件事一起做完的结果。离线回归也补齐了：20 组不同噪声种子下位移极差 ≤1 样本、反射比直达声强 90% 时仍选直达声、只有漂移时必须拒绝。
> 9e. **主值改走时间戳通道**。相关法的 lag 是「录音数组下标 − 发射数组下标」，而两个流**不是同时开始的**：默认输出流的首个回调比采集流晚 0.4–1.4 s（本机实测，且这个错位每次运行都不同）。所以相关法的绝对值天生不可用。时间戳法把「发出去的那个样本」和「录到的那个样本」各自换算成同一根回调墙钟再相减，错位自动抵消——已验证它**与自有环形缓冲无关**（`--ring-ms 50` 与 `400` 同值）**与 `--buffer` 无关**。相关法的值降级为诊断字段 `delay_ms_correlation`。
> 9f. **198 ms 全在播放侧，而且 WASAPI 自己不承认**。时间轴诊断显示：采集侧是实时的（录音下标 ÷ 采样率 = 采集回调时刻，差 <2 ms），播放侧才是延迟来源。而 `playback − callback` 与 `capture − callback` 两条时间戳的差只有 **43 ms**——设备只报 43 ms，其余 ~155 ms 对 `IAudioClock` 不可见。这与「笔记本 Dolby/Nahimic 类 APO 在引擎之后又加一层延迟」的特征一致（同一现象也解释了默认输出流启动要 ~0.8 s）。
> 9g. **D1 判定：默认共享模式不达标**。实测 198.3 ms（p50，n=5，极差 0.39 ms），预算 ≤15 ms p95。`--buffer 128` 与 `480` 差 0.16 ms，说明调小 cpal 缓冲救不了——要救只能绕过 APO（WASAPI 独占模式，或在系统里关掉该输出的「音频增强」）。
> 9h. **只有默认设备这一对能测**：换 `扬声器 (TOPPING USB DAC)` 或 `Realtek Digital Output` 时录音里根本没有脉冲（峰值 0.010–0.012 = 纯底噪），因为这两路在本机没有可被麦克风听到的声学路径。虚拟设备对（网易 / Steam）也没有 loopback 路径（网易峰值 0.0000；Steam 采集是 44.1 kHz，与播放 48 kHz 不一致，工具直接报错）。
> 9i. **新增 `--repeat N` / `--dump <wav>` 与三条诊断输出**：连测中位数与极差、录音 WAV（排查「两个峰」这类问题的唯一手段）、`stream_nanos − wall_nanos` 的中位数（= 设备缓冲深度）、播放/采集点击的绝对时间轴。这几样是把「数字不对」拆成「哪一侧不对」的关键，不要再靠猜。
> 9j. **报告字段有增有删**：新增 `detection_snr` / `delay_ms_correlation` / `repeats` / `delay_spread_ms` / `run_delays_ms` / `delay_fractional_lag` / `click_spread_ms`；**删掉** `delay_ms_stream_clock` 与 `stream_clock_spread_ms`（它们是基于「跨流原点不共享」这个错误假设留的实验字段，现在证明假设本身是错的：两路 QPC 共享原点，错位来自流启动时刻）。这是 P2 期间唯一一次「schema 不只增不减」，理由是被删字段的名字会误导读者。

> 9k. **WASAPI 独占模式（P2-6 第二步）已实现并实测，结论是「这条路在本机被 APO 链堵死」**（2026-11-17）：
>
> - cpal 0.18 的公开 API 只有共享模式，所以 `apps/loopback/src/exclusive.rs` 直接对 `windows` crate 写 `IAudioClient`（只做**渲染**：采集侧实测已是实时的，198 ms 全在播放侧）。事件驱动 + `IAudioRenderClient` + `IAudioClock` 做诊断；`CallbackStamp` 五个字段语义与共享模式完全一致，`stamp_delay_of` 一行没改。
> - 三个驱动怪癖（已进 `measurements.md` §1.2 的表）：缓冲时长必须是设备周期整数倍；**`hnsPeriodicity` 只接受等于 `hnsBufferDuration`**（0 与「一个周期」都被拒）；**必须先 `GetBuffer(整块)` → 填静音 → `ReleaseBuffer`，再 `Start()`，且不能先查 `GetCurrentPadding`**——`Start` 之前它会报错，一旦兜底成「满」就永远预填不进去。这个坑让第一版静默跑了 3 秒、填充 0 次。
> - 实测（同机同代码，只换端点）：挂 APO 的 `扬声器 (Realtek(R) Audio)` 与 `Realtek Digital Output` 能 `Initialize`、能 `Start`，但 `GetPosition` 恒 0、`padding` 恒满、填充 **0** 次；无 APO 的 `扬声器 (TOPPING USB DAC)` 正常，i16 / 288 帧（6.00 ms）/ 周期 144 帧，2 s 内填充 **313** 次。→ 结论 **C-07 / C-08 / C-09**。
> - 新增 CLI：`--exclusive`；`--exclusive-rate <hz>`（**仅诊断**：强行让渲染与采集采样率不同，只为判断设备到底在不在消费，此时不产出延迟读数）；`--output` 在独占模式下也生效（按端点友好名精确优先、其次子串）。新增报告字段 `playout_format.actual_buffer_frames`。
> - 诊断口径修正：`stream_nanos` 是 QPC、`wall_nanos` 是 `Instant`，两个纪元差几十分钟，之前「设备时刻 − 回调」会印出 +3900356 ms 这种没法读的数。现在用 `exclusive::qpc_epoch_offset_ns()` 对齐，采集侧读数为 **−10.3 ms**（正好一个 480 帧缓冲），播放侧 +9.2 ms。
> - 工具行为改进：独占流若一次都没填充，直接报出原因并附同机对照，不再退化成一句「没测到脉冲」。

> 9m. **播放路径看门狗（P2-4 的第一块）+ TS3 3.6.2 的实测参考**（2026-11-17）：
>
> - `audio_io::Watchdog`：每路流起一条 50 ms 的监视线程，回调里 `touch()` 一次 QPC；停滞超过
>   `CALLBACK_STALL_MS = 500` 就发 `StreamEvent::Fatal { kind: "stalled" }`，恢复后允许再次上报。
>   阈值取 500 ms 的理由：按 10 ms 缓冲算已经落后 50 个缓冲，再等只是让用户多听半秒静音。
> - 为什么必须有它：设备被拔、驱动挂了、或端点「`Initialize`/`Start` 成功但硬件不走」时，
>   cpal 的回调**直接不再被调用且不抛错误**，上层只看到「没有新数据」，分不清安静还是死了。
> - 参考值来自 TS3 3.6.2 的实际二进制（解包 `soundbackends` 与 exe 字符串）：它的看门狗是
>   `callbackWaits1/2 wait exceeded 5 secs`、渲染侧自旋上限 1000 次、采集侧 10000 次，
>   **且只记日志不恢复**——官方已知限制里「设备不出声时渲染线程卡在 callbackWaits」正是这个后果。
>   我们取 500 ms 且必须能恢复，这是明确的取舍差异。
> - 为避免参数爆炸，采集/播放回调的共享句柄打包成 `CallbackContext<Q, S>`（环、计数、事件、时间戳、看门狗）。
> - 真机复测：正常播放不误报（`--repeat 2` 无 stalled），读数 175.53 / 175.88 ms，与上一轮一致。
> - TS3 解包结论：`soundbackends` 只有 `directsound_win64.dll`，WASAPI 在 exe 内；exe 里能找到
>   `IAudioClient` / `GetDevicePeriod` / `IMMDeviceEnumerator` / `IMMNotificationClient`；
>   编解码是 Opus + Speex（AEC 用 Speex），没有 RNNoise；DSP 通过 `setPlaybackDsp` 配置。
>   **没有可直接复用的音频实现代码**（客户端闭源，只有字节补丁与重打包工具链）。
> 9n. **重采样结案 + ADR-0010 落地**（2026-11-17）：

>   本机实测值，禁止端到端单一数字承诺。同步更新技术设计 §2.2、附录 A 注意项、ADR 索引、

> 9r. **P3-4：20 ms 交叉淡入热切换**（2026-11-17）：
>
> - `stages::Crossfade` 包住「当前档」与「下一档」，`begin(next)` 之后 2 帧（20 ms）内线性淡入。
>   它不是 `StageKind`——切换是运行期操作，不是链路里的一档。
> - 「加权平均」四个字盖不住三个坑，这个模块就是为它们存在的：
>   1. **两路延迟不同**（0 / 10 / 30 ms）。不对齐就混出梳状滤波（发闷）甚至回声。做法：把延迟
>      短的那一路推迟到与长的一路对齐（`target`），两路输出都从环形历史里按偏移读。
>   2. **新环节的流水线是空的**。DFN3 要喂满 30 ms 才出有意义的输出，直接接上去就是一次断音。
>      做法：切换时先用**输入历史预热**新环节（喂它过去 30 ms 的音频，输出写进历史缓冲），
>      它接手的第一个样本就是对齐的。
>   3. **降延迟方向会丢音频**。从 DFN3 切回 RNNoise，若立刻收掉 20 ms 对齐延迟就得丢 20 ms 音频。
>      v1 选择**不回收**（`target` 单调不减）：宁可多背 20 ms，也不断音。回收要变速率滑移
>      （200 ms 内悄悄吃掉 20 ms），留给 P4。
> - 权重用**线性**而不是等功率：两路高度相关（同一段音频，一路过了降噪），等功率会在中间点 +3 dB。
> - 五条单元测试：等延迟切换无台阶、2 帧内切完、延迟不匹配时阶跃只出现一次（无中间值 = 无回声）、
>   对齐目标不回收、预热后第一帧就有真实输出。

> 9t. **P4-1：网络模拟器（固定种子可复现）**（2026-11-17）：

> - `testkit::netsim::NetSim<T>`：泛型载荷（语音包类型 P5 才有，泛型让模拟器先独立测试）。

>   这是「弱网结论必须可复现」的前提——随机源一换，历史结论就全废。
> - 三个参数：`loss`（概率丢弃）、`jitter_ms`（0..=jitter 均匀延迟）、`reorder`（该概率下把延迟

>   （10 000 包 10% 允许 ±1.5 个百分点，且投递+丢弃 = 送入）、抖动不越界、乱序确实产生逆序
>   且不丢不重、抖动积压后推进时钟必到齐。

> 9u. **D7-1 有答案了：neteq 关默认 feature 后能用、解码器可插拔，但它会分配**（2026-11-17）：
>
> - `cargo tree` 实测：`default-features = false` 之后只剩 `log` / `ringbuf` / `serde` / `thiserror` /

> - `neteq::codec::AudioDecoder` 是公开 trait，`NetEq::register_decoder(payload_type, Box<dyn
>   AudioDecoder + Send>)` 收任意实现 → **保留我们自己的 libopus 解码**，不引入 ropus。理由：
>   两个 Opus 实现等于两种 FEC / PLC 行为，弱网下这种不一致最难查。
> - 验证不是「读文档」而是**跑通**：`jitter::tests::our_opus_decoder_plugs_into_neteq` 用我们的

>   全零，测试必红——这就是这条测试存在的意义。

>   `Vec<f32>`，所以 neteq **每包、每 tick 都堆分配**。这与「热路径零分配」直接冲突 → 抖动缓冲
>   不能跑在音频回调里。两条路线：(a) 网络线程跑缓冲、PCM 经 `rtrb` 无锁环交给音频线程
>   （推荐，时间伸缩正是 NetEQ 的价值所在）；(b) 换不分配的缓冲实现（丢掉时间伸缩）。
> - 顺手记一个坑：`NetEqConfig::default()` 的采样率是 **16 000**，必须显式传 48 000，否则时间
>   伸缩按错误速率工作。
> - **新增依赖带来的 advisory**：`cargo deny` 报 RUSTSEC-2026-0293（ringbuf < 0.5.2 的
>   `Consumer::skip/clear` 在元素 Drop panic 时会二次释放）。核实后按「**不可达**」忽略，并把理由
>   写进 `deny.toml`：neteq 0.9.1 的源码里**没有任何 ringbuf 引用**（`grep -r ringbuf src/` 为空，
>   纯遗留依赖），我们自己的环用 `rtrb` 也不用 ringbuf，且触发条件还要求元素 Drop 会 panic。
>   解除条件写在同一处：neteq 升级到 ringbuf ≥ 0.5.2，或换掉 neteq。
> 9v. **P4-2 接收路径落地：两个环把分配关在工作线程里**（2026-11-17）：
>
> - `audio-core::receive`：`PacketSender`（网络侧）→ `packets` 环 → `ReceivePath::tick()`（工作线程，
>   会分配）→ `pcm` 环 → `PcmReceiver::pull_frame()`（音频回调，**零分配**）。
> - 为什么要拆成 tick / pull：neteq 的 `decode -> Vec<f32>` 与 `AudioFrame { samples: Vec<f32> }`
>   决定了它每包每 tick 都分配，而热路径纪律是零分配。调和办法不是改 neteq，是把分配关进
>   另一个线程。**线程本身归 P5 的网络循环**——现在没有真实网络源，擅自起线程只是多一份不可
>   复现的行为；测试直接调 `tick()`，完全确定。
> - **必须处理的事实**：NetEQ 的默认目标延迟是 **80 ms**（浏览器场景调参），而附录 A 第 9 行的
>   预算是 L1 10–15 ms、L2 15–20 ms。`JitterBuffer::set_maximum_delay` 把它压进预算（已测：
>   `set_maximum_delay(20)` 后 `target_delay_ms() <= 20`）。这条不压，L1 档从抖动缓冲就超预算。
> - PCM 环的深度**就是**接收侧的额外延迟（4 帧 = 40 ms），别开大：抖动缓冲自己已经在自适应
>   延迟了，再叠一层只是把总延迟推高。
> - 四条测试：下溢填静音并计数、10 帧包能穿过抖动缓冲解出有声帧、别的发送方的包被忽略、
>   包环满返回 false 而不是阻塞或 panic。
> - 还缺（明确记着）：P5 的网络线程调用 `tick()`；P4-3 用 `NetSim` 扫丢包率出矩阵。
> 9w. **P4-3 丢包矩阵：先修好「丢包能被看见」，再量出分界线**（2026-11-17）：
>
> - **前提 bug（必须先修）**：`JitterBuffer::push` 原来自己递增序号，于是网络丢掉的包在 NetEQ
>   眼里根本不存在（序号连续）——它不会做 PLC，只会把后面的音频往前挪。那是「时间压缩」而不是
>   「丢包隐藏」，量出来的数字不是弱网下的数字。改成由发送方给 `seq` / `timestamp`（`IncomingPacket`
>   多了这两个字段），并加 `note_seq` 用序号空洞数出网络丢包。
> - **顺手抓到 neteq 0.9.1 的一个真坑**：`PacketBuffer::get_span_duration_ms` 用 `u32` 算
>   `span_samples * 1000`，时间戳跨度一大就**乘溢出**（debug 构建 panic、release 算垃圾）。
>   这条路径在网络线程上，panic 等于断音。对策：`JitterBuffer::push` 拒收跳变超过 5 s 的包
>   （`NetEqError::InvalidTimestamp`），并写测试钉住「拒收而不是 panic」。
> - `testkit loss-matrix`：素材 → 编码 → `NetSim` → `ReceivePath` → 解码，产出 SNRseg / 全局 SNR /
>   帧能量误差 / 对齐极差 / 缓冲峰值 / 码率。参考信号是**编解码往返**（不是原始素材），否则 32 kbps
>   自己的 17.5 dB 会把丢包损伤淹掉。
> - **对齐必须分块**（200 ms 一块）：丢包后 NetEQ 先 `expand` 再 `accelerate`，块内时间轴不是常数。
>   踩过两次坑，都写进了注释：① 用单一全局延迟时，600 帧里只丢 6 个包就把 SNRseg 从 34.9 打到
>   1.6 dB——那不是损伤，是对错了位；② 最后一块的搜索区间会被 `output` 长度掐到塌缩，于是按
>   lag = 0 对齐，把 0 % 丢包的全局 SNR 从「无损」拉低到 10.9 dB。现在的规矩是「窗口太窄就沿用
>   上一块的延迟，不在塌缩的区间里瞎猜」，并且打分前把结尾那段「流结束」的 PLC 垃圾裁掉。
> - **结果**（`docs/measurements.md` §3.1）：0 % 丢包输出与参考**逐样本相同**（自检成立）；只靠
>   PLC 时 3 % 丢包 SNRseg 26.3 dB、10 % 时 9.86 dB（C-21）；包级冗余（每包发两遍，带宽 ×2）把
>   5 % 拉回 34.0 dB、10 % 拉回 30.2 dB（C-22）。抖动缓冲深度峰值 10 % 丢包下仍 ≤ 20 ms，
>   L2 预算守得住（C-24）。
> - **一个架构结论**：Opus in-band FEC **接不上 NetEQ**（C-23）——`AudioDecoder` 只有
>   `decode(encoded) -> Vec<f32>`，没有 FEC 入口，而 FEC 恢复出来是 PCM、NetEQ 要的是包。要接上
>   得改 neteq 的 trait 或自己写抖动缓冲。所以先把「冗余能买多少 dB」量清楚，再决定动不动 neteq。
> - 四条测试：0 % 丢包近乎透明、丢得越多越差、同种子逐位复现、冗余换来质量但码率翻倍。

> 9y. **P4-5 混音与按人控制：8 路、零分配、指令走无锁环**（2026-11-17）：
>
> - `audio-core::mix`：`Mixer`（音频线程）⇄ `MixControl`（UI 线程）。8 路定长槽位，音源抽象成
>   `TrackSource`（`PcmReceiver` 是真实实现，测试里用假音源）——这样混音能脱离网络/编解码单独测。

>   `pop`（每帧上限 64 条），控制侧的 `Mutex` 在非实时路径上，可以接受。指令在**下一次 `mix` 边界
>   生效**（最多 10 ms），`has_track` 反映的是音频侧状态，别当「指令已执行」的凭据。
> - **增益一律一帧（10 ms）线性渐变**：静音、独听、改音量、新轨加入都走同一条路，所以都不会「咔」。
>   测试钉住了「第一帧在渐变、第二帧到目标」。
> - **独听语义**：任一轨独听 → 其余轨静音；**静音优先于独听**（自己点了静音，别人怎么独听都不会把
>   自己放出来）。多轨同时独听 = 这几轨都出声。

>   起伏，多人同时说话时听感是「抽气」。软限幅无状态、无攻击时间，正常混音根本碰不到拐点；过载量

> 9z. **P4-4 漂移长跑：结论是「不通过」，而且不是调参能救的**（2026-11-17）：
>
> - 新增 `testkit drift-run`（`crates/testkit/src/drift.rs`）：**虚拟时钟、不睡觉**，一个 tick = 10 ms
>   虚拟时间；漂移注入在**发送侧**（每 tick 产生 `480 × (1 + ppm×10⁻⁶)` 个样本，序号/时间戳按发送方
>   样本计数走）——真实世界里改不了声卡快慢，能改的只有「收到多少」。4 小时 = **144 万帧**，release
>   下约 5 分钟墙钟，所以这条长跑可以反复重跑，不是一次性仪式。
> - 判据从「缓冲深度不单调漂移」细化成三条**可测**的：①**稳态水平在 15–20 ms 预算内**（把「收敛到
>   错误的水平」和「永远在爬」分开——两者修法完全不同）；②**稳定之后不再爬**（后三分之一 − 中间三
>   分之一 ≤ 2 ms）；③**不摆动**（稳态极差 ≤ 5 ms）。外加 0 下溢 / 0 硬跳变 / 0 清空，以及样本守恒。

>   - **0 ppm 通过**：4 小时缓冲**纹丝不动 14.00 ms**，压缩/拉伸/PLC 全 0，极差 0。这条同时是管线自检。
>   - **+100 ppm 不通过**：漂移确实被压缩掉 **67 708 / 69 120** 样本（98 %），但缓冲稳在 **36.76 ms**
>     （`33 → 44 ms` 锯齿，周期约 60 s，每次压缩 9.8 ms ≈ 163 ppm，比注入值多 63 % 所以必然过冲）。
>     **凭空多付 17 ms 延迟，而且延迟自己在 ±6 ms 内摆。**
>   - **−100 ppm 不通过**：`inserted_samples_for_deceleration` **恒为 0**——一次预拉伸都没有。缓冲在
>     `5 → 21 ms` 之间以 8 分钟为周期乱走，靠 **194 次 PLC** 补了约 1.44 s 音频。5 ms 的谷底意味着
>     任何网络抖动都会直接打成欠载（这个测试里没有抖动，所以看不见）。
> - **根因（读源码，不是猜）**：`neteq` 0.9.1 `get_decision` 的压缩阈值是
>   `high_limit = max(target, low_limit + 20 ms)`——**那个「+20 ms」是常数**，target 调到多低都绕不过
>   （target 20 ms → 阈值 35 ms，快速压缩 140 ms）；而预拉伸额外要求 `当前缓冲 ≥ 3 帧 = 30 ms`，在
>   20 ms 的预算里**永不成立**；`K_BASE_MIN_DELAY_MS = 20` 还把最小延迟硬编码成 20 ms。这不是 bug
>   而是取舍：该 crate 自己的测试 `test_continuous_streaming_buffer_convergence` 明确断言「20–40 ms
>   的缓冲只应发生极少的加速」——它按浏览器 80 ms 的 target 调参。
> - **顺带修了一个测量口径**：`concealed_samples` 是**上界**不是精确值（Expand 的整帧都记成隐藏样本，
>   实际只外推一小段；实测高报 25 %），所以守恒判据写成 `0 ≤ 推导值 ≤ 自报值`（±1 帧），不是等式（C-32）。
> - **结论：NetEQ 的自适应延迟不能当漂移补偿器用**（C-30/C-31）。技术设计 §6.6 与 §13 里那条
>   「NetEQ 是否已实现漂移补偿——**待验证**」，答案已出：**实现了，但工作点在我们的预算之外**。
>   → 触发**对策 D**，新开 **P4-6**（外层自建「按缓冲深度微调」的补偿器）。
> - 测试 3 条：0 ppm 缓冲不动、±1000 ppm 双向越界（**这是结论快照，P4-6 做完它会红**，那时把它改成
>   断言「漂移被吸收」）、同参数逐位复现。
> 9aa. **P4-6 漂移补偿：正向成立，反向还不成立**（2026-11-17）：
>
> - 先推导，再写代码。这条关系决定了整个结构，**必须先写下来**：
>   抖动缓冲深度每 tick 的变化 = `480(1+ε) − 480×pulls`，也就是 **B 只受「这一 tick 拉了几帧」
>   影响**——丢样本、补样本、改重采样比，对 B 一点作用都没有。而音频侧每 tick 固定取走 480 个，
>   所以每 tick 也必须写进 480 个。于是执行器被分成两个：**丢/补样本**改变「总延迟」，
>   **拉包次数**改变 B 与 PCM 环之间的分配；稳态解唯一：`slip = 480ε`、`pulls = 1+ε`（C-33）。
> - 这条推导**否掉了对策 D 原本的「微调重采样比」**：它同样需要「拉包信用」这一层，却多付插值
>   延迟、CPU 与每帧分配，换来的只是拼接更平滑；而拼接可以用 1.33 ms 等功率交叉淡化压到
>   `max_step` 测不出来。所以改成丢/补样本——同样的活，代价更小。
> - 落地：`audio-core::drift` 的 `DriftControl`（网络线程侧、零分配）。丢 `d` 个样本 = 在 X 处把
>   `in[X..X+F]` 淡出、`in[X+d..X+d+F]` 淡入；补 `m` 个 = 在 X 处倒回 m 个样本再交叉淡化接回。
>   控制器：队列深度（**包数**，不是样本数）的 EMA 误差 → 带小数的 `slip` 累积器（100 ppm 下稳态
>   只要每 tick 丢 **0.048** 个样本，取整会永远不动）→ 丢/补；拉包次数由 slip 的积分（信用）决定，
>   环水位做硬边界。6 条单元测试（直通逐样本一致、丢/补长度、拼接连结性、目标深度不动、太深丢、太浅补）。
> - **实测（4 小时）**：
>   - **0 ppm：逐样本透明**——0 丢 0 补，输出与不开补偿完全一致，缓冲 14.00 ms 纹丝不动；
>   - **+100 ppm：四条判据全绿**——24 个窗口全是 **14.00 ms**（对照 36.76 ms、33–44 ms 锯齿），
>     丢 68 375 样本、多拉 144 帧、环水位只动 265 样本且一个都没丢，**0 下溢、0 PLC、0 硬跳变、
>     0 软跳变**，`max_step` 0.0482（平滑上界的 1.47 倍）。**省回 22.6 ms**（C-34）；
>   - **−100 ppm：不成立**——缓冲均值 55.84 ms、峰值 197 ms，补偿器在该补的地方反而丢了 1.2 M 个
>     样本，NetEQ 被逼着加速 639 656 个。根因：补样本抬高环 → 「环太高就少拉」→ 队列变深 → 控制器
>     开始丢样本 → 环掉 → 又多拉，正反馈（C-35）。
> - **踩到的三个坑（都写进代码注释了）**：
>   1. 传感器不能用 `buffered_samples`：它把 `leftover_samples` 与 `leftover_time_stretched_samples`
>      也算进去，而这两个在 NetEQ 做时间伸缩时会自己涨——正反馈，实测一路跑到 10 % 时间压缩 + 全程 PLC。
>      改用**排队包数**；
>   2. 目标的**口径必须和采样时刻对齐**：补偿器在「收包之后、拉包之前」看队列，无漂移时那个时刻恒为
>      2（缓冲里 1 包 + 刚到的 1 包）。写 1.0 会让它一直以为「太深」而满速丢样本；
>   3. 拼接的**插入路径**尾巴要从「倒回之后」的位置接（`x-m+F`），否则输出长度少 m 个——长度对不上时
>      环水位记账会一路歪掉。
> - **三次结构返工（都写进代码注释了，别再走一遍）**：
>   1. 传感器用 `buffered_samples` → 正反馈（它含 leftover，做时间伸缩时自己涨）；
>   2. 「信用」和「环水位阀门」两套规则同时改 `credit` → 互相追，4 小时环涨 136 473 样本、
>      溢出丢 35 733 个（静默丢音频，比爆音难查得多）；
>   3. 环水位从「一帧垫子」开始记账 → 估计值比真实值高 480，反向时把环抽干、队列堆到 18 包。
>      必须**如实从 0 记账**，垫子靠多拉真拉出来。
> - 最后收敛到**一条规则**：`环 < 一帧 → 多拉；环 > 两帧 → 少拉`。因为 `Σslip = 480 × Σ(pulls−1)`
>   是恒等式，这条规则的平均拉包率自动等于 `1 + slip/480`，也就是漂移量本身——B 由 slip 唯一
>   确定，一个控制环就够。
> - ~~**状态：默认关闭**~~（已被 9ab 关闭）。还缺：① 反向的正反馈；② 一次「抖动 + 漂移」联合长跑。
>   两条都在 9ab 里做完了。
> 9ab. **P4-6 收尾：反向修好了、补偿器转默认开启、联合长跑照出真正的弱点**（2026-11-17 16:20）：
>
> - **反向的根因不是控制参数，是一句写法**：第一版把「少拉一帧」写成「回放上一帧」。PCM 环每 tick
>   的净变化 = 写进去的样本数 − 480（音频侧固定取走 480），所以
>   **多拉一帧 = 环 +480（唯一能让环变深的动作）**、正常一帧 = 环不变、少拉一帧**必须写 0**。
>   写 480 等于环不变，于是反向漂移时「补样本把环抬高」之后没有任何东西能把环降下来——环只会
>   涨到溢出。改成写 0 之后，那一帧由环里的存货顶上，**连拼接都不需要**（环本来就是连续样本流）。
> - 顺带修了两处记账：① 环水位下界从 480 抬到 482（一帧 + MAX_SLIP），因为丢样本每 tick 最多
>   拿走 2 个，下界正好 480 时实测会掉到 478，音频侧当场拿到 2 个样本的静音；② 滤波器**从目标
>   起步**而不是从第一次读数起步（起播瞬间队列是 0，从 0 起步会让补偿器把「还没收到包」当成
>   「缓冲太浅」，一路补样本把环推满，再花几分钟收回来）。
> - **4 小时实测（默认参数，四条判据全绿）**：0 ppm 稳态 12.00 ms、摆动 0.00、丢 218 个样本（3 ppm）、
>   补 0、`fabricated` 0；+100 ppm 稳态 **12.19 ms**、摆动 10.00（一个包，物理下限）、趋势 −0.00、
>   丢 68 858、多拉 147、环水位 +262、**0 下溢 0 硬跳变 0 软跳变**（C-34 修订）；−100 ppm 稳态
>   **17.81 ms**、摆动 10.00、补 67 428、少拉 142、环水位 +10、**0 下溢 0 硬跳变**（C-36）。
>   → `ReceivePath::new` 里补偿器**改为默认开启**（`DriftConfig::default()`）。
> - **联合长跑（抖动 0–10 ms + 丢包 0.5 %，4 小时）**：均值 14.27 ms、趋势 −0.01、0 下溢、0 硬跳变、
>   守恒成立；缓冲摆动 3–48 ms 完全由网络决定（NetEQ 在追抖动），所以**摆动这条判据在抖动链路上
>   不适用**，`violations()` 改成有抖动时跳过它。**顺带发现守恒等式漏了一项**：丢了 1 个包 NetEQ
>   就得多造 480 个样本来顶替，而「发送帧数 − 收到帧数」把丢包和漂移算成了一笔账——漏掉时 1 小时
>   0.5 % 丢包下守恒差出 105 024 个样本（推出负数，物理上不可能）（C-38）。
> - **照出来的真弱点：抖动链路上做 26 倍的无效功**（C-37）。1 小时丢 178 k、补 265 k 个样本，
>   而真正的漂移只有 17 k。传感器（排队包数）同时被漂移和抖动推动，200 ms 的 EMA 滤不掉 10–100 ms
>   的抖动，控制器每 tick 都饱和。**试过放慢 EMA，不行**：闭环是 `s² + αs + kp = 0`，α 必须 ≥ 2√kp
>   才不振荡，实测 α = 0.0005、kp = 0.02 时 Q ≈ 283，反向 4 小时里丢 30 918、补 40 635，两个方向在
>   对打（把 kp 也一起缩小则稳态偏置涨到 20 ms、缓冲跑到 56 ms）。正解是**换传感器**：
>   `Δ序号 / Δtick − 1` 对抖动与丢包都免疫，量出来就是 ε，不需要反馈环去猜——那要网络层把序号
>   喂进来，属 P5 的接线范围。判据量不到它（0 硬跳变、0 软跳变、`max_step` 1.51 倍），记为质量隐患。
> - 测试：audio-core 7 条（新增 `a_fast_sender_is_absorbed_without_runaway` /
>   `a_slow_sender_is_absorbed_without_runaway` 两条**闭环**回归，直接盯「队列钉住 + 环水位在
>   [一帧, 两帧] + 丢补不对打」）；testkit 4 条（`compensation_holds_the_budget_for_a_slow_sender`
>   由「断言它失败」改成「断言它通过」，`short()` 从 60 s 抬到 5 分钟——滤波时间常数 200 ms 加起播

> 9ac. **P5 传输闭环：协议、密码学、SFU、控制面、真 UDP 联调全部落地**（2026-11-17 17:20）：

> 9af. **修掉「声音空旷 + 失真」：等功率交叉淡化在每个拼接点上抬 +3 dB**（2026-11-17 21:05）——
> 起因：用户真机跑完反馈「声音有点空旷和失真」，贴了 280 秒的 `[stats]` 与退出汇总。
>
> - **从数字里直接读出了原因**：汇总里 `混音峰值 1.404`、软限幅 1315 样本，而发送端的
>   `采集峰值 0.950`。`1.404 / 0.993 ≈ √2` —— 这不是巧合，是等功率交叉淡化的中点值。
>   `splice()` 用 `(cos θ, sin θ)`，`cos²+sin²=1` 保的是**功率**；但这里交叉淡化的两路是
>   **同一路信号错开 1–2 个样本**（相关系数 ≈ 1），中点就是 `cos45° + sin45° = √2`。
>   每次拼接 = 1.33 ms 的 +3 dB 幅度凸包，而补偿器每秒做 ~74 次，于是语音上叠了一个
>   每秒几十次（实测每秒拼掉 74–104 个样本、每次 1–2 个样本）的 +3 dB 凸包。听感正是「空旷、发飘、
>   有点失真」。
> - **改法**：等增益权重 `(1 − w, w)`，两路相同时恒等于 1，与相关性无关（C-51）。
> - **门禁为什么漏了这条**：`max_step` 量的是**一阶差分**，而 +3 dB 凸包是**平滑**的 —— 64 个样本
>   升上去再落回来，逐点差分只有 `2πAf/F` 量级，一阶差分判据对它天然失明。所以「`max_step` 通过」
>   不等于「波形没被改动」。新增两条判据：`a_splice_keeps_the_level`（拼接区的峰值不得超过输入的
>   峰值）、`crossfade_weights_sum_to_one`。
> - **真机 A/B**（同一台机器、同一条链路、3 进程真 TLS + 真 UDP + 真声卡、90 s、0.25 幅度单音）：
>   改前混音峰值 **0.360（+3.17 dB）**、`slip` 6674；改后 **0.257（+0.23 dB）**、`slip` 6713。
>   3 dB 的凸包消失，而拼接次数一点没少 —— 说明改动只修了「拼接的幅度」，没有粉饰「拼接的次数」。
> - **C-37 的传感器写了、量准了、但接进环之后失败，因此默认关闭**。实现是
>   `DriftControl::note_seq_advance`（`Δseq/Δticks − 1`，对抖动和丢包免疫），单元测试钉住
>   0/±100 ppm 下误差 < 20 ppm，统计行也加了 `drift=±Nppm`。但一接进控制环，**+100 ppm 的
>   四小时长跑从绿变红**：稳态缓冲深度 12.19 → 28.11 ms、多拉/少拉帧 147/1 → 36 603/36 458、
>   丢/补样本 68 858/0 → 785 772/717 499。「净」量是对的（丢减补 = 漂移本身），但前馈是一个
>   **不经过传感器**的直流偏置，叠在 PCM 环水位的继电规则（< 一帧多拉、> 两帧少拉）上，把环推进了
>   一个 ~20 tick 周期的极限环。所以 `feedforward` 默认 false，代码留着、测量记下来。
> - **这次实测把 C-37 讲清楚了**（但没关掉它）：① 推动补偿器的「抖动」主要来自**我们自己两个
>   进程的 10 ms 相位差**，不是网络 —— 本机 127.0.0.1 回环（RTT 0.1 ms、0 丢包）照样每秒做
>   74 个样本的无效拼接；② 这份无效工作**正在替延迟预算兜底**：0 ppm + 10 ms 抖动下默认参数
>   17.8 ms（在预算内）、EMA 0.005/kp 0.005 → 30.6 ms、死区 0.25 包 → 30.5 ms、关掉补偿 →
>   28.8 ms，后三个全顶出 15–20 ms 预算。也就是说「延迟达标」是过度补偿的副产品，真要关掉得先修
>   `jitter.rs` 里「NetEQ 为什么停不在 20 ms 目标上」。这两条失败实验都写进了 `drift.rs` 的文档。
> - **新增 `--no-drift`**：诊断用，用户自己就能对比「加工感」是不是补偿器造成的。
> - **统计行新增 `pacing=±Nppm`**（对端**发包节奏**相对我们 tick 节奏的偏差），5 分钟后才显示：
