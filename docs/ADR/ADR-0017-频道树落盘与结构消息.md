# ADR-0017：频道树落盘（整棵树一次写），结构改动走四条消息

- **状态**：已定
- **日期**：2026-11-19
- **相关**：`docs/权限与频道管理设计-v0.1.md`（完整方案 §3 / §4 / §5）；
  `docs/proto/hushsquad-control-v1.proto`（`CreateChannel` / `UpdateChannel` / `MoveChannel` / `DeleteChannel`）；
  `crates/store/src/channels.rs`；`crates/server-core/src/channel_store.rs`；ADR-0016（权限先落地）

## 背景

在 P7-2 之前，频道树**不落盘**：服务器启动时按 `--channel` 在内存里建几个频道，重启就回到
一个「大厅」。也就是说管理员在客户端里改的结构活不过一次重启——这让「客户端里维护频道树」
这件事根本不成立。

同时，P7-2 要往控制面加**写**消息（之前控制面只有读：`ChannelSync` / `ChannelAdded` / …）。
按 `ADR/README.md` 的规则，「改变控制面字段」必须有一条 ADR。

于是要回答三个问题：**存哪儿**、**怎么发号**、**怎么保证一次拖拽要么全成要么全不成**。

## 决策

1. **存进服务器那个 SQLite**（`users.db` 同一个文件，`schema v1 → v2` 只加表）。
   不引入配置文件、不引入第二个库文件：备份服务器就是拷一个文件。
2. **`channel_id` 由服务器发号并显式写回**，表用 `INTEGER PRIMARY KEY`（**不用** `AUTOINCREMENT`）。
   发号只有一个来源（`Server::next_channel_id`），启动时接到「库里最大 id + 1」。
3. **持久化接口只有两个方法**：`load()` 读整棵树、`save(rows)` 用一个事务替换整张表。
   每次结构变化之后整棵树重写，不做「插入一行 / 改一行 / 删一行」的增量账。
4. **四条结构消息**：`CreateChannel` / `UpdateChannel` / `MoveChannel` / `DeleteChannel`。
   没有 `ReorderChannels`：一次拖拽的落点就是「移到父级 P 的第 i 位」，`MoveChannel` 已经能表达。
5. **校验一律在服务器**（名字、同级重名、深度 ≤ 3、防成环、有人拒删、最后一个可加入的频道不可删）。
   客户端菜单的裁剪只是可发现性，不是安全边界（ADR-0016 的同一条原则）。
6. **落盘失败如实报告**：内存改动已经生效时，广播照发，同时给发起者一条
   `INTERNAL`「改动已生效，但没能写进磁盘（重启会丢）」。

## 备选与被否原因

| 方案 | 被否原因 |
|---|---|
| 每次操作一条 SQL（`INSERT` / `UPDATE` / `DELETE`） | 拖拽要重排一堆兄弟的 `position`，得自己保证「这些 `UPDATE` 在同一个事务里、顺序是对的」。存储层要多维护一套「哪个操作对应哪几条语句」的账，加一种结构操作就要改一次 |
| 频道树存成配置文件（TOML / JSON） | 它是**会被频繁改**的状态，不是配置。并发写要做原子替换，读坏一个字节整棵树没了；而 SQLite 的事务、约束、崩溃恢复都是现成的 |
| `AUTOINCREMENT`，让库发号 | 「读出来再插回去」会换 id。迟到的客户端拿着旧 id 会**误操作到另一个频道**（而不是收到 `CHANNEL_NOT_FOUND`）。id 必须由服务器统一发，才能保证「删掉的 id 永不复用」 |
| 一次拖拽发一条「整表重排」（原来的 `ReorderChannels`） | 它是为了防并发丢频道设计的，但拖拽语义下并发只会让 `position` 的含义稍微偏移，服务器夹到合法范围即可，**不会丢任何频道**。少一条消息就少一套校验 |
| 客户端本地存一份频道树（离线可用） | 两台管理员的本地副本会打架，而「谁的树算数」没有答案。真相只有服务器一份 |

## 后果

- **好**：
  - 结构改动**原子**：拖拽要重排的兄弟、连带删除的子树，都在一次事务里；
  - 存储层薄：加一种结构操作不用碰 `store`；
  - 老库自动升级（v1 的库打开就多一张空表，账号一条不动，有测试钉住）；
  - 协议是**纯新增**（新消息 + 新错误码），主版本不变，旧客户端会忽略未知 oneof 分支。
- **代价**：
  - 每次结构变化重写全表。100 个频道 = 100 行，在「管理员点了一下」的频率下无所谓，
    但如果将来出现「几百个频道 + 自动化脚本频繁改」，这里要改成增量写。
  - **落盘失败时内存与磁盘会短暂不一致**（改动生效了但没存下来）。选择「如实报告」而不是
    「回滚内存」，是因为回滚要撤销一次已经广播出去的改动，代价远大于一条提示。
  - `MoveChannel.position` 是「前端算好的整数下标」，所以**客户端要懂一点树的几何**
    （落点判定、深度限制）。服务器仍然复核，但「拖到哪」这件事两边都有代码。
  - `proto3 optional` 的存在性语义被用来表达「不填 = 不改」。这让 `UpdateChannel` 一条消息
    能覆盖改名 / 人数上限 / 标志位三件事，代价是字段必须是 `optional`（不能靠 0 当哨兵）。

## 什么时候该重新考虑

- 频道数到几百、且结构改动变成高频操作 → 改成增量写（`save` 换成「按 id upsert + 删除缺失」）；
- 需要频道级 ACL（ADR-0016 的后路被触发）→ `channels` 旁边加 `channel_acl` 表，`save` 的粒度要重新设计；
- 需要「临时频道」（最后一个人离开自动回收）→ 它和「整棵树快照」相互影响，得先想清楚
  「服务器自己改结构」要不要也走一次全量写。
