# ADR-0015：上行门控（语音激活 / 按住说话 / 常开）的判据与代价

- **状态**：已定
- **日期**：2026-11-19
- **相关**：`docs/ADR/ADR-0005`（10 ms 帧）、`ADR-0007`（降噪待裁决）、`ADR-0010`（延迟分档）、
  `docs/UI设计-v0.1.md` §4.4；`docs/measurements.md` C-55；代码 `crates/audio-core/src/gate.rs`

## 背景

界面（`docs/UI设计-v0.1.md` §4.4）从一开始就画了三种说话方式：**语音激活**（默认）、
**按住说话**、**常开**。但在做 P6-2 之前，上行**没有任何门控**——麦克风一直在发，
三个按钮点了没用。这一条被写进了缺口表，而不是在界面里装样子。

要把它们变成真的，必须回答四个问题，每一个都不可逆（改了就要重测、重写文档）：

1. **判据是什么**：电平？VAD 概率？两者都要？
2. **预缓冲多长**：界面稿上写的是 300 ms（「不吃头一个字」）。
3. **静默期发不发东西**：完全不发，还是发点什么？
4. **默认值给谁**：命令行的默认值与产品默认值是不是同一个。

## 决策

### 1. 判据是「电平过门限 **且** VAD 概率过线」

两个判据同时成立才算「在说话」。理由是它们各自单独都不够：

| 只看 | 后果 | 实测（C-55，20 s 素材） |
|---|---|---|
| 电平 | 键盘、椅子、风扇全发出去 | 键盘 99.9% 开门、风扇 100% 开门 |
| VAD | 链上没有 VAD 时（`--chain none`）概率恒为 `1.0`，等于常开 | 直通档必须退化成只看电平 |

`1.0` 在 `Stage::process` 的契约里是「我没有意见」（`crates/audio-core/src/lib.rs`），
所以「VAD 概率 ≥ 0.5」这条判据在无 VAD 的链上自动成立 —— 降级是**同一个表达式**的结果，
不是一条特判分支。

### 2. 预缓冲 3 帧（30 ms），不是 300 ms

这是本条 ADR 里最容易被推翻直觉的一处。补发**不是**把音频延迟 300 ms 发出去，而是
「开门的那一刻，把攒下的几帧一次性塞进去」。所以它是一次**突发**：

```
开门瞬间 ──▶ 攒下的 N 帧 ──▶ 对方抖动缓冲
```

对方抖动缓冲的目标延迟是 20 ms、上限 60 ms（`--jitter-min/--jitter-max`），稳态深度
实测 20–36 ms（C-52）。**余量只有 25–40 ms = 2–4 帧**。补 30 帧的话，多出来的 260 ms
会被缓冲直接裁掉——白补，还白白污染抖动统计。

要真做到 300 ms 预缓冲，得改协议（在语音头里加一个「这是一段补发的突发，别裁」的标记），
那是另一个量级的改动，而且会把稳态延迟预算（ADR-0010 的 22.5 ms）撑破。**不做。**

所以：`PREROLL_MAX = 10` 帧是硬上限，默认 3 帧。界面上原来那句「配 300 ms 预缓冲」
是错的，已改成 30 ms 并写清代价。

### 3. 静默期仍然每 200 ms 发一个保活标记

完全不发会引出两个问题：

1. **对方的丢包率变成假数**。接收端按序列号空洞数丢包（`ReceivePath::note_seq`），
   5 秒静默 = 500 个空洞 = 「丢了 500 个包」。丢包率是这个项目里最不该说谎的数字。
2. NAT 映射会在静默期过期（UDP 打洞的常识）。

保活标记占一个序号（`Incoming::Silence { seq }`），接收端拿到它就把序号推过去**但不记账**
（`ReceivePath::note_keepalive`）。它同时喂给漂移前馈：那 20 个包**确实存在过**，只是没发，
所以「发包节奏」的估计不会被门控打乱（否则门控一开一关，pacing 就会抖出几千 ppm）。

代价：静默期约 1.6 kbps（一个约 40 B 的包 / 200 ms），实测 24 s 静默共 120 个保活、
上行 1.5 kbps（C-55）。相对常开的 46–60 kbps，仍然省了 97%。

### 4. 命令行的默认值是 `open`，产品默认值是 `vad`

同一个二进制，两个默认值，这是有意的：

- **命令行**的默认值被脚本和端到端测试依赖着。它们断言「每帧一个包」，换成语音激活会让
  它们挂在「没有收到包」上，而那个失败信息完全指不出原因。
- **产品**的默认值是语音激活（界面第一屏就是这个），它跟着 `ConnectRequest.voice` 一起下去，
  连接的第一帧就已经在门控之下，不需要用户去设置页点一下。

两边共用同一条实现（`run_with`），所以这不是两套行为，只是两个入口的默认参数不同。

## 备选与被否原因

| 方案 | 被否原因 |
|---|---|
| 只用电平（阈值可调） | 键盘/椅子/风扇都会被发出去，降噪档存在的意义就没了（C-55：键盘 99.9% → 0.0% 全靠 VAD） |
| 只用 VAD | 无 VAD 的链（`--chain none`）会退化成常开；而且 VAD 对稳态噪声并不可靠（见下面的「已知缺口」） |
| 预缓冲 300 ms（真延迟发送） | 稳态延迟 +300 ms，直接违反 ADR-0010 的分档；而且 ADR-0010 明确禁止单一数字承诺之外再加隐藏延迟 |
| 预缓冲 30 帧（一次性突发） | 超出对方抖动缓冲余量，多出来的会被裁掉（见决策 2） |
| 静默期完全不发 | 对方的丢包计数变成假数；NAT 映射会过期（见决策 3） |
| 单门限 + 无滞回 | 门限附近每帧翻一次：听感是嗡嗡的断续，而且每次都重新走编码器状态 |
| 把门控做在 `Capture` 里 | `Capture` 不知道用户选的是哪种说话方式，也不该知道；门控需要「电平 + VAD + 模式」三件事，只有 `app.rs` 的 tick 同时有 |

## 后果

- **好**：三种说话方式都是真的，行为可回放（`testkit gate` 一条命令就能复现判据）；
  静默期的丢包率仍然是真的 0；常开模式逐字节保持旧行为（默认值只改在界面入口）。
- **代价**：
  - 门控会让**别人的**抖动缓冲在开口的瞬间吃到一次 ≤3 帧的突发。这是可测的（`jitter_ms`
    会在开口那一刻抬一下），已在网络面板里可见。
  - 「按住说话」在命令行里没有键盘，只能验证「不按不发」。
  - 保活标记占用语音序号，所以报告里「最多 N 个是打点包占用的序号」这句话现在还要加上保活
    （`report()` 已经把两者分开打印）。
- **已知缺口（写在这里，不藏）**：
  - **VAD 对稳态宽带噪声不可靠**。合成素材上 RNNoise 的概率是：键盘 0.028、椅子 0.026、
    多人 0.015（都对），但**风扇 0.988、白噪声 0.587**（都错）。真人说话是 0.722。
    所以默认门限给得低（−50 dBFS）、让 VAD 干主要的活；风扇漏过去这件事只能靠用户把
    灵敏度往上推，或者用「按住说话」。这条与 C-18 是同一个结论的另一面：**合成素材判不了
    RNNoise 的门控行为**，要真实的风扇/空调录音才能定判据。已记入待办。
  - 门控只管「发不发」，不管「发什么」：常开模式下键盘声照样会出去（那是用户的选择）。
