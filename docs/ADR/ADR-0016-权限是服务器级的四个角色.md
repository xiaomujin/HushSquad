# ADR-0016：权限是服务器级的四个角色，不做按频道 ACL

- **状态**：已定
- **日期**：2026-11-19
- **相关**：`docs/权限与频道管理设计-v0.1.md`（完整方案）；`docs/proto/hushsquad-control-v1.proto`（`Perm`）；
  `GLOSSARY.md`（权限位 / 分组容器 / 子树）

## 背景

P7 要解决三件事：管理员在客户端里右键维护频道树、给其他人分配权限、越权不可能。
第三件决定前两件能不能做——**在这条 ADR 之前，`perms` 在服务器上没有任何一处校验**：
位图从数据库读出来、写进会话、下发给客户端，然后就再没被读过。也就是说那时候的
「右键删除频道」在协议上等于「任何人删任何频道」。

于是必须回答一个问题：**权限的作用域是什么**。

## 决策

1. **权限是账号级的全局位图**（`users.perms`，`u64`），不是每频道一份 ACL。
2. **四个内置角色**，展开成位图：服主（`OWNER`）/ 管理员（`ADMIN`）/ 协管（`MUTE_OTHERS|KICK|MOVE_ANYONE`）/ 成员（`JOIN_CHANNEL`）。
   角色只是位图的**命名组合**，库里存的是位图。
3. **不做按频道 ACL**，但留后路：位图只用了低 9 位，将来加 `channel_acl(channel_id, user_id, perms)`
   与「频道 ACL ∪ 沿树继承 ∪ 全局」的规则即可，协议字段不用改。
4. **权限必须比频道编辑先落地**（P7-1 早于 P7-2）。

## 备选与被否原因

| 方案 | 表达力 | 被否原因 |
|---|---|---|
| **A. 全局角色**（选中） | 能表达「他是管理员」，不能表达「他只是这个频道的管理员」 | — |
| **B. 按频道 ACL，沿树继承**（Mumble） | 最完整 | 每个频道一份 ACL 要同步给客户端、要做 ACL 编辑器、要定义继承与显式覆盖的优先级。Mumble 的 ACL 是「功能齐全但没人用」的典型：「谁能进这个频道」要打开三层对话框才能回答 |
| **C. 服务器组 + 频道组**（TeamSpeak） | 接近 B，心智模型更清楚 | 两套角色、两套 UI、两套存储，仍然要同步频道组；而且「给他权限」变成一道选择题，用户分不清两个「组」的区别 |
| 每频道存一份「频道管理员名单」，只给这一种特例 | 介于 A 与 B 之间 | 它只解决「谁能管这个频道的人」，不解决「谁能进这个频道」，却要引入与 B 相同的同步结构。真要跨过这条线，不如直接做 B |

选 A 的决定性理由不是「简单」，是**规模**：小队 5–20 人、频道 5–10 个、管理员 1–2 个。
在这个规模下，B 的表达力换来的全是维护成本。

还有一条只有实现者才会遇到的收益：**权限全局之后，客户端拿到自己的 `perms` 就能在本地决定
所有 UI**（菜单要不要出现、哪些项灰掉），不需要为每个频道回服务器问「我能在这里做什么」。
如果权限是按频道的，每一次渲染频道树都要向服务器查一次权限，或者把所有频道的权限都同步下来。

## 后果

- **好**：
  - 协议零改动就能开始（`AuthResult.perms` 与 `Perm` 枚举早就存在）；
  - 客户端不需要「按频道查权限」的往返，右键菜单纯本地计算；
  - 数据库不需要为权限做迁移（`users.perms` 已有列）。
- **代价**：
  - **做不到「这个频道只让某几个人进」**。要这个能力只能等 B。
  - 权限一改，影响的是这个人在**所有**频道里的能力。撤掉一个人的协管，他在每个频道都失去踢人权——
    这对小队场景是对的，对「多个社团共用一台服务器」是错的。
  - `u64` 的高位是留给未来的，所以**位定义一旦发出去就不能重排**（只能在末尾追加）。
- **两条防呆**（写进方案 §5，因为它们是权限系统唯一真正危险的地方）：
  - **授予的位必须是自己的子集**：管理员造不出服主，也给自己加不了权限；
  - **不能对权限比自己高的人做破坏性操作**：管理员踢不了服主。

## 什么时候该重新考虑

- 出现「一个频道只让某几个人进」的真实需求（而不是想象）；
- 管理员超过 3 个，且开始互相干扰（说明「全服管理员」这个粒度太粗）；
- 一台服务器被多个互不相关的社团共用。

任何一条成立，就按决策 3 的后路扩成 B，而不是在这条 ADR 上打补丁。
