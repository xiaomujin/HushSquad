## 重要限制（2026-11-16 起）

当前测试素材为**合成音频**（`testkit gen` 生成，随机种子固定），只能用于趋势与回归，**不能**用于：

- D6 盲听裁决（30 ms 延迟可接受性）；
- 技术设计 §11.2「降噪有明显压制」的终判；
- 「降噪不引入明显失真 / 不吞字」这类主观判断。

真实素材到位后的顺序：替换 `testdata/` → 重跑 P3-5 基线 → 才允许做 P3-6。

### 1.2 WASAPI 独占模式（P2-6，`apps/loopback --impulse --exclusive`）

动机：§1.1 把 198 ms 定位到播放侧。查注册表确认默认端点的 APO 链是 Realtek `RltkAPOU64`
（SFX/MFX/EFX 各一个）串 DTS APO3 `dtsapo3core64`（MFX/EFX 各一个），**共 5 个 APO**，
`DTSAPO3Service` 在跑。独占模式按定义不经过音频引擎与 APO，且不需要管理员权限
（改注册表关「音频增强」要提权）。

cpal 的公开 API 只有共享模式，所以直接对 `windows` crate 写 `IAudioClient`。三个卡点：

| 卡点 | 现象 | 结论 |
|---|---|---|
| 缓冲时长 | 传 0 或任意值 → `AUDCLNT_E_BUFFER_SIZE_ERROR`（0x88890016） | 必须是设备周期的整数倍 |
| `hnsPeriodicity` | `0` 在 3–96 ms 全档被拒（0x88890016）；取「一个周期」而缓冲两周期 → `AUDCLNT_E_BUFDURATION_PERIOD_NOT_EQUAL`（0x88890013） | **本驱动只接受 `periodicity == bufferDuration`** |
| 启动前预填 | 不预填时 `GetCurrentPadding` 恒等于缓冲大小、`available` 恒为 0，事件照来却一次都填不进去 | 必须先 `GetBuffer(整块)` → 填静音 → `ReleaseBuffer`，再 `Start()`（MSDN 的做法）；**且不能先查 padding**——`Start` 之前它会报错，一旦兜底成「满」就永远预填不进去 |

结果——**同一台机器、同一份代码，只换端点**：

| 端点 | FxProperties 值数 / APO | 独占流 | 实测 |
|---|---:|---|---|
| `扬声器 (Realtek(R) Audio)`（默认） | 153 / 5 个 APO | 建起来了，**不跑** | `Initialize` OK、`Start` OK，但 `IAudioClock::GetPosition` 恒为 0、`padding` 恒等于缓冲大小，2 s 内填充 **0** 次 |
| `Realtek Digital Output` | 149 / 同族 APO | 建起来了，**不跑** | 同上，填充 0 次 |
| `扬声器 (TOPPING USB DAC)` | 0 / 无 APO | **正常** | i16、288 帧（6.00 ms）缓冲、周期 144 帧、`GetStreamLatency` 6.00 ms；2 s 内填充 **313** 次（≈1878 ms 音频） |

**第一版结论是错的，这里是更正。** 当时把「独占不跑」归因给 APO 链，理由是「无 APO 的端点正常」。
但把该端点的音效增强关掉（`Disable_SysFx = 1`，已确认写入）之后**独占依旧不跑**，所以那个因果不成立。

真正的原因是**取用方式**：同一端点、同一份代码，

| 配置 | 结果 |
|---|---|
| `flags = EVENTCALLBACK`、`periodicity = bufferDuration` | Initialize/Start 都成功，设备不消费（填充 0 次） |
| `flags = 0`（轮询）、`periodicity = 0` | **正常跑**，512 帧缓冲，1 ms 定时器精度下 3 s 只欠载 ~500 样本 |

所以正确的表述是：**该端点的事件驱动独占不可用，轮询可用**；与 APO、与采样率（48 / 192 kHz 都试过）都无关。
这提醒一件事：`Initialize` 与 `Start` 返回成功**不等于流在跑**，必须看设备时钟是否推进。

> 工具侧已加 `--exclusive-mode auto|event|poll` 与「填充 0 次就报错」的判据，
> 并且测量期间把系统定时器精度提到 1 ms（默认 15.6 ms 会让轮询按 15 ms 的节奏喂料，必然欠载）。

### 1.3 延迟拆分：数字回环（P2-6 续，`--loopback`）

物理环回把「播放缓冲 + DAC + 空气 + ADC + 采集缓冲」揉成一个数，分不清该优化哪一段。
`--loopback` 在**播放设备上开 WASAPI 回环采集**（把渲染设备当输入用，cpal 自动开 loopback 模式），
拿到的是设备真正要播的那份数据，于是两段可以分开量。

前提：回环采集必须用端点**混音格式**（本机 192 kHz；传 48 kHz 直接 `AUDCLNT_E_UNSUPPORTED_FORMAT`），
所以渲染采样率也得跟着走——为此 `start_playout` 增加了 `preferred_rate` 参数。

| 日期 | 路径 | 端点 / 采样率 | 指标 | n | p50 | 极差 | 相关度 | 备注 |
|---|---|---|---|---:|---:|---:|---:|---|
| 2026-11-17 | 数字回环 | `扬声器 (TOPPING USB DAC)` / 48 kHz | 写入 → 设备输出 | 2 | 23.32 | 0.005 | 1.000 | 逐位一致，SNR 溢出 f32 |
| 2026-11-17 | 数字回环 | `扬声器 (Realtek(R) Audio)` / 192 kHz（无重采样） | 写入 → 设备输出 | 3 | 34.27 | 0.037 | 1.000 | 逐位一致 |
| 2026-11-17 | 数字回环 | 同上 / **渲染 48 kHz**（引擎 48→192 重采样） | 写入 → 设备输出 | 3 | 36.34 | 0.046 | 1.000 | 重采样只值 **2.07 ms** |
| 2026-11-17 | 物理环回 | Realtek → USB 麦 / 48 kHz | 写入 → 麦克风回来 | 5 | 175.29 | 0.899 | 0.68 | 音效增强**已关闭** |
| 2026-11-17 | 物理环回 | 同上，音效增强**开启** | 同上 | 5 | 198.29 | 0.714 | 0.68 | 关掉增强省 **23 ms** |

**独占模式的缓冲差分**（同一路径，只改设备缓冲，n=1 各）：

| 设备缓冲 | 实测延迟 | 相对上一档 |
|---|---:|---|
| 512 帧（10.67 ms） | 137.92 | — |
| 1536 帧（32.00 ms） | 159.40 | 缓冲 +21.3 ms → 延迟 +21.5 ms |
| 3072 帧（64.00 ms） | 191.57 | 缓冲 +32.0 ms → 延迟 +32.2 ms |

缓冲每加 X ms，延迟就加 X ms → **播放侧如实计入**；剩下的 ~127 ms 与播放缓冲无关，是常量。

由此得到拆分：

| 段 | 延迟 | 怎么量的 |
|---|---:|---|
| 我们的播放路径（写入 → 设备输出） | **23.3 ms**（TOPPING）/ **34.3 ms**（Realtek） | 数字回环，相关度 1.000 |
| 声学往返（写入 → 麦克风回来） | **175.3 ms** | 物理环回 |
| 差额 = 扬声器 → 空气 → 麦克风 | **~141 ms** | 上面两行相减 |

这 141 ms 不是音效链（采集端点 `fx=1`、没有任何 APO CLSID），也不是我们自己的缓冲
（差分实验已排除播放侧）。**还没拆开的唯一变量**：端点混音格式是 192 kHz 而我们按 48 kHz 跑，
中间隔着驱动的重采样。把该端点的默认格式改成 48 kHz 就能去掉它——一次点击的单变量实验。

> 结论：本机 D1 = **175 ms**，其中只有 34 ms 归我们的播放路径，**~141 ms 在输入方向（USB 麦克风）**。
> 这也解释了为什么关掉音效增强只省 23 ms：APO 在播放侧，而大头在采集侧。
> 对产品的含义：D1 的瓶颈是用户的麦克风，不是我们的处理链；客户端的延迟承诺必须按实测设备给，
> 不能假设「软件够快就够了」。

#### 1.3.1 那 141 ms 不是重采样（`--render-rate` 实测）

端点混音格式是 192 kHz，而我们的流是 48 kHz，中间隔着引擎（共享）或驱动（独占）的重采样。
用 `--render-rate 48000` 让**渲染**留在 48 kHz、**回环采集**仍锁在 192 kHz，就能单独量出它的代价：

| 数字回环的渲染采样率 | 延迟 | n | 极差 |
|---|---:|---:|---:|
| 192 kHz（不重采样） | 34.27 ms | 3 | 0.037 |
| 48 kHz（引擎 48→192） | **36.34 ms** | 3 | 0.046 |

**重采样只值 2.07 ms。** 于是：

| 段 | 延迟 |
|---|---:|
| 声学往返（渲染 48 kHz） | 175.29 ms |
| 数字回环（渲染 48 kHz，同一渲染路径） | 36.34 ms |
| **差额 = DAC 模拟 + 空气 + 麦克风** | **138.95 ms** |

DAC 模拟与空气合计约 1–2 ms，所以 **~137 ms 是这只 USB 电容麦的输入延迟**。
它不出现在 Windows 的 APO 列表里（采集端点 `fx=1`、无 CLSID），是设备固件/驱动的内部缓冲。

> 这条把 C-12 收紧了：**D1 的 175 ms 里，139 ms 是麦克风，34 ms 是我们的播放路径，2 ms 是重采样。**
> 也就意味着改系统默认格式（192 kHz → 48 kHz）**不值得做**——最多省 2 ms。

#### 2.1 AGC2 的电平行为（P3-1，release，`codec=none`，20 s 素材）

| 素材 | 输入 RMS | 输出 RMS | 增益 | 稳态峰值 | 被钉在 \|x\|>0.99 的样本 |
|---|---:|---:|---:|---:|---:|
| `clean` | -19.26 dBFS | -17.74 | **+1.52 dB** | -5.5 dBFS | 57（0.006%） |
| `fan` | -19.39 | -19.89 | **-0.50 dB** | -11.2 dBFS | 11（0.001%） |
| `babble` | -21.11 | -18.83 | **+2.28 dB** | -7.2 dBFS | 33（0.003%） |

三段素材本身就在合适电平上（-19 dBFS RMS ≈ 正常说话音量），所以 AGC2 基本「不动手」（±2 dB 内），
稳态峰值留在 -5 ～ -11 dBFS、没有顶满量程——这是想要的行为。

**开场瞬态（已知缺陷，待裁决）**：WebRTC 默认 `initial_gain_db = 15`，而增益下降速率上限是 6 dB/s，
所以每路流的**头 1–2 s** 会比稳态响一截：

| 时段（`clean`） | RMS |
|---|---:|
| 第 1 秒 | **-11.2 dBFS** |
| 稳态（3 s 后） | -19.2 dBFS |

即 **+8 dB 的开场爆音**，峰值被限幅器顶到满量程（全片 57 个样本被钉在 \|x\|>0.99）。
备选是把 `initial_gain_db` 设为 0——单元测试 `zero_initial_gain_removes_the_startup_burst` 证明
瞬态消失，代价是安静麦克风开头几秒偏轻（6 dB/s 爬升）。取舍需要真实语音素材做盲听，归入 P3-6 / D6，
**当前保持 WebRTC 默认**，并由 `default_initial_gain_causes_a_bounded_startup_burst` 把行为钉住。

#### 2.2 RNNoise 的电平行为（P3-2）——**不能用来判断音质**

| 素材 | 输入 RMS | `rnn` 后 | Δ | `highpass,rnn,agc2` 后 | Δ |
|---|---:|---:|---:|---:|---:|
| `clean`（合成元音） | -19.26 dBFS | -21.72 | **-2.46 dB** | -18.78 | +0.48 dB |
| `fan`（风扇） | -19.39 | -32.18 | **-12.79 dB** | -26.06 | -6.66 dB |
| `keyboard`（键盘） | -26.39 | -27.17 | **-0.79 dB** | -25.08 | +1.31 dB |
| `babble`（多人） | -21.11 | -21.66 | **-0.55 dB** | -37.25 | -16.14 dB |
| `noise_only`（纯噪声） | -10.79 | -13.20 | **-2.41 dB** | -11.67 | -0.88 dB |

逐秒看更清楚（`clean`，`rnn` 单跑）：-19.4 / -19.2 / -21.7 / **-70.3** / -39.7 / -43.2 / -41.5 / -22.1 dBFS。
也就是说：合成元音在第 3 秒被**几乎完全门控掉**（-70 dBFS），第 8 秒才回来。

**这条不能读成「RNNoise 不行」**，只能读成「合成素材不能用来判音质」：

- `clean` 是 `testkit gen` 用三个共振峰 + 音节包络合成的元音，没有辅音、没有音高变化、没有真实录音的房间与口型；
- RNNoise 的 VAD 与增益是拿**真实语音**训练的，对这类信号的判决没有代表性；
- 高通前置会显著改变门控行为（同一段 `babble`：不加高通 -0.55 dB，加高通后 -16 dB）——说明判决对频谱细节极敏感；
- 真实语音素材目前没有（ADR-0007 的阻塞项），所以**音质结论必须等 D6 盲听**。

工程上能从这张表拿到的只有两件事：

1. **电平不能靠降噪器**：它的门控可以到 -40 dB，也能基本不动（-0.6 dB）。电平由后面的 AGC2 负责，这也是设计顺序「降噪 → AGC2」的理由之一；
2. **环节顺序要钉死**：`highpass` 在 `rnn` 之前还是之后，门控结果差 15 dB 以上。顺序写进技术设计 §6.2，并由 `ChainDesc` 显式表达。

## 3. 丢包与鲁棒性

### 3.1 丢包矩阵（P4-3，`testkit loss-matrix`）

配置：素材 `clean` 6 s（600 帧）、Opus 32 kbps / 10 ms 帧、抖动缓冲目标延迟上限 20 ms、
种子 42（同种子逐位复现，见 `crates/testkit/src/lossmatrix.rs`）。

参考信号**不是**原始素材，而是「同一素材、同一编码器、无损网络下的往返结果」——否则 32 kbps
本身的 17.5 dB 会把丢包的损伤淹掉。这样 SNRseg 只反映网络损伤。

**PLC 模式（现状：丢包交给 NetEQ 的 `expand` 外推）**

三条读法：

1. **0 % 丢包时输出与参考逐样本相同**（全局 SNR 200 dB = 零误差，`energy_err_db = 0.00`）。
   这是测量管线的自检：参考走「编码即解码」，输出走「编码 → 抖动缓冲 → 解码」，两条路在
   无损网络下必须重合。它红了就说明是管线坏了，不是丢包。
2. **PLC 在 3 % 就开始塌**：SNRseg 从 35 → 26.3 dB，帧能量误差 0.04 → 1.22 dB。10 % 时
   SNRseg 9.86 dB，已经不是「音质下降」而是「听不清」。
3. **冗余把 5 % 从 21.0 dB 拉回 34.0 dB、10 % 从 9.9 dB 拉回 30.2 dB**，代价是线上码率
   32.2 → 64.3 kbps。1 %/3 % 下两列完全相同，是因为该种子下没有任何一帧的两份副本同时丢
   （3 % 时期望的双丢包数 ≈ 600 × 0.0292² ≈ 0.5，落在 0）。

**指标口径与已知局限（重要，别把这张表读成感知分数）**：

- **SNRseg 不是感知分数**。PESQ/POLQA 是授权算法，没有可信的离线 Rust 实现；自己拍一个
  「感知分」等于伪造结论。SNRseg 比的是**波形**，对丢包引入的爆音、断续、金属声只是间接敏感。
  「可听性」的判决仍然阻塞在 D6 盲听（C-18）。
- **高丢包下 SNRseg 应当读作保真度下界**。NetEQ 丢包后先 `expand`（插一帧）再 `accelerate`
  （抽掉几毫秒），块内的时间轴不再是常数，逐块对齐必然有残余错位；而 1 kHz 在 48 kHz 下偏 5
  个样本就是 37° 相位。`对齐极差` 那一列就是这个置信度：0 ms 时可信，73 ms 时只能当下界看。
  所以同时给了**帧能量误差**（10 ms 能量差的均值），它对齐不敏感，是更稳的那一列。
- **抖动缓冲深度峰值始终 ≤ 20 ms**（NetEQ 自报 `current_buffer_size_ms`），说明 `对齐极差`
  不是延迟真的涨了，而是对齐估计在损伤下变不确定。这一条同时验证了附录 A 第 9 行的 L2 预算
  （15–20 ms）在 10 % 丢包下仍然守得住。

### 3.2 Opus in-band FEC 接不上 NetEQ（结论，不是猜测）

选型报告 §2.6 把 in-band FEC 当成弱网的第一道防线。实测**接不上**：

- `neteq` 的 `AudioDecoder` trait 只有 `decode(encoded) -> Vec<f32>`，没有 FEC 入口；
- Opus 的 in-band FEC 要求「丢包时用**下一包**解出当前帧」，产出的是 **PCM**；
- 而 NetEQ 要的是**包**才能排进它自己的播放队列（序号、时间戳、时间伸缩都基于包）。

要接上只有两条路：改 `neteq` 的 trait（fork 或上游 PR），或者放弃它的时间伸缩自己写抖动缓冲。
两条都不是「顺手」的量级。**所以 P4-3 先用「包级冗余」量出弱网能买到多少 dB（上表），再决定
要不要为 FEC 动 neteq**——如果 5 % 丢包下冗余已经把 SNRseg 顶到 34 dB，动 neteq 的动力就很小。

冗余与 FEC 的差别只有一个：冗余恢复出来的是一份**真包**（能直接塞进 NetEQ），FEC 恢复出来的
是 PCM。在 0 抖动的模型下两者恢复概率相同（1 − p²），所以这张表的冗余列可以当作 FEC 的
**上界估计**。

### 3.3 时钟漂移长跑（P4-4，`testkit drift-run`）

抖动缓冲吸收的是**网络抖动**（零均值）；**时钟漂移**是单调的。48 kHz 晶振 ±100 ppm 意味着每小时
0.36 s 的账，只有连续开两小时会议才会显形——所以这一项必须是长跑，且必须能离线重跑。

配置：虚拟时钟（无 `sleep`，一个 tick = 10 ms 虚拟时间）、4 小时 = **1 440 000 帧**、1 kHz 单音
（−12 dBFS，Opus 32 kbps / 10 ms 帧）、目标延迟夹在 **15–20 ms**、PCM 环 8 帧。漂移注入在
**发送侧**：每过一个播放 tick，发送方产生 `480 × (1 + ppm×10⁻⁶)` 个样本，序列号与时间戳都按
发送方的样本计数走——对抖动缓冲来说这就是「包来得比消耗快/慢」。

| 注入 | 两端样本差 | 时间压缩 | 时间拉伸 | 稳态缓冲深度 | 摆动 | 爬升 | 下溢 | 硬跳变 | 判定 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 0 ppm | 0 | 0 | 0 | **14.00 ms** | 0.00 | +0.00 | 0 | 0 | **通过** |
| +100 ppm | +69 120（+1440 ms） | 67 708 | 0 | **36.76 ms** | 13.92 | +0.05 | 0 | 0 | **不通过** |
| −100 ppm | −69 600（−1450 ms） | 0 | **0** | **12.94 ms** | 16.00 | +0.20 | 0 | 0 | **不通过** |

四小时里没有一次下溢、没有一次硬跳变（最大一阶差分 0.0359，平滑正弦的解析上界 0.0327——多出来
的那点是 Opus 量化噪声），**样本守恒的账也基本对得上**（见下）。所以「管线本身没问题」这条
自检成立；不通过的是漂移这一项。

**读法一：0 ppm 是根定海神针。** 4 小时里缓冲深度**一次都没动过**（14.00 ms，极差 0），压缩、
拉伸、PLC 全为 0（PLC 那 960 样本全发生在起播的 2 秒内）。这条同时是测量管线的自检：如果这里
不平，后面的数字都不用看。

**读法二：正向漂移不是「没补偿」，而是「补偿在错误的水平上」。** 4 小时累计多出 69 120 样本
（1.44 s），NetEQ 通过时间压缩吃掉了 **67 708** 个（98 %）——它确实在补偿。代价是它把缓冲
**稳在 36.76 ms**：`33 → 44 ms` 的锯齿，周期约 60 秒，每次压缩约 9.8 ms。9.8 ms ÷ 60 s ≈
163 ppm，比注入的 100 ppm 多出 63 %，所以锯齿必然过冲。相对附录 A 第 9 行的 15–20 ms，这等于
**凭空多付 17 ms 延迟，且延迟本身在 ±6 ms 内来回摆**。

**读法三：反向漂移根本没有补偿机制。** 4 小时里 `inserted_samples_for_deceleration` 是 **0**——
一次预拉伸都没有。缓冲在 `5 → 21 ms` 之间以 8 分钟为周期乱走（均值 12.94、摆动 16.00），靠的是
**194 次 PLC 外推**（NetEQ 自报 93 120 样本，按守恒推导实际造出 68 928 样本，约 1.44 s 的音频
是「编」出来的）。它没有爆音、没有下溢，但 5 ms 的谷底意味着**任何一点网络抖动都会直接打成
欠载**——这个测试里没有抖动，所以看不出来。

**根因（读 `neteq` 0.9.1 源码，`src/neteq.rs::get_decision`）**：

- 压缩阈值 `high_limit = max(target, low_limit + 20 ms)`，而 `low_limit = max(target×3/4, target − 85 ms)`。
  target = 20 ms 时：`low = 15 ms`、**`high = 35 ms`**、快速压缩（`fast accelerate`）在 `4×high = 140 ms`。
  **那个「+20 ms」是常数**，所以把 target 调到多低，阈值永远是 target + 20 ms——调参绕不过去。
- 预拉伸（`PreemptiveExpand`）额外要求 `当前缓冲 ≥ 3 帧 = 30 ms`。20 ms 的预算里这个条件**永远
  不成立**，所以负向是结构性缺失，不是调参问题。
- `K_BASE_MIN_DELAY_MS = 20`：这个移植版把最小延迟硬编码成 20 ms，`set_minimum_delay(15)` 压不下去。
- 这不是 bug，是**设计取舍**：该 crate 自己的测试 `test_continuous_streaming_buffer_convergence`
  明确断言「20–40 ms 的缓冲只应发生极少的加速」——它按浏览器 80 ms 的 target 调参，而我们的
  预算是 20 ms。

**结论：NetEQ 的自适应延迟不能当作漂移补偿器用。** 技术设计 §6.6 与 §13 里那条「NetEQ 是否
已实现漂移补偿——**待验证**」，现在答案是：**实现了，但它的工作点在我们预算之外**。
→ 触发**对策 D**（执行方案 §11）：外层自建「按缓冲深度微调」的补偿器，见 P4-6。

**守恒账为什么是区间而不是等式**：`neteq` 的 `concealed_samples` 把 Expand 的**整个输出帧**都
记成隐藏样本，而 Expand 实际会先吃掉一部分真音频、只外推剩下的一小段，所以它只是**上界**
（−100 ppm 这一跑：自报 93 120，推导 68 928，高报 25 %）。因此判据写成
`0 ≤ 推导值 ≤ 自报值`（±1 帧容差），而不是「两者相等」。0 ppm 与 +100 ppm 两跑的推导值分别是
0 和 −480（一个帧边界内的取整误差）。

**已知局限**：① 单音素材只用来暴露「拼接」与「缓冲见底」，判不了音质（C-18 同理）；② 没有叠加
网络抖动——真实弱网下漂移与抖动同时存在，缓冲谷底（5 ms）会比这里危险得多，这一项要等 P4-6
做完补一次「抖动 + 漂移」联合长跑。

**复现**（release，三跑串行约 15 分钟；并行跑三份约 5 分钟）：

```powershell
cargo run -p testkit --release -- drift-run --hours 4 --ppm 0    --out testdata/drift-0ppm.json
cargo run -p testkit --release -- drift-run --hours 4 --ppm 100  --out testdata/drift-p100ppm.json
cargo run -p testkit --release -- drift-run --hours 4 --ppm -100 --out testdata/drift-n100ppm.json
```

同参数逐位复现（有测试钉住）。输出里的 `结论：` 段就是四条判据的机器判决，不是人眼看的。

### 3.4 漂移补偿（P4-6 / 对策 D）——正反两向都成立，抖动链路上会做无效功

§3.3 的结论是「NetEQ 的补偿工作点在预算之外」，所以补偿器只能自己做。做的过程里先推导出一条
**决定了整个结构**的关系：

> 抖动缓冲深度每 tick 的变化 = `480(1+ε) − 480×pulls`。
> 也就是说 **B 只受「这一 tick 从抖动缓冲拉了几帧」影响**——丢样本、补样本、改重采样比，对 B
> 一点作用都没有。而音频侧每 tick 固定取走 480 个样本，所以每 tick 也必须写进 480 个。

于是执行器被分成两个：**丢/补样本**改变「总延迟」，**拉包次数**改变 B 与 PCM 环之间的分配。
稳态解唯一：`slip = 480ε`、`pulls = 1+ε`。对策 D 原来写的「微调重采样比」也走同一条路，但它
多付了插值延迟、CPU 与每帧分配，换来的只是拼接更平滑——而拼接可以用 1.33 ms 等功率交叉淡化
压到 `max_step` 测不出来。所以改成丢/补样本。

**一个控制环就够。** 环不漂的条件是 `Σslip = 480 × Σ(pulls − 1)`，所以拉包次数被丢/补样本
唯一确定。把「PCM 环低于一帧就多拉、高于两帧就少拉」当成规则，它的**平均**拉包率自动等于
`1 + slip/480`——也就是漂移量本身。

**结构上改了三次才立住，三次都测出了具体数字，不是猜的**：

1. **「少拉一帧」必须一个样本都不写。** 第一版写成「回放上一帧」（环水位不变），于是反向漂移
   时补样本抬高环，而没有任何动作能把它降下来——环只会一路涨到溢出。4 小时实测：缓冲均值
   55.84 ms、峰值 197 ms，补偿器丢了 1 215 935 个样本（该补的地方在丢）。改成写 0 之后，那一
   帧由 PCM 环里的存货顶上，完全透明（环本来就是连续样本流，不写就是不写，没有拼接）。
2. **环水位必须如实从 0 记账。** 给过「一帧垫子」，等于让估计值比真实水位高 480：于是「环太满
   就少拉」在真实水位只有一帧时就触发，反向把环抽干、队列推到 18 包。
3. **两个环不能同时改同一个量。** 「信用」和「环水位阀门」都去改 `credit` 时，两者互相追：
   4 小时环涨 136 473 个样本、溢出丢 35 733 个（**静默丢音频，比爆音难查得多**）。

**实测（4 小时虚拟时间，`testkit drift-run --hours 4`，对照是 `--no-compensate`）**：

| 注入 | 补偿 | 稳态缓冲深度 | 摆动 | 爬升 | 下溢 | 硬跳变 | 最大一阶差分 | 判定 |
|---|---|---:|---:|---:|---:|---:|---:|---|
| 0 ppm | 关 | 14.00 ms | 0.00 | +0.00 | 0 | 0 | 0.0359 | 通过 |
| 0 ppm | **开** | **12.00 ms** | 0.00 | +0.00 | 0 | 0 | 0.0483 | 通过（4 小时丢 218 个样本 = 3 ppm、补 0） |
| +100 ppm | 关 | 36.76 ms | 13.92 | +0.05 | 0 | 0 | 0.0359 | 不通过（§3.3） |
| +100 ppm | **开** | **12.19 ms** | 10.00 | −0.00 | **0** | **0** | 0.0484 | **通过** |
| −100 ppm | 关 | 12.94 ms | 16.00 | +0.20 | 0 | 0 | 0.0359 | 不通过（§3.3） |
| −100 ppm | **开** | **17.81 ms** | 10.00 | +0.00 | **0** | **0** | 0.0482 | **通过** |
| +100 ppm ＋ 抖动 0–10 ms ＋ 丢包 0.5 % | **开** | 14.27 ms | 45.00（网络） | −0.01 | **0** | **0** | 0.0494 | 通过（不判摆动） |

**正向（发送方快）**：4 小时丢 68 858 个样本（= 1.43 s，等于漂移 69 120 减去几帧取整），多拉
147 帧，环水位只动 262 个样本且一个都没丢；0 下溢、0 PLC、0 硬跳变、0 软跳变，`max_step` 0.0484
（平滑上界 0.0327 的 1.48 倍）。相对 §3.3 的 36.76 ms **省回 24.6 ms**。

**反向（发送方慢）**：补 67 428 个样本、少拉 142 帧、环水位只动 10 个样本，稳态 17.81 ms、
摆动 10.00 ms、0 下溢、0 硬跳变。**这是 C-35 那个缺口的关闭**：原来 1 215 935 个样本的乱丢没了，
现在只有 218 个，而且方向正确（该补的时候在补）。

**0 ppm 下几乎逐样本透明**：4 小时只丢 218 个样本、一个都没补，`fabricated` 为 0。这条很重要：
它说明补偿器不会在正常链路上偷偷改音频。

**摆动 10 ms 是物理下限，不是控制精度**：抖动缓冲按整包计量，一包 = 480 样本 = 10 ms，
「1 包」与「2 包」之间必然跳一档。要求 < 10 ms 等于要求它停在半个包上。

**联合长跑（抖动 ＋ 漂移）**：这是 §3.3「已知局限 ②」要求补的那一跑，也是**唯一一条把补偿器的
弱点照出来的跑法**。四条判据全过（均值 14.27 ms、趋势 −0.01、0 下溢、0 硬跳变、守恒成立），
但它**在做 26 倍的无效功**：一小时丢 178 k、补 265 k 个样本，而真正的漂移只有 17 k。根因是传感器
——排队包数同时被漂移（直流）和抖动（交流）推动，而 200 ms 的 EMA 滤不掉 10–100 ms 的抖动，
控制器于是每 tick 都饱和在 ±`MAX_SLIP`。**正确的修法不是把 EMA 放慢**：闭环特征方程是
`s² + αs + kp = 0`，α 必须 ≥ 2√kp 才不振荡；实测 α = 0.0005、kp = 0.02 时 Q ≈ 283，反向 4 小时
里丢 30 918、补 40 635 个样本，两个方向在对打。该换的是**传感器**：漂移可以从
`Δ序号 / Δtick − 1` 直接量出来，这个比值对抖动和丢包都免疫，量出来就是 ε，不需要反馈环去猜。
那需要网络层把序号喂进来，属于 P5 的接线范围（C-37）。

**已知局限（写清楚，别当它没有）**：

1. **抖动链路上做无效功**（C-37）：**仍然开着**。前馈传感器（`Δ序号 / Δtick − 1`）已经接上，
   但实测发现两件事：（a）这份「抖动」主要来自我们自己两个进程的 10 ms 相位差，不是网络
   ——本机 127.0.0.1 回环（RTT 0.1 ms、0 丢包）照样每秒做 74 个样本的无效拼接；（b）这份无效
   工作**正在替延迟预算兜底**。0 ppm + 10 ms 抖动下：默认参数 17.8 ms（在预算内）、
   EMA 0.005 / kp 0.005 → 30.6 ms、死区 0.25 包 → 30.5 ms、关掉补偿 → 28.8 ms，后三个都顶出
   15–20 ms 预算。也就是说「延迟达标」是过度补偿的副产品。要真正关掉它，得先修
   `jitter.rs` 一侧「NetEQ 为什么停不在 20 ms 目标上」，那是另一件事。
   （c）**序号前馈已经实现并量准了，但接进控制环会让 +100 ppm 的四小时长跑从绿变红**：
   稳态缓冲深度 12.19 → 28.11 ms、多拉/少拉帧 147/1 → 36 603/36 458（一个 ~20 tick 周期的极限环）。
   「净」量两边都对（丢减补 = 漂移本身），但前馈是不经过传感器的直流偏置，叠在 PCM 环水位的
   继电规则上就让环在两边界之间撞。所以 `DriftConfig::feedforward` 默认 **false**，代码与测量都留着，
   单元测试钉住估算精度（0/±100 ppm 下误差 < 20 ppm）。
2. **环水位是记账估出来的**（`ring_level += 写出 − 480`），不是读环；守恒判据的容差因此是
   4 帧。它抓的是「成百上千帧凭空消失」，不是精密对账。
3. **摆动判据只在干净链路上成立**：抖动一来缓冲的上下摆是 NetEQ 在追抖动（3–48 ms），那是网络的
   性质。所以 `violations()` 在有抖动时跳过这一条，靠均值/趋势/下溢/硬跳变四条兜底。
4. **补偿器依赖 `packets_queued`**（NetEQ 排队的包数），这是 `neteq` 暴露的内部量；换抖动
   缓冲实现时这个接口要重新找。
5. **「样本守恒」判据只在有丢包时是紧的**。它要求「推导出来的造样本数」落在
   `[0, NetEQ 自报的 PLC 样本数]` 之间，而那个上界主要来自丢包隐藏：0.5 % 丢包下上界是 979 680，
   零丢包时上界掉到 ~1 920。于是「+100 ppm + 10 ms 抖动 + **零丢包**」这一组无论开不开补偿都判不过
   （开补偿 +9 504、关补偿 −8 368）。也就是说这条判据量的是「丢包隐藏的记账口径」，
   不是「漂移补偿有没有凭空造样本」；历史那几次绿是 0.5 % 丢包给的大上界兜着的。

### C-51 等功率交叉淡化在每个拼接点上抬 +3 dB —— 听感「空旷 + 失真」的直接原因

真机 281.6 s 回环（LAN，RTT 0.1/0.2 ms，真丢包 0）的客户端汇总：**混音峰值 1.404、软限幅 1315 样本**，
而发送端的采集峰值只有 0.950。`1.404 / 0.993 ≈ √2` —— 这不是巧合，是等功率权重的中值。

`splice()` 用 `(cos θ, sin θ)`。`cos² + sin² = 1` 保证的是**功率**守恒，只有在两路信号**不相关**
（功率相加）时才等于**幅度**守恒。这里的两路是同一路信号错开 1–2 个样本，相关系数 ≈ 1，
中点是 `cos 45° + sin 45° = √2`：每次拼接都是 1.33 ms、+3 dB 的幅度凸包。
拼接密度实测每秒 74–104 个样本（本机 90 s A/B：6674 / 90 ≈ 74；用户日志 29 185 / 281.6 s ≈ 104），
每次只动 1–2 个样本，折算下来**每秒几十次**，听感上就是「空旷、发飘、有点失真」。

**门禁为什么没抓到**：`max_step` 量一阶差分，而 +3 dB 凸包是**平滑**的（64 个样本升上去再落回来，
逐点差分只有 `2πAf/F` 量级），一阶差分判据对它天然失明。这条值得单独记：「`max_step` 通过」
不等于「波形没被改动」。新增的判据是**幅度守恒**（`a_splice_keeps_the_level`）。

改法：等增益权重 `(1 − w, w)`，两路相同时恒等于 1，与相关性无关。

| 测量 | 改前 | 改后 |
|---|---:|---:|
| 0.25 幅度单音的混音峰值（3 进程真链路 90 s，同一台机器） | 0.360（+3.17 dB） | 0.257（+0.23 dB） |
| `slip` 拼接样本数（同上） | 6674 | 6713（不变，C-37 仍在） |
| `max_step` / 平滑上界（testkit，0 ppm + 10 ms 抖动） | 1.47 | 1.10 |
| `testkit drift-run` 稳态缓冲深度（同上） | 17.81 ms | 17.81 ms（无变化） |

真机上那个 1.404 应当回到 ~0.99：软限幅不再被音频本身触发（`clip` 应从 1315 掉到 0）。

### 5.1 单包固定开销（release，100 B 载荷，7 轮取中位数）

复现：`cargo run -p testkit --release -- p5-bench --out testdata/p5-bench.json`

| 项 | 耗时 | 说明 |
|---|---:|---|
| HKDF-SHA256 派生一对方向密钥 | **606 ns** | 每会话每 `key_epoch` 一次，不在热路径 |
| ChaCha20-Poly1305 封装（100 B） | **1.33 µs** | |
| ChaCha20-Poly1305 解封 + 校验（100 B） | **1.32 µs** | |
| 20 B 头解析 + 长度自洽 | **1.3 ns** | 纯字段搬运，比一次缓存未命中便宜得多 |
| 滑动窗口判定一次 | **0.86 ns** | 一次有符号比较 + 一次位运算 |
| **fan-out 到 7 个听众（单包）** | **12.47 µs** | 含客户端封装 1 次 + 服务器 7 次封装 + 7 次缓冲拷贝 |

推论：8 人同频道、每人 100 pps 时，服务器每 10 ms 处理 8 个入站包、每个 fan-out 7 份，
合计 **99.8 µs / 10 ms = 单核的 1.0 %**。密码学不是这套东西的瓶颈 —— 它是每包 1.33 µs
的固定成本，而抖动缓冲与降噪是每帧 0.4–1.6 ms 的变量成本（§2）。

**基准自检**：报告里的 `fanout_copies_per_packet` 必须等于听众数。第一次跑出来是
`1.0` 而不是 `7.0` —— 因为虚拟时钟每轮从 0 重启，第二轮起全部被判「超速」，
量到的是丢弃路径。这类错误只有自检能抓到，光看耗时数字看不出来（1.33 µs 和 12.47 µs
都在「合理」区间里）。

### 5.4 实装中发现并修掉的五个问题

写代码之前这些都不在计划里。它们都是**规格里没写、只有写下去才会撞到**的东西：

1. **fan-out 复用同一块 scratch 原地加密** → 第二个收包人拿到的是双重加密的垃圾。
   原地加密的 API 天生要求「每一轮都从明文重新拷一份」，这一条不写在文档里就一定会踩。
2. **服务器不校验头里的 `sender_id`** → 任何成员都能让服务器替自己转发一条
   「看起来是别人说的」语音。接收端按 `sender_id` 区分说话人，所以这是**冒充**。
   修法是在 AEAD 之后加一道比对（放在 AEAD 之前会把线路噪声误记成冒充）。
3. **`channel_epoch` 每频道各自计数** → 两个频道会撞到同一个 epoch，
   「跨频道包被拒」这条安全性质形同虚设。改成**服务器全局单调**。
4. **校验顺序**：协议草案写「窗口去重 → AEAD」，但 `seq` 在明文头里 ——
   先更新窗口等于给伪造源地址的攻击者一个「把窗口推走」的把手，随后到达的合法包
   全被判「太老」。改成 **AEAD → 窗口**，代价是每包多一次 1.33 µs 的校验。
5. **服务器自己发的包会复用 nonce**：BindAck / ProbeAck 的 `sender_id` 都是 0，
   重绑定两次就是同一个 `(key, nonce)` 加密两条不同消息 —— ChaCha20-Poly1305 下这是
   可恢复明文的灾难。修法是每条会话一个独立的 `server_seq`，且有测试钉住。

### 5.5 没测什么

- **4G / 热点切换的 2 秒重绑**：本机环回上验证了「同 token 从新 socket 重绑后立刻可用、
  旧 socket 立刻失效」，但没有真实网络路径与 NAT 超时；
- ~~**TLS 1.3 控制面**~~：**已接**（`rustls` 0.23 + `tokio-rustls`，证书从 PEM 读）。

  任何一处不一致都会让 BindAck 解不开；

**定时器粒度**（同一台机器，同一份代码，只差一次 `timeBeginPeriod(1)`）：

| 配置 | tick 频率 | 3 秒上行帧数 | 接收端缓冲 |
|---|---:|---:|---:|
| 不调（Windows 默认 15.6 ms 粒度） | **64 Hz** | 193（应为 300） | 20 ms 目标 → **涨到 95 ms** |
| `timeBeginPeriod(1)` | **100.0 Hz** | 302 | 稳定在 56 ms（= 上限 − 4） |

不调的时候不是「稍慢」：每秒只发得出 640 ms 的音频，而网络仍按 100 帧/秒灌进来，
抖动缓冲**单调上涨**。这类故障在报告里只会表现为「缓冲有点高」，所以客户端把实际 tick 频率

默认间隔因此定为 5 秒（30 分钟通话 ≈ 360 个样本、0.2 % 虚报），报告里也把「最多 N 个是打点
占用的序号」写在同一行。
