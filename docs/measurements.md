当前测试素材为**合成音频**（`testkit gen` 生成，随机种子固定），只能用于趋势与回归，**不能**用于：

### 1.2 WASAPI 独占模式（P2-6，`apps/loopback --impulse --exclusive`）

动机：§1.1 把 198 ms 定位到播放侧。查注册表确认默认端点的 APO 链是 Realtek `RltkAPOU64`
（SFX/MFX/EFX 各一个）串 DTS APO3 `dtsapo3core64`（MFX/EFX 各一个），**共 5 个 APO**，
`DTSAPO3Service` 在跑。独占模式按定义不经过音频引擎与 APO，且不需要管理员权限
（改注册表关「音频增强」要提权）。

cpal 的公开 API 只有共享模式，所以直接对 `windows` crate 写 `IAudioClient`。三个卡点：

| 卡点 | 现象 | 结论 |
|---|---|---|
| 缓冲时长 | 传 0 或任意值 → `AUDCLNT_E_BUFFER_SIZE_ERROR`（0x88890016） | 必须是设备周期的整数倍 |
| `hnsPeriodicity` | `0` 在 3–96 ms 全档被拒（0x88890016）；取「一个周期」而缓冲两周期 → `AUDCLNT_E_BUFDURATION_PERIOD_NOT_EQUAL`（0x88890013） | **本驱动只接受 `periodicity == bufferDuration`** |
| 启动前预填 | 不预填时 `GetCurrentPadding` 恒等于缓冲大小、`available` 恒为 0，事件照来却一次都填不进去 | 必须先 `GetBuffer(整块)` → 填静音 → `ReleaseBuffer`，再 `Start()`（MSDN 的做法）；**且不能先查 padding**——`Start` 之前它会报错，一旦兜底成「满」就永远预填不进去 |

结果——**同一台机器、同一份代码，只换端点**：

| 端点 | FxProperties 值数 / APO | 独占流 | 实测 |
|---|---:|---|---|
| `扬声器 (Realtek(R) Audio)`（默认） | 153 / 5 个 APO | 建起来了，**不跑** | `Initialize` OK、`Start` OK，但 `IAudioClock::GetPosition` 恒为 0、`padding` 恒等于缓冲大小，2 s 内填充 **0** 次 |
| `Realtek Digital Output` | 149 / 同族 APO | 建起来了，**不跑** | 同上，填充 0 次 |
| `扬声器 (TOPPING USB DAC)` | 0 / 无 APO | **正常** | i16、288 帧（6.00 ms）缓冲、周期 144 帧、`GetStreamLatency` 6.00 ms；2 s 内填充 **313** 次（≈1878 ms 音频） |

**第一版结论是错的，这里是更正。** 当时把「独占不跑」归因给 APO 链，理由是「无 APO 的端点正常」。
但把该端点的音效增强关掉（`Disable_SysFx = 1`，已确认写入）之后**独占依旧不跑**，所以那个因果不成立。

真正的原因是**取用方式**：同一端点、同一份代码，

| 配置 | 结果 |
|---|---|
| `flags = EVENTCALLBACK`、`periodicity = bufferDuration` | Initialize/Start 都成功，设备不消费（填充 0 次） |
| `flags = 0`（轮询）、`periodicity = 0` | **正常跑**，512 帧缓冲，1 ms 定时器精度下 3 s 只欠载 ~500 样本 |

所以正确的表述是：**该端点的事件驱动独占不可用，轮询可用**；与 APO、与采样率（48 / 192 kHz 都试过）都无关。
这提醒一件事：`Initialize` 与 `Start` 返回成功**不等于流在跑**，必须看设备时钟是否推进。

> 工具侧已加 `--exclusive-mode auto|event|poll` 与「填充 0 次就报错」的判据，
> 并且测量期间把系统定时器精度提到 1 ms（默认 15.6 ms 会让轮询按 15 ms 的节奏喂料，必然欠载）。

### 1.3 延迟拆分：数字回环（P2-6 续，`--loopback`）

物理环回把「播放缓冲 + DAC + 空气 + ADC + 采集缓冲」揉成一个数，分不清该优化哪一段。
`--loopback` 在**播放设备上开 WASAPI 回环采集**（把渲染设备当输入用，cpal 自动开 loopback 模式），
拿到的是设备真正要播的那份数据，于是两段可以分开量。

前提：回环采集必须用端点**混音格式**（本机 192 kHz；传 48 kHz 直接 `AUDCLNT_E_UNSUPPORTED_FORMAT`），
所以渲染采样率也得跟着走——为此 `start_playout` 增加了 `preferred_rate` 参数。

| 日期 | 路径 | 端点 / 采样率 | 指标 | n | p50 | 极差 | 相关度 | 备注 |
|---|---|---|---|---:|---:|---:|---:|---|
| 2026-11-17 | 数字回环 | `扬声器 (TOPPING USB DAC)` / 48 kHz | 写入 → 设备输出 | 2 | 23.32 | 0.005 | 1.000 | 逐位一致，SNR 溢出 f32 |
| 2026-11-17 | 数字回环 | `扬声器 (Realtek(R) Audio)` / 192 kHz（无重采样） | 写入 → 设备输出 | 3 | 34.27 | 0.037 | 1.000 | 逐位一致 |
| 2026-11-17 | 数字回环 | 同上 / **渲染 48 kHz**（引擎 48→192 重采样） | 写入 → 设备输出 | 3 | 36.34 | 0.046 | 1.000 | 重采样只值 **2.07 ms** |
| 2026-11-17 | 物理环回 | Realtek → USB 麦 / 48 kHz | 写入 → 麦克风回来 | 5 | 175.29 | 0.899 | 0.68 | 音效增强**已关闭** |
| 2026-11-17 | 物理环回 | 同上，音效增强**开启** | 同上 | 5 | 198.29 | 0.714 | 0.68 | 关掉增强省 **23 ms** |

**独占模式的缓冲差分**（同一路径，只改设备缓冲，n=1 各）：

| 设备缓冲 | 实测延迟 | 相对上一档 |
|---|---:|---|
| 512 帧（10.67 ms） | 137.92 | — |
| 1536 帧（32.00 ms） | 159.40 | 缓冲 +21.3 ms → 延迟 +21.5 ms |
| 3072 帧（64.00 ms） | 191.57 | 缓冲 +32.0 ms → 延迟 +32.2 ms |

缓冲每加 X ms，延迟就加 X ms → **播放侧如实计入**；剩下的 ~127 ms 与播放缓冲无关，是常量。

由此得到拆分：

| 段 | 延迟 | 怎么量的 |
|---|---:|---|
| 我们的播放路径（写入 → 设备输出） | **23.3 ms**（TOPPING）/ **34.3 ms**（Realtek） | 数字回环，相关度 1.000 |
| 声学往返（写入 → 麦克风回来） | **175.3 ms** | 物理环回 |
| 差额 = 扬声器 → 空气 → 麦克风 | **~141 ms** | 上面两行相减 |

这 141 ms 不是音效链（采集端点 `fx=1`、没有任何 APO CLSID），也不是我们自己的缓冲
（差分实验已排除播放侧）。**还没拆开的唯一变量**：端点混音格式是 192 kHz 而我们按 48 kHz 跑，
中间隔着驱动的重采样。把该端点的默认格式改成 48 kHz 就能去掉它——一次点击的单变量实验。

> 结论：本机 D1 = **175 ms**，其中只有 34 ms 归我们的播放路径，**~141 ms 在输入方向（USB 麦克风）**。
> 这也解释了为什么关掉音效增强只省 23 ms：APO 在播放侧，而大头在采集侧。
> 对产品的含义：D1 的瓶颈是用户的麦克风，不是我们的处理链；客户端的延迟承诺必须按实测设备给，
> 不能假设「软件够快就够了」。

#### 1.3.1 那 141 ms 不是重采样（`--render-rate` 实测）

端点混音格式是 192 kHz，而我们的流是 48 kHz，中间隔着引擎（共享）或驱动（独占）的重采样。
用 `--render-rate 48000` 让**渲染**留在 48 kHz、**回环采集**仍锁在 192 kHz，就能单独量出它的代价：

| 数字回环的渲染采样率 | 延迟 | n | 极差 |
|---|---:|---:|---:|
| 192 kHz（不重采样） | 34.27 ms | 3 | 0.037 |
| 48 kHz（引擎 48→192） | **36.34 ms** | 3 | 0.046 |

**重采样只值 2.07 ms。** 于是：

| 段 | 延迟 |
|---|---:|
| 声学往返（渲染 48 kHz） | 175.29 ms |
| 数字回环（渲染 48 kHz，同一渲染路径） | 36.34 ms |
| **差额 = DAC 模拟 + 空气 + 麦克风** | **138.95 ms** |

DAC 模拟与空气合计约 1–2 ms，所以 **~137 ms 是这只 USB 电容麦的输入延迟**。
它不出现在 Windows 的 APO 列表里（采集端点 `fx=1`、无 CLSID），是设备固件/驱动的内部缓冲。

> 这条把 C-12 收紧了：**D1 的 175 ms 里，139 ms 是麦克风，34 ms 是我们的播放路径，2 ms 是重采样。**
> 也就意味着改系统默认格式（192 kHz → 48 kHz）**不值得做**——最多省 2 ms。

#### 2.1 AGC2 的电平行为（P3-1，release，`codec=none`，20 s 素材）

| 素材 | 输入 RMS | 输出 RMS | 增益 | 稳态峰值 | 被钉在 \|x\|>0.99 的样本 |
|---|---:|---:|---:|---:|---:|
| `clean` | -19.26 dBFS | -17.74 | **+1.52 dB** | -5.5 dBFS | 57（0.006%） |
| `fan` | -19.39 | -19.89 | **-0.50 dB** | -11.2 dBFS | 11（0.001%） |
| `babble` | -21.11 | -18.83 | **+2.28 dB** | -7.2 dBFS | 33（0.003%） |

三段素材本身就在合适电平上（-19 dBFS RMS ≈ 正常说话音量），所以 AGC2 基本「不动手」（±2 dB 内），
稳态峰值留在 -5 ～ -11 dBFS、没有顶满量程——这是想要的行为。

**开场瞬态（已知缺陷，待裁决）**：WebRTC 默认 `initial_gain_db = 15`，而增益下降速率上限是 6 dB/s，
所以每路流的**头 1–2 s** 会比稳态响一截：

| 时段（`clean`） | RMS |
|---|---:|
| 第 1 秒 | **-11.2 dBFS** |
| 稳态（3 s 后） | -19.2 dBFS |

即 **+8 dB 的开场爆音**，峰值被限幅器顶到满量程（全片 57 个样本被钉在 \|x\|>0.99）。
备选是把 `initial_gain_db` 设为 0——单元测试 `zero_initial_gain_removes_the_startup_burst` 证明
瞬态消失，代价是安静麦克风开头几秒偏轻（6 dB/s 爬升）。取舍需要真实语音素材做盲听，归入 P3-6 / D6，
**当前保持 WebRTC 默认**，并由 `default_initial_gain_causes_a_bounded_startup_burst` 把行为钉住。

#### 2.2 RNNoise 的电平行为（P3-2）——**不能用来判断音质**

| 素材 | 输入 RMS | `rnn` 后 | Δ | `highpass,rnn,agc2` 后 | Δ |
|---|---:|---:|---:|---:|---:|
| `clean`（合成元音） | -19.26 dBFS | -21.72 | **-2.46 dB** | -18.78 | +0.48 dB |
| `fan`（风扇） | -19.39 | -32.18 | **-12.79 dB** | -26.06 | -6.66 dB |
| `keyboard`（键盘） | -26.39 | -27.17 | **-0.79 dB** | -25.08 | +1.31 dB |
| `babble`（多人） | -21.11 | -21.66 | **-0.55 dB** | -37.25 | -16.14 dB |
| `noise_only`（纯噪声） | -10.79 | -13.20 | **-2.41 dB** | -11.67 | -0.88 dB |

逐秒看更清楚（`clean`，`rnn` 单跑）：-19.4 / -19.2 / -21.7 / **-70.3** / -39.7 / -43.2 / -41.5 / -22.1 dBFS。
也就是说：合成元音在第 3 秒被**几乎完全门控掉**（-70 dBFS），第 8 秒才回来。

**这条不能读成「RNNoise 不行」**，只能读成「合成素材不能用来判音质」：

- `clean` 是 `testkit gen` 用三个共振峰 + 音节包络合成的元音，没有辅音、没有音高变化、没有真实录音的房间与口型；
- RNNoise 的 VAD 与增益是拿**真实语音**训练的，对这类信号的判决没有代表性；
- 高通前置会显著改变门控行为（同一段 `babble`：不加高通 -0.55 dB，加高通后 -16 dB）——说明判决对频谱细节极敏感；
- 真实语音素材目前没有（ADR-0007 的阻塞项），所以**音质结论必须等 D6 盲听**。

工程上能从这张表拿到的只有两件事：

1. **电平不能靠降噪器**：它的门控可以到 -40 dB，也能基本不动（-0.6 dB）。电平由后面的 AGC2 负责，这也是设计顺序「降噪 → AGC2」的理由之一；
2. **环节顺序要钉死**：`highpass` 在 `rnn` 之前还是之后，门控结果差 15 dB 以上。顺序写进技术设计 §6.2，并由 `ChainDesc` 显式表达。

## 3. 丢包与鲁棒性

三条读法：

1. **0 % 丢包时输出与参考逐样本相同**（全局 SNR 200 dB = 零误差，`energy_err_db = 0.00`）。
   这是测量管线的自检：参考走「编码即解码」，输出走「编码 → 抖动缓冲 → 解码」，两条路在
   无损网络下必须重合。它红了就说明是管线坏了，不是丢包。
2. **PLC 在 3 % 就开始塌**：SNRseg 从 35 → 26.3 dB，帧能量误差 0.04 → 1.22 dB。10 % 时
   SNRseg 9.86 dB，已经不是「音质下降」而是「听不清」。
3. **冗余把 5 % 从 21.0 dB 拉回 34.0 dB、10 % 从 9.9 dB 拉回 30.2 dB**，代价是线上码率
   32.2 → 64.3 kbps。1 %/3 % 下两列完全相同，是因为该种子下没有任何一帧的两份副本同时丢
   （3 % 时期望的双丢包数 ≈ 600 × 0.0292² ≈ 0.5，落在 0）。

**指标口径与已知局限（重要，别把这张表读成感知分数）**：

- **SNRseg 不是感知分数**。PESQ/POLQA 是授权算法，没有可信的离线 Rust 实现；自己拍一个
  「感知分」等于伪造结论。SNRseg 比的是**波形**，对丢包引入的爆音、断续、金属声只是间接敏感。
  「可听性」的判决仍然阻塞在 D6 盲听（C-18）。
- **高丢包下 SNRseg 应当读作保真度下界**。NetEQ 丢包后先 `expand`（插一帧）再 `accelerate`
  （抽掉几毫秒），块内的时间轴不再是常数，逐块对齐必然有残余错位；而 1 kHz 在 48 kHz 下偏 5
  个样本就是 37° 相位。`对齐极差` 那一列就是这个置信度：0 ms 时可信，73 ms 时只能当下界看。
  所以同时给了**帧能量误差**（10 ms 能量差的均值），它对齐不敏感，是更稳的那一列。
- **抖动缓冲深度峰值始终 ≤ 20 ms**（NetEQ 自报 `current_buffer_size_ms`），说明 `对齐极差`
  不是延迟真的涨了，而是对齐估计在损伤下变不确定。这一条同时验证了附录 A 第 9 行的 L2 预算
  （15–20 ms）在 10 % 丢包下仍然守得住。

### 3.2 Opus in-band FEC 接不上 NetEQ（结论，不是猜测）

选型报告 §2.6 把 in-band FEC 当成弱网的第一道防线。实测**接不上**：

- `neteq` 的 `AudioDecoder` trait 只有 `decode(encoded) -> Vec<f32>`，没有 FEC 入口；
- Opus 的 in-band FEC 要求「丢包时用**下一包**解出当前帧」，产出的是 **PCM**；
- 而 NetEQ 要的是**包**才能排进它自己的播放队列（序号、时间戳、时间伸缩都基于包）。

要接上只有两条路：改 `neteq` 的 trait（fork 或上游 PR），或者放弃它的时间伸缩自己写抖动缓冲。
两条都不是「顺手」的量级。**所以 P4-3 先用「包级冗余」量出弱网能买到多少 dB（上表），再决定
要不要为 FEC 动 neteq**——如果 5 % 丢包下冗余已经把 SNRseg 顶到 34 dB，动 neteq 的动力就很小。

冗余与 FEC 的差别只有一个：冗余恢复出来的是一份**真包**（能直接塞进 NetEQ），FEC 恢复出来的
是 PCM。在 0 抖动的模型下两者恢复概率相同（1 − p²），所以这张表的冗余列可以当作 FEC 的
**上界估计**。
